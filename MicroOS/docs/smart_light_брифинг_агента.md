# БРИФИНГ АГЕНТА: профиль smart_light (МикроОС 5.0)

> Назначение документа: холодный старт новой ветки разработки. Прочитав

> Документ написан из «ядерной» ветки (smart_lock + home_master).
> Третья редакция: 2026-08-13, ядро **5.7.0** (вторая: 2026-08-06, ядро
> 5.4.1; первая: 2026-08-02). Что изменилось за неделю — §2, там многое.

## 1. Что это за проект

**МикроОС 5.0** — модульная ОС для экосистемы умного дома автора.
Неизменяемое ядро + подключаемые профили устройств. Эталонный профиль —
**smart_lock** (контроллер СКУД, в проде), на нём отлажено ядро.

Философия (не нарушать):

- **Ядро неизменяемо.** Профиль подключается через точки инжекции данными,
  а не правками ядра. Если «чешется» править ядро — это повод для сервиса
  ядра, и такие вопросы выносятся в ядерную ветку.
- **Автономность.** Устройство полноценно работает без HA/брокера/интернета.
  HA — надстройка, не точка отказа. Упала сеть — бизнес-логика продолжается;
  поднялась — накопленное доезжает само (outbox-реплей, доказан на стендах).
- **Параноидальный проводной контур (решение владельца 05.08.2026).**
  WiFi/BT глушатся на ВСЕХ устройствах, только провода. Реализация —
  см. §8, там произошла важная смена подхода.
- **Параноидальная безопасность.** Секреты — только в NVS, никогда в JSON.
  Токены сессий вместо ПИНов.
- **Детерминизм.** Никакого `localtime_r`/TZ-окружения, никаких «обычно
  работает». Уроки записываются прямо в код комментариями.

Наследие: монолит v4.2.2 (в проде), мёртвая ветка v5.0_dead (архитектурный
задел; идеи протокола Мастер↔Помощники — §9).

## 4. Ядро: что есть и как подключается

20–21 модуль грузятся фазами: describe → registerExtensions → init → start,
каждую фазу ядро прогоняет для всех, затем кооперативный tick-цикл
(бюджет onEvent 50 мс; своих задач FreeRTOS в профилях не плодить).

Ключевые сервисы: ConfigService (схема+валидация+NVS секреты+debounce save+
CFG_EVENT_CHANGED; таблица общая, CFG_MAX_FIELDS=96, addFields fail-fast —
см. правило 15), StorageService (LittleFS, atomicWrite, NVS), TimeService
(NTP+RTC DS3231, детерминированный пояс), NetworkService (ETH по BoardDesc,
DHCP hostname, мониторинг шлюза, уровни деградации FULL/LOCAL_NET/AUTONOMOUS,
локальный режим для плат без сети), MqttTransport (outbox-реплей — доказан
на стендах обоих контроллеров), HttpService (/api/config, /api/system,
/api/time/set, инжекция профильного API через IUiProvider — контракт
`handleApi(pathTail, ShUiRequest, buf, size, statusCode)`, JSON-буфер 24 КБ,
arg() транзиентен — копировать сразу), AudioService
(очередь/приоритеты/ADVERT-семантика, SoundPack данными), HealthMonitor
(ПАЗ: WDT 10 с, проверки IHealthCheck, heap, температура), UpdateService
(A/B OTA + откат + bootloop→Safe Mode), LogService, AuditService,
TelemetryService, DataLogService (3 яруса: 6ч/31сут/год), AuthService,
CounterService (PCNT — только на кристаллах с PCNT, см. §10),
ScheduleService (правила из конфига/IScheduleProvider, Fail-Safe при
недостоверном времени), SpeechBuilder (составная речь из папок 05/06).
Профильные сервисы мастера (образец сложного профиля): SdService,
BrokerService, BridgeService, JournalService — в `projects/home_master/src/`.

**Точки инжекции профиля:** IDeviceProfile (boardId в HardwareManifest!),
IConfigProvider, IUiProvider, IHealthCheck, ISoundPack. Драйверы — в
DriverRegistry (урок: написать драйвер мало — зарегистрируй).

## 5. Железные правила (уроки, высечены в коде)

1. **Время — детерминированное.** `getLocalTime = gmtime_r(unix +
   tz_offset*3600)`. RTC хранит UTC-wall. Никакого localtime_r/TZ.
2. **printf-формат и аргументы — 1:1, глазами, после КАЖДОЙ правки.**
3. **CFG_READONLY тоже персистится** (счётчики!).
4. **ETH.setHostname — ПОСЛЕ ETH.begin** (до — тихий no-op).
5. **Новые поля JSON-статуса — в КОНЕЦ**, отдельным аргументом.
6. **Секретам не место** в JSON/логах/скриншотах.
7. **Панель кэшируется агрессивно**: менял data/web — bump CACHE_NAME в sw.js.
8. **Никаких String/std::map в горячих путях ядра** (heap-churn).
9. Хост-тесты — до прошивки, всегда. **43351 PASS — норма** (на 13.08),
   меньше — стоп.
10. ПАЗ-пороги и «ручки» — в конфиг с валидацией, не константы.
11. **НОВОЕ (M0, 06.08): app.bin никогда не шьётся без своей таблицы
    разделов.** Смена схемы разметки = только erase + flash_full
    (Build Master). Иначе LittleFS «исчезает» на ровном месте.
12. **НОВОЕ (S3, 06.08): буферы >4 КБ — только в куче/статике, не на стеке.**
    loopTask = 8 КБ; цепочка VFS→LittleFS→flash на S3 глубже классики,
    стек-канарейка ловит это паникой в бутлупе (урок 5.3.1).
13. **НОВОЕ (S3, 06.08): две системы нумерации SPI.** Arduino SPIClass на
    S3: FSPI=0 (шина SPI2), HSPI=1 (шина SPI3); SPIClass(2) — несуществующая
    шина. IDF spi_host_device_t (ETH.begin): SPI2_HOST=1, SPI3_HOST=2.
    На классике: FSPI=1, HSPI=2, VSPI=3. Путаница стоила трёх «мёртвых»
    SD-карт (урок 5.3.2).
14. **НОВОЕ (06.08): явные вызовы WiFi.mode/esp_bt_* ЗАПРЕЩЕНЫ** — тянут
    в прошивку +337 КБ стеков и пробивают бюджет 1,2 МБ (см. §8).
15. **НОВОЕ (13.08, урок 5.6.0/5.6.1): таблица конфиг-полей общая и
    конечная** (CFG_MAX_FIELDS=96). addFields() fail-fast: одно не влезшее
    поле обрывает всю группу молча (одна строка [E] в логе, устройство
    живёт на вшитых умолчаниях). Контроль — бут-лог `init: N fields
    registered`. Рост таблицы = проверить и HTTP_JSON_BUF (~250 Б/поле).
16. **НОВОЕ (13.08): mklittlefs недетерминирован** — md5 образа гуляет
    между сборками при байт-идентичном входе. Доказательство изменения
    ФС — round-trip содержимого (littlefs-python), НЕ md5. Exit-коду
    mklittlefs тоже не верим (при переполнении падает молча с exit 0).
17. **НОВОЕ (13.08, M3.2): ShUiRequest::getArg() транзиентен** — значение
    живёт до следующего вызова getArg (кольцевой буфер транспорта).
    Копировать в локал СРАЗУ, потом читать следующий аргумент.

## 8. Глушение радио — КАК ОНО СДЕЛАНО (смена подхода, 5.3.2)

**Подход первой редакции этого брифинга (явные WiFi.mode(WIFI_OFF) +
esp_bt_controller_disable() + conformance-страж) — ОТМЕНЁН.** Измерено на
сборке 5.3.2: такие вызовы тянут в прошивку весь WiFi/BT-стек (**+337 КБ**)
и пробивают дисциплинарный бюджет 1,2 МБ.

Действующий подход — **«радио выключено отсутствием кода»**: RF-блок не
запитан, пока кто-то не вызовет esp_wifi_init/BT-init, а ни один модуль
ядра и профилей этого не делает. Ядро трогает лишь `WiFi.onEvent`
(регистрация колбэков ETH-событий — не радио) и псевдонимы
WiFiClient/WiFiServer (= NetworkClient/NetworkServer ядра 3.x — сокеты
lwIP, работают поверх Ethernet без инициализации радио).

Обязанность профиля smart_light (и стиль conformance-стража): **не вызывать
WiFi/BT API вообще** — ни инициализацию, ни даже «выключение». Лучшая
глушилка — отсутствие кода, который мог бы радио включить. Wi-Fi fallback
в ядре не существует в принципе (аудит 06.08.2026).

Опционально оценить на стенде: `setCpuFrequencyMhz(80/160)` — кристалл
живёт на 78–80 °C, снижение частоты может дать градусы.

## 10. smart_light: входные параметры (актуализировано 06.08.2026)

**Решения владельца 06.08.2026 (твёрдые):**

- **Помощник = ESP32-C3 SuperMini.** Маленькая плата, достаточно ног/мозгов,
  единая архитектурная платформа для всех Помощников.
- **Связь Мастер↔Помощники: RS485, FULL DUPLEX со стороны Мастера** —
  т.е. две витые пары (TX-пара Мастера и RX-пара), не одиночная пара
  half-duplex. Трансиверы: 2× MAX485 на сторону или full-duplex MAX489/
  MAX491/MAX3488. Помощников на шине может быть несколько: RX-пара —
  мультидроп, передаёт только опрошенный (коллизии исключает циклический
  опрос Мастера).
- **Роль Помощника (самый нижний, но критичный уровень):** сбор и
  ВАЛИДНАЯ подготовка данных датчиков для Мастера; приём команд/данных
  от Мастера и их вывод (AMOLED-дисплей, DFPlayer-озвучка). Помощник
  **сразу знает всю возможную периферию** (таблица поддерживаемых
  устройств данными), сканирует фактически подключённое и рапортует
  Мастеру манифест подключённых устройств + обработанные данные.
- Параноидальный контур распространяется и на Помощников: радио C3
  глушится «отсутствием кода» (§8), связь только по шине.

**Ядерная поддержка C3 SuperMini (уже в ядре 5.4.1, эта ветка сделала):**

- `BoardId::Esp32C3SuperMini` в `src/platform/BaseProfile.*`: EthKind::None
  (сети нет фактом железа → NetworkService сам в локальном режиме,
  честный AUTONOMOUS, HTTP/MQTT не стартуют), системная I2C SDA=6/SCL=7,
  документация пинов в шапке BaseProfile.h. Идентичность — базовый MAC
  из eFuse (радио не трогается).
- Smoke-сборка ядра под esp32c3 (RISC-V, unicore, 4 МБ flash, ~400 КБ
  SRAM): собирается и линкуется целиком (1 171 500 Б с профильными
  модулями hm — реальный профиль Помощника будет заметно легче).
- **У C3 НЕТ PCNT** — CounterService::attachPcnt на C3 честно отказывает
  (guarded по SOC_PCNT_SUPPORTED). Импульсные счётчики — не для C3.
- **UART всего два:** UART0 (консоль стенда RX=20/TX=21; основной лог —
  USB-CDC, FQBN `CDCOnBoot=cdc`) и UART1 (матрица GPIO) — целевой под
  RS485. DFPlayer → либо SoftwareSerial 9600 (проверенный паттерн), либо
  делить UART1 — дизайн-вопрос ветки.
- Пины C3 SuperMini: разведены GPIO0–10, 20, 21. Осторожно: GPIO8 (LED
  активен низким + страппинг), GPIO9 (BOOT), GPIO2 (страппинг, на boot —
  высокий). GPIO11–17 — встроенная flash. Свободно для профиля:
  0, 1, 3, 4, 5, 10, 20, 21 (+2 с оговоркой). Бюджет ног под RS485
  (TX/RX/DE) + I2C + AMOLED (SPI/CS/DC/RST/BL) + DFPlayer — считать
  при проектировании, он впритык: это нормально, но осознанно.
- Build Master v12.3: чип esp32c3 поддержан (детект/стражи), пресет
  «ESP32-C3 SuperMini (USB-CDC)» в списке плат.
- Стенд стабильности платы (когда придёт железо): boot + conformance
  (14 PASS — норма), Safe Mode по BOOT (GPIO9, зажать ПОСЛЕ начала
  загрузки), soak 72 ч с heap-watermark, USB-CDC лог.

**Прочее (без изменений):**

- Исполнители Мастера: диммерные каналы (отсечка по фронту, защита,
  аварийные фразы старой звуковой схемы).

## 12. Рабочий процесс (не ломать)

- Код ядра — в `src/`, профиль — в `projects/<profile>/`; ядро профилем
  не правится. Плата объявляется boardId, периферия — манифестом.
- Хост-тесты зелёные (43351 PASS) → сборка arduino-cli (esp32 core 3.3.11)
  → FS: mklittlefs прямо по data/ (с 5.6.x без gzip — разделы ФС
  достаточны) + обязательная верификация образа парсингом (round-trip
  СОДЕРЖИМОГО через littlefs-python: md5 образа недетерминирован, exit-коду
  mklittlefs не верим) → набор в arduino/
  (per-file: rm + cp.tmp + sync + mv + cmp; деревья: diff -r MATCH).
- Каждая сборка-релиз: bump MICROOS_VERSION_STR; тег `MICROOS|x.y.z|END`
  проверять в бинаре.
- Панель: sw.js CACHE_NAME bump при каждом изменении (устройства с PWA).
- Каждый инцидент в поле — урок: комментарий в код + (обычно) тест.
- Секреты не покидают устройство; восстановление из бэкапа — только
  осознанно, «без всяких предупреждений, понимая что делаешь».
- Стиль общения с автором: русский, по делу, «уроки» нумеруем и помним.

# БРИФИНГ АГЕНТА: профиль weather_gate (МикроОС 5.0)

> Назначение документа: холодный старт новой ветки разработки. Прочитав
> его (и пакет целиком, порядок — в `00_ПРОЧТИ_МЕНЯ.md`), агент обязан
> работать так, будто участвовал в проекте с начала.
> Документ написан из «ядерной» ветки (smart_lock + home_master).
> Первая редакция: 2026-08-16, ядро **5.8.0**.
> Это не DIY-поделка: «хоть и гаражный» проект, но с промышленной
> дисциплиной качества. Что это значит числами — §12 и `06_уровень_кондиций.md`.

---

## 1. Что это за проект

**МикроОС 5.0** — модульная ОС для экосистемы умного дома автора.
Неизменяемое ядро + подключаемые профили устройств. Эталонный профиль —
**smart_lock** (контроллер СКУД, в проде), на нём отлажено ядро;
второй живой профиль — **home_master** (мастер контура, в проде).

Философия (не нарушать):

- **Ядро неизменяемо.** Профиль подключается через точки инжекции данными,
  а не правками ядра. Если «чешется» править ядро — это повод для сервиса
  ядра, и такие вопросы выносятся в ядерную ветку.
- **Самодостаточность (принцип владельца, дословно):** «любое
  устройство/контроллер абсолютно самодостаточен, ничего нет — сам всё
  делаю, есть сеть и окружение — функционал только расширяется».
  Это архитектурный закон ветки weather_gate, см. §9.
- **Параноидальный проводной контур.** WiFi/BT глушатся на ВСЕХ устройствах
  «отсутствием кода» (§8), только провода. Осознанное единственное
  исключение ветки — радиоприёмник CC1101, receive-only (§7, §8).
- **Параноидальная безопасность.** Секреты — только в NVS, никогда в JSON.
- **Детерминизм.** Никакого `localtime_r`/TZ-окружения, никаких «обычно
  работает». Уроки записываются прямо в код комментариями.

Наследие: монолит v4.2.2 (в проде), мёртвая ветка v5.0_dead (архитектурный
задел).

## 4. Ядро: что УЖЕ есть под weather_gate (не изобретать)

Ветка weather_gate необычно выгодна: половина задач уже решена ядром.
Прежде чем проектировать свой механизм — проверь этот список.

- **DataLogService + DataLogCore (ядро, с 5.0)** — готовый даталоггер
  временных рядов. На канал: RAW-кольцо в RAM (360 точек ≈ 6 ч при
  1/мин), ярус HOUR (append-файл LittleFS, 744 записи = 31 сутки),
  ярус DAY (366 записей = год). Профиль регистрирует каналы
  (`registerChannel(id, title, unit)`), точки пишет `logPoint(ch, v)`.
  Чистая логика вынесена в DataLogCore.h и покрыта хост-тестами.
  **Это и есть «RAM-кольцо давления для Замбретти» и локальная история
  шлюза — писать своё кольцо ЗАПРЕЩЕНО.** 8 каналов максимум
  (DLOG_MAX_CHANNELS) — погоде хватает: press/temp/hum/wind/rain/lux(?).
  Точка с недостоверным временем отбрасывается (урок 5.0.x).
- **Ds3231Driver (ядро)** — RTC на системной I2C (0x68, SDA=32/SCL=33,
  400 кГц). На той же шине сядет BME280 (0x76/0x77) — конфликта адресов
  нет, шина общая, BusManager следит за здоровьем I2C и умеет
  восстановление (см. SmartLockHealthChecks).
- **TimeService** — NTP + RTC, детерминированный пояс
  (`gmtime_r(unix + tz*3600)`). Достоверность времени — флаг; Замбретти
  и даталоггер обязаны уважать его (без достоверного времени точки не
  пишутся, тренд не считается — Fail-Safe, как у ScheduleService).
- **MqttTransport** — outbox-реплей (доказан стендами обоих контроллеров),
  BOOT-событие с причиной рестарта (5.8.0), клиент-id = hostname.
  Публикация погоды — через него, никаких своих MQTT-клиентов.
- **TelemetryService** — периодический статус вверх; погодные величины
  регистрируются телеметрийными айтемами профиля.
- **ConfigService** — схема+валидация, NVS-секреты, CFG_EVENT_CHANGED,
  setHiddenGroups для служебных групп. Высота установки датчика,
  пороги, периоды — ВСЁ в конфиг с валидацией, не константы (правило 10).
- **HttpService + IUiProvider** — панель и API профиля; контракт
  `handleApi(pathTail, req, buf, size, statusCode)`, getArg транзиентен
  (правило 17), JSON-буфер 24 КБ. В панели замка уже живёт uPlot
  (`data/web/uplot.*`) — графики давления/температуры брать оттуда же.
- **HealthMonitor** — ПАЗ: WDT 10 с, IHealthCheck-проверки профиля
  (BME280 молчит? CC1101 без пакетов час? — это IHealthCheck-и ветки).
- **UpdateService** — A/B OTA + bootloop→Safe Mode. Работает из коробки.
- **StorageService.atomicWrite** — для кэша «последнего хорошего прогноза»
  (паттерн /wx_cache.json у замка — образец).
- **projects/test_rig** — минимальный профиль-скелет на WT32-ETH01
  (той же плате!): компилирует ядро, гоняет конформанс. Начало ветки —
  копия test_rig, а не пустой каталог.
- **Готовый потребитель погоды — smart_lock (код менять НЕ нужно):**
  замок подписан на конфиг `lock.weather_topic`, парсит JSON
  `{"temp":…, "feels_like"|"feel":…, "state"|"text":…}` (незнакомые ключи
  игнорирует!), кэширует в /wx_cache.json, пишет канал wx_t в свой
  DataLog. Шлюз публикует совместимый JSON — и погода на замке работает
  без единой правки замка, только его конфиг. Проверка «HA выключен,
  погода на замке есть» — приёмочный сценарий ветки (§12).

Мост M2 на мастере уже умеет транзит вверх/вниз к HA-брокеру: публикации
шлюза при живом HAOS уезжают в HA сами, без кода ветки.

## 5. Железные правила (уроки, высечены в коде)

Полный журнал уроков — `07_дорожная_карта_кондиций.md`. Здесь — те, что
бьют по ветке weather_gate напрямую, плюс новые из 5.8.0:

1. **Время — детерминированное.** `getLocalTime = gmtime_r(unix +
   tz_offset*3600)`. RTC хранит UTC-wall. Никакого localtime_r/TZ.
2. **printf-формат и аргументы — 1:1, глазами, после КАЖДОЙ правки.**
3. **CFG_READONLY тоже персистится** (счётчики дождя — это счётчики!).
4. **ETH.setHostname — ПОСЛЕ ETH.begin** (до — тихий no-op).
5. **Новые поля JSON-статуса — в КОНЕЦ**, отдельным аргументом.
6. **Секретам не место** в JSON/логах/скриншотах.
7. **Панель кэшируется агрессивно**: менял data/web — bump CACHE_NAME
   в sw.js (копируешь sw.js из эталона — смотри правило сразу).
8. **Никаких String/std::map/std::vector в горячих путях** (heap-churn).
   Радио-пакеты и тренды — фиксированные POD-буферы и кольца.
9. Хост-тесты — до прошивки, всегда. **43351 PASS — норма** (на 16.08),
   меньше — стоп. Новая чистая логика без новых тестов не принимается.
10. ПАЗ-пороги и «ручки» — в конфиг с валидацией, не константы.
11. **app.bin никогда не шьётся без своей таблицы разделов.** Смена
    разметки = только erase + flash_full (Build Master).
12. **Буферы >4 КБ — только в куче/статике, не на стеке** (урок S3 5.3.1;
    на классике loopTask тоже не резиновый).
13. **Две системы нумерации SPI** (Arduino FSPI/HSPI vs IDF
    SPI2_HOST/SPI3_HOST). На ESP32-classic (WT32-ETH01): FSPI=1, HSPI=2,
    VSPI=3. CC1101 — на VSPI или HSPI, выбор зафиксировать в манифесте.
14. **Явные вызовы WiFi.mode/esp_bt_* ЗАПРЕЩЕНЫ** (+337 КБ стеков в
    прошивку). Радио выключено отсутствием кода (§8). CC1101 — не WiFi/BT,
    но правило «не тащить лишние стеки» действует и на него.
15. **Таблица конфиг-полей общая и конечна** (CFG_MAX_FIELDS=96, на все
    профили в сборке). addFields() fail-fast. Контроль — бут-лог
    `init: N fields registered`. Свои ~20–30 полей планировать заранее.
16. **mklittlefs недетерминирован** — md5 образа гуляет; доказательство
    изменения ФС — round-trip содержимого (littlefs-python), exit-коду
    mklittlefs не верим.
17. **ShUiRequest::getArg() транзиентен** — копировать значение в локал
    СРАЗУ, потом читать следующий аргумент.
18. **НОВОЕ (5.8.0): веб грузится после сети с задержкой 10 с** —
    не «чинить» этот гард, он от бут-шторма. Панель, запрашивающая API
    раньше времени, получает честный отказ — и обязана пережить его.
19. **НОВОЕ (5.8.0, процессное): один файл — одна правка за раз,**
    никаких параллельных edit-ов одного файла (словили гонку правок в
    HomeMasterUi.h — поймал только билд). Зафиксировано как процессный
    урок обеих веток.

## 7. Аппаратура weather_gate (подтверждено владельцем 16.08.2026)

**Плата: WT32-ETH01** — та же, что у эталона (ESP32-classic, 4 МБ flash,
LAN8720, PHY power GPIO16, системная I2C SDA=32/SCL=33). Разметка flash —
как у smart_lock (default.csv: app0/app1 по 0x140000, LittleFS 0x160000).

Периферия профиля:

| Узел | Интерфейс | Назначение |
|---|---|---|
| DS3231 | I2C 0x68 (системная шина, SDA=32/SCL=33) | RTC — драйвер ядра готов |
| GY-BM280 (BME280) | I2C 0x76 или 0x77 (ТА ЖЕ шина) | давление/температура/влажность в точке установки шлюза |
| E07-900M10S (CC1101) | SPI + GDO0 + GDO2 | приём пакетов погодной станции, **только приём** |

Погодная станция владельца: **Fine Offset WS1080 (семейство WH1080),
915 МГц**. E07-900M10S (850–930 МГц) — корректный модуль под неё.

Стартовое предложение пин-плана (финал — через ResourceManager + стенд;
страппинг-пины 0/2/12/15 учитывать, PHY не трогать):

- SPI для CC1101: SCK=14, MOSI=13, MISO=35, CS=5;
- GDO0=36, GDO2=39 (оба input-only — идеально для прерываний приёма);
- I2C: 32/33 (уже системная, BME280 просто садится рядом с DS3231);
- GPIO2 — статус-LED профиля (с оговоркой на страппинг), 12 — резерв.

MISO/GDO на вход-only пинах (35/36/39) — осознанно: эти ноги ничем другим
не занять, а здесь они в самый раз.

BME280: адрес по перемычке модуля (0x76 типично для GY-BM280; SDO к GND).
Первым делом на стенде — скан шины BusManager-ом: должны отвечать 0x68 и
0x76/0x77.

## 8. Радио: доктрина и осознанное исключение

Доктрина флота: **WiFi/BT выключены отсутствием кода** — ни один модуль
не вызывает esp_wifi_init/BT-init; «выключатели» тоже запрещены (тягут
стеки, +337 КБ). Лучшая глушилка — отсутствие кода, который мог бы радио
включить. Wi-Fi fallback в ядре не существует в принципе.

**Исключение ветки weather_gate — CC1101, и оно осознанное:**

- Это НЕ WiFi/BT-стек ESP32, а отдельный sub-GHz трансивер по SPI.
- Режим — **строго receive-only**: драйвер не содержит пути передачи
  (функции TX физически отсутствуют, не «не вызываются»). Передатчик
  станции — у неё самой; шлюз в эфир ничего не излучает, паранойя
  контура не нарушена: проводной сегмент остаётся проводным, а
  беспроводной — односторонним «радиослушателем» погоды.
- Это решение владельца (16.08.2026), зафиксировано здесь, чтобы у
  агента не было соблазна «добавить и передачу».

**Протокол Fine Offset WS1080/WH1080 @915 МГц** — референс-разбор:
rtl_433, декодер `fineoffset_wh1080` (FSK, PWM-кодирование символов,
контроль целостности в пакете; типичный период обновления станции
~48 с — уточнить по живому эфиру на стенде). Состав посылки семейства:
ветер (скорость/порыв/направление), температура, влажность, счётчик
осадков; часть вариантов добавляет UV/освещённость.

Требование ветки: прежде чем писать дешифратор, **записать реальные
пакеты эфира** (SDR или лог сырого битового потока CC1101 на стенде) и
собрать из них **файл тест-векторов** для хост-тестов (§12). Декодер без
векторов с реального эфира не принимается — «обычно работает» здесь не
катит, как и везде в проекте.

## 9. Архитектура данных (сердце ветки)

**Закон самодостаточности (владелец, дословно): «любое устройство/контроллер
абсолютно самодостаточен, ничего нет — сам всё делаю, есть сеть и
окружение — функционал только расширяется».** Всё ниже — следствия.

```
  WS1080 ─915 МГц─> CC1101 ─┐
                            ├─> weather_gate (WT32-ETH01)
  BME280 ─────I2C───────────┘    │ сам: сбор, валидация, история
  DS3231 ─────I2C────────────────┘ (DataLog 6ч/31сут/год), ПРОГНОЗ
                                   (Замбретти), своя панель, свои ПАЗ
                                   │ провод (MQTT через MqttTransport)
                       ┌───────────┼────────────────────┐
                       ▼           ▼                    ▼
                 smart_lock    home_master              HA
               (weather JSON,  (журнал событий;     (транзитом через
                только конфиг)  DataLog-каналы wx    мост M2, когда
                                для рядов — W4)      жив; не нужен)
```

- **Шлюз самодостаточен полностью:** без сети/брокера/мастера/HA он
  собирает погоду, ведёт историю (ярусы DataLog переживают ребут —
  это LittleFS), строит прогноз и показывает всё в своей панели.
- **Вверх по сети:** телеметрия (TelemetryService) + weather-JSON для
  замка (retained; замок подписан конфигом `lock.weather_topic`, код
  замка не трогаем) + события (BOOT, ПАЗ) в журнал мастера.
- **Мастер = долговременное хранилище рядов** (W4): его профиль
  регистрирует DataLog-каналы wx_* и кормит их из MQTT-подписки —
  паттерн уже доказан замком (onWeatherMqtt → logPoint). Журнал
  мастера НЕ используется для рядов — журнал это события (закон §2).
- **Вниз по сети (backfill):** запрос/ответ по MQTT: шлюз после ребута
  может запросить у мастера недостающее окно ряда. ТОЛЬКО после ребута
  и ТОЛЬКО как ускорение: штатно тренд восстанавливается из своих
  ярусов HOUR + свежих точек (~1–3 ч), без мастера. Запрос/ответ —
  chunked, бюджеты сообщений MqttTransport уважать.
- **HA — надстройка:** при живом HAOS публикации уходят транзитом через
  мост M2; при мёртвом — ничего не ломается.

**Прогноз на шлюзе (решение владельца, согласовано 16.08.2026):**

- Алгоритм №1 — **Замбретти**: входы = давление, приведённое к уровню
  моря (высота установки — поле конфига!), тренд за 3 ч, направление
  ветра, сезон. Дождь и влажность Замбретти НЕ использует.
- Тренд 3 ч берётся из RAW-кольца DataLog канала давления (360 точек
  при 1/мин = 6 ч — с запасом).
- Алгоритм №2 (кандидат, позже) — **Сагер**: использует температуру,
  влажность, ветер; оценить после того, как Замбретти живёт в поле.
- Прогноз — значение с меткой времени и флагом достоверности; кэш
  «последнего хорошего» через atomicWrite (паттерн /wx_cache.json).
- Чистая логика — `ZambrettiCore.h` (POD, без Arduino) + хост-тесты
  по опубликованным таблицам Замбретти. Правило проекта: вся математика
  тестируется на хосте, железо только подтверждает.

## 11. Первые задачи ветки (предложение ядерной ветки)

Стадии W1–W5; каждая — со своими хост-тестами, сборкой и стендом.
Порядок менять можно, пропускать ворота (§12) — нельзя.

1. **W1. Скелет + BME280.** Копия test_rig → projects/weather_gate;
   boardId WT32-ETH01; пин-план §7 через ResourceManager. Драйвер
   Bme280Driver (ядро, `src/drivers/`): компенсационные формулы —
   чистая логика, хост-тесты по референс-векторам даташита. Стенд:
   скан I2C (0x68+0x76/77), сравнение с образцовым термометром/барометром,
   дёрганье шины → восстановление (паттерн SmartLockHealthChecks).
2. **W2. CC1101 + декодер WS1080.** Драйвер Cc1101Driver (профильный,
   receive-only, TX-пути отсутствуют физически). Запись реального эфира,
   файл тест-векторов; FineOffsetDecoder — чистая логика, хост-тесты:
   валидные векторы, битые CRC, короткие пакеты, мусор. Стенд: 24 ч
   приёма, сверка с родной консолью станции (доля принятых окон).
3. **W3. Профиль по руководству.** WeatherGateApp/Config/Ui строго по
   `02_руководство_автора_профилей.md`: схема конфига (~20–30 полей,
   высота/пороги/периоды), setHiddenGroups для служебных, панель с
   uPlot (давление+тренд), телеметрия, weather-JSON для замка,
   IHealthCheck-и (BME280, молчание эфира). Приёмка: «HA выключен —
   погода на замке есть».
4. **W4. Ряды на мастере.** HomeMasterApp регистрирует DataLog-каналы
   wx_* и кормит их из MQTT (паттерн замка). Это правка ПРОФИЛЯ
   home_master — согласовать с ядерной веткой до старта; самому ядру
   ничего не нужно. Бюджет: 8 каналов, файлы копеечные (16 Б/час/канал).
5. **W5. Замбретти + backfill + soak.** ZambrettiCore.h + хост-тесты по
   таблицам; тренд из RAW-кольца; кэш прогноза; backfill-запрос к
   мастеру после ребута (опционально-ускоряющий); полевой soak 72 ч
   минимум с heap-watermark и журналом ПАЗ. Сагер — после полевых
   данных Замбретти.

Параллельно всегда: bump MICROOS_VERSION_STR на каждый релиз ветки,
оба боевых профиля обязаны собираться (регресс-контроль ядра).

## 12. Проверочные тесты и ворота качества

Почему это «промышленный уровень, хоть и гаражный» — числами
(подробно: `06_уровень_кондиций.md`):

- **Ворота 1 — хост-тесты.** Каталог `host/` этого пакета: 43351
  assert, 0 FAIL — норма на 16.08. Запуск: `host/run_tests.sh`
  (g++ -std=c++17, без Arduino). Ветка ОБЯЗАНА добавить тесты на свою
  чистую логику: компенсация BME280 (вектора даташита), декодер WS1080
  (вектора реального эфира + мусор), Замбретти (вся таблица + границы
  трендов). Счётчик PASS только растёт.
- **Ворота 2 — сборка.** Оба боевых профиля + weather_gate собираются
  arduino-cli (esp32 core 3.3.11); тег `MICROOS|x.y.z|END` в бинаре.
- **Ворота 3 — образ ФС.** mklittlefs + round-trip верификация
  содержимого (правило 16).
- **Ворота 4 — стенд/поле.** Бенч-протокол стадии (§11): у каждой W —
  свои измеримые приёмки. Общие: heap-watermark стабилен на soak,
  ноль ПАЗ-ложняков, outbox-реплей после обрыва сети, ребут по
  питанию без потери конфига и ярусов.
- **Ворота 5 — журнал релиза.** Запись в дорожную карту: состав,
  уроки, числа бенча. Нет записи — не было релиза.

Прошлая приёмка ядра (образец планки): 3-браузерный стресс панели с
восстановлением heap-watermark, ночные soak 11,4 ч, дёрганье питания
по журналу SD, 12 клиентов встроенного брокера. Твои стенды должны
выглядеть так же скучно и измеримо.

## 13. Рабочий процесс (не ломать)

- Код ядра — в `src/`, профиль — в `projects/weather_gate/`; ядро
  профилем не правится. Запросы на ядро — в ядерную ветку,
  сформулированные как сервис/данные.
- Плата объявляется boardId, периферия — манифестом, пины — через
  ResourceManager (конфликт = лог CONFLICT, а не «вроде работает»).
- Драйверы регистрируются в DriverRegistry (написать мало —
  зарегистрируй). BME280 — в ядерные драйверы (общая шина, пригодится
  другим профилям); CC1101 — профильный.
- Чистая логика отделяется от железа (паттерн *Core.h): DataLogCore,
  JournalCore — образцы. Всё, что можно посчитать без Arduino,
  считается без Arduino и тестируется на хосте.
- Хост-тесты зелёные → сборка → верификация ФС → стенд → запись в
  дорожную карту. Per-file доставка артефактов: rm + cp.tmp + sync +
  mv + cmp; деревья — diff -r MATCH.
- Панель: sw.js CACHE_NAME bump при каждом изменении data/web.
- Каждый инцидент в поле — урок: комментарий в код + (обычно) тест +
  строка в дорожной карте.
- Секреты не покидают устройство. Восстановление из бэкапа — только
  осознанно, «без всяких предупреждений, понимая что делаешь».
- Стиль общения с автором: русский, по делу, «уроки» нумеруем и помним.

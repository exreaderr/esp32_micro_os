# МикроОС 5.0 — базовая модель реорганизованной системы

> **Актуализация (13.08.2026):** документ — проектная база; живое состояние
> реализации (ядро **5.7.0**, эталон smart_lock и мастер home_master в проде,
> журнал парка M3.1/M3.2, host-тесты 43351/0) — в
> `МикроОС_5.0_дорожная_карта_кондиций.md` и сгенерированном из кода
> `МикроОС_5.0_справочник_платформы.md`.

**Статус:** архитектурное предложение (base model)
**Основание:** сквозной анализ МикроОС v4.2.2 (16 модулей, ~24 000 строк)
**Цель:** специализация модулей по функционалу/назначению, устранение системных пересечений

> **Поправка по ходу реализации (фаза 3+):** драйверная модель уточнена до
> трёх уровней — платформа (ядро) / общая периферия (ядро, активация
> профилем) / спецпериферия (каталог `profiles/drivers/`). WiegandDriver
> перенесён из ядра в каталог (нужен только СКУД-подобным устройствам);
> его пины объявляются через `addGpio()`, типизированных полей манифеста
> нет. Актуальное состояние — в справочнике платформы и руководстве автора.

## 1. Что показал сквозной анализ v4.2.2

### 1.1. Сильные стороны текущей версии (сохраняем)

- Единый жизненный цикл модулей (`init/start/stop/tick`) через `IModule` — работает, модули изолированы на уровне include (проверено: ни один .cpp не включает чужой заголовок, кроме `AudioExtensions → AudioManager`).
- Событийная изоляция: модули не вызывают синглтоны друг друга, обмен только через события (проверено по `::getInstance()` — перекрёстных вызовов нет).
- Фиксированные буферы вместо `String` в горячих структурах, рекурсивные мьютексы, защита от повторного входа — правильная встраиваемая практика.
- Командная система (`SH_EVENT_CMD_EXECUTE` / `CMD_*`) — единый способ адресного взаимодействия.

### 1.2. Системные проблемы (устраняем реорганизацией)

**П1. Двойная шина событий.** Событие проходит цепочку: `postEvent → esp_event_post → задача esp_event → AppCore::eventHandler → xQueueSendFromISR → eventProcessorTask → dispatchEvent → module->onEvent`. И *параллельно* каждый из 15 модулей сам подписан на обе шины с `ESP_EVENT_ANY_ID` и получает то же событие второй раз. Итог: двойная доставка, две очереди (по ~150 байт на событие в каждой), каждый модуль просыпается на каждое событие системы.

**П2. Менеджеры-гиганты со смешанной ответственностью:**

| Модуль | Чужие обязанности внутри |
|---|---|
| `ConfigManager` | Применение сетевых настроек (`applyNetworkSettings`, `refreshNetwork`) — сетевая логика в хранилище конфигурации |
| `DeviceManager` | Инициализация Ethernet PHY (WT32-ETH01) — сеть в «железном» модуле |
| `PazManager` | Watchdog + heap + I2C-recovery + ping сети + температура кристалла + залипание актуаторов + **обратная связь СКУД** (`notifyCardScanned/DoorOpened/RelayActivated`) — доменная логика СКУД в системном стороже |
| `TempSensorManager` + `PazManager` | Оба читают температуру кристалла ESP32 — два источника одних данных с разными порогами |
| `UserManager` + `WebServerManager` | Две независимые системы сессий (`_sessions` в обоих), два механизма аутентификации |
| `MqttManager` | Транспорт + троттлинг телеметрии + **Home Assistant Discovery** — прикладной протокол внутри транспорта |
| `RTCManager` | Часы + форматирование + **планировщик** (`isNightTime`, `isWorkingHours`) + будильник |
| `AudioManager` | Драйвер DFPlayer (UART-протокол) + очередь приоритетов + **ночной режим** (зависит от времени суток) |
| `AudioExtensions` | Озвучивание имён пользователей, событий СКУД, погоды, счётчиков — знает про все домены сразу |

**П3. Пять модулей напрямую работают с LittleFS/NVS** (`ConfigManager`, `LogManager`, `UserManager`, `DataLoggerManager`, `OTAManager`), каждый со своей атомарной записью, ротацией и бэкапом — пять реализаций одного механизма.

**П4. Скопированная инфраструктура в каждом модуле** (признак недостающего базового класса): `safeStrCopy`, `logMessage` (2 перегрузки), `publishErrorEvent`, `handleCommand`, `eventHandler`, `streamDiagnosticInfo`, `printStats`, `_initInProgress`, `MUTEX_TIMEOUT_MS = 500` — дублируется во всех 15 модулях.

**П5. Коллизии в пространстве событий:**
- `SH_EVENT_TEMP_WARNING = USER_BASE + 0x0600` **совпадает** с `SH_EVENT_MQTT_CONNECTED = USER_BASE + 0x0600` (и весь диапазон TempSensor 0x0600–0x0603 пересекается с MQTT 0x0600–0x0608).
- `SH_EVENT_MODULE_STATUS = 0x1000` совпадает с `SH_EVENT_USER_BASE = 0x1000` и с `CONFIG_EVENT_CHANGED = 0x1000`.
- Дублирование по смыслу: `SH_EVENT_TIME_SYNC` (системное) против семейства `SH_EVENT_RTC_*`; `SH_EVENT_TEMPERATURE_UPDATE` против `SH_EVENT_TEMP_UPDATE`.

**П6. Сетевое состояние никем не владеет.** Системные события `SH_EVENT_NET_CONNECTED/DISCONNECTED/IP_CHANGED` объявлены, но публикуются не единым владельцем: Ethernet инициализирует `DeviceManager` (события `0x0108+`), link-проверку делает `MqttManager` через `ETH.linkUp()`, ping — `PazManager`. Три модуля по-разному узнают о состоянии сети.

**П7. Конфликт макросов логирования** (обнаружен при входе в сессию): `IoTFramework.h` и `LogManager.h` определяют разные `LOG_DEBUG/LOG_INFO/...` с разными сигнатурами; макросы имеют те же имена, что и константы enum `LogLevel`. Работает на грани правил препроцессора, ломается при смене порядка include.

**П8. Небезопасные точки интеграции:** `PazManager::registerCriticalSensor(float*)` — сырой указатель на данные другого модуля; `notify*` методы требуют ручного связывания в `main.cpp` в обход событийной шины.

## 2. Архитектурные принципы МикроОС 5.0

1. **Одна шина событий.** Убираем `esp_event` из внутреннего контура: одна типизированная шина ядра с подпиской по конкретным `eventId` (а не `ANY_ID`). Одна очередь, один диспетчер, доставка только подписчикам.
2. **Один модуль — одна ответственность.** Каждый модуль отвечает на вопрос «что он *есть*», а не «что он ещё умеет». Смешанные модули v4.2.2 расщепляются по границам ответственности.
3. **Слои вместо плоского списка.** Зависимости направлены только вниз: приложения → доменные сервисы → системные сервисы → транспорт/драйверы → ядро. Обратные связи — только событиями.
4. **Драйвер ≠ сервис.** Драйвер говорит с железом и не знает о системе. Сервис реализует политику и не трогает регистры. Между ними — события/команды.
5. **Инфраструктура — один раз.** Хранилище, логирование, безопасное копирование, диагностика, мьютекс-обёртки выносятся в `ModuleBase` и `StorageService`.
6. **Единый владелец состояния.** У каждого системного факта (сеть, время, температура, здоровье) — ровно один модуль-владелец, публикующий события. Остальные — подписчики.
7. **Ядро не знает о периферии.** Аппаратная платформа фиксирована одна — **WT32-ETH01 + DS3231 + MAX803S** — и под неё собирается универсальное ядро. Вся прочая периферия и бизнес-логика подключаются через механизм расширений: модули **инжектят** в системные сервисы свои параметры конфигурации, API-эндпоинты, MQTT/HA-сущности и проверки здоровья. Новое устройство = новый профиль, а не новая правка ядра.

├──────────────────────────────────────────────────────────────┤

│   AccessControl   VoiceAssistant   HaBridge   Scheduler      │
├──────────────────────────────────────────────────────────────┤
│ СИСТЕМНЫЕ СЕРВИСЫ (services/)                                │
│   ConfigService  StorageService  TimeService  LogService     │
│   AuthService    HealthMonitor   UpdateService  TelemetrySvc │
├──────────────────────────────────────────────────────────────┤
│ ТРАНСПОРТ (net/)                                             │
│   NetworkManager   MqttTransport   HttpServer                │
├──────────────────────────────────────────────────────────────┤
│ ДРАЙВЕРЫ (drivers/) — НЕ IModule, регистрируются в реестре   │

### 3.1. Ядро (core/)

| Модуль | Ответственность | Чем заменяет |
|---|---|---|
| **Kernel** | Жизненный цикл, регистрация модулей, tick-планировщик, статистика, WDT системы, **Safe Mode** (recovery-режим платформы, см. 3.1.1) | `AppCore` (сокращён) |
| **EventBus** | Единая шина: публикация, типизированная подписка по eventId, ISR-отправка, защита от рекурсии | `esp_event` + очередь AppCore + per-module подписки ANY_ID |
| **ModuleBase** | Базовый класс модулей: `log()`, `safeStrCopy`, `publishError`, `getDiagnostics`, флаги состояния, мьютекс | 15 копий одного кода |
| **DriverRegistry** | Реестр драйверов, поиск по имени/типу, делегирование событий | половина `DeviceManager` |
| **BusManager** | Владение шинами I2C/SPI: инициализация, сканирование, блокировка шины, recovery | вторая половина `DeviceManager` + `PazManager::restoreI2cBus` |

#### 3.1.1. Kernel Safe Mode — системный recovery-режим платформы

В монолите smart_lock Safe Mode «прибит» к логике замка (удержание EXIT 3 с →
статический IP 192.168.1.200). По сути это **системный режим любого устройства**
платформы: найти и настроить контроллер при инициализации или после сбоя.
Переносится в ядро и работает одинаково для всех профилей.

**Триггеры входа (любой достаточен):**
1. **Кнопка** — удержание 3 с при старте. Пин кнопки профиль объявляет в
   манифесте (`safe_mode_pin`; у smart_lock = EXIT, GPIO14). Ядро читает пин
   до инициализации модулей — профиль в этом не участвует.
2. **Bootloop-счётчик ≥ 3** (предложение A1) — автоматический вход без человека.
3. **Паника/WDT** при предыдущем старте + повторный сбой на ранней фазе init.
4. **Команда** из serial-консоли или recovery-эндпоинта.

**Поведение ядра в Safe Mode:**
- Сеть принудительно поднимается в известной конфигурации: сначала DHCP;
  если ответа нет за 10 с — fallback на статику `192.168.1.200/24`
  (плашка-информер, как в монолите).
- Стартуют **только**: Kernel, StorageService, ConfigService (read-only),
  LogService, NetworkManager, HttpServer с recovery-UI, UpdateService.
  Профильные модули, драйверы периферии и бизнес-логика **не инициализируются**
  (надёжно, даже если профиль «роняет» устройство).
- Recovery-UI (`/`, минимальный): сетевая настройка, загрузка прошивки,
  сброс конфигурации, просмотр причины входа (reset reason, bootloop count,
  последний panic-лог).
- Публикуется событие `SYS_SAFE_MODE_ENTERED(reason)`; в HA — индикатор
  аварийного режима устройства.
- Выход — рестарт; bootloop-счётчик при этом не сбрасывается, пока устройство
  не проработает 60 с в штатном режиме.

**Причина входа** фиксируется в RTC RAM (переживает soft-reset) и NVS —
recovery-UI и журнал показывают, кто и почему оказался в Safe Mode.

### 3.2. Драйверы (drivers/)

Не являются модулями ОС — реализуют `IDeviceDriver` (уже есть в v4.2.2), не наследуют `IModule`, не подписаны на шину напрямую. Результаты работы отдают через колбэки сервису-владельцу.

| Драйвер | Железо | Сервис-владелец |
|---|---|---|
| `WiegandDriver` | Считыватель D0/D1, ISR, паритет, дебаунс | AccessControl |
| `DfPlayerDriver` | UART-протокол DFPlayer, здоровье чипа | VoiceAssistant |
| `Ds3231Driver` | Чтение/запись RTC по I2C | TimeService |
| `EspTempDriver` | temperature_sensor ESP-IDF | HealthMonitor (единственный владелец температуры кристалла) |

### 3.3. Транспорт (net/)

| Модуль | Ответственность |
|---|---|
| **NetworkManager** | Единственный владелец состояния сети: Ethernet PHY (из `DeviceManager`), link up/down, IP, публикует `NET_CONNECTED/DISCONNECTED/IP_CHANGED`. Выдаёт клиентские сокеты. Поглощает `applyNetworkSettings` из ConfigManager (подписывается на `CONFIG_CHANGED`) и ping-диагностику из PazManager |
| **MqttTransport** | Только pub/sub: подключение, переподключение, LWT, QoS. Без HA Discovery и без троттлинга. **5.1.0:** собственный outbox (RAM-кольцо 8 сообщений) — зеркальные события и publishRaw при разрыве копятся и уходят replay'ем при reconnect; retained-дедупликация, потери посчитаны |
| **HttpServer** | Только HTTP: маршрутизация, статика, загрузка файлов. Аутентификацию делегирует AuthService командой |

### 3.4. Системные сервисы (services/)

| Модуль | Ответственность | Источник в v4.2.2 |
|---|---|---|
| **StorageService** | Единая работа с LittleFS/NVS: атомарная запись, ротация, бэкапы, контроль свободного места | устраняет 5 дублирующих реализаций |
| **ConfigService** | Хранение/валидация/миграция конфигурации; публикует `CONFIG_CHANGED(key)`. Без сетевой логики | `ConfigManager` минус `applyNetworkSettings` |
| **TimeService** | Системное время: RTC (через Ds3231Driver) + NTP + таймзона. Единый источник `TIME_SYNC` | `RTCManager` минус планировщик/будильник |
| **Scheduler** | Временные интервалы: ночной режим, рабочие часы, будильники, cron-подобные задачи. Подписчик TimeService. **Реализован в 5.1.0** как ScheduleService (события 0x0180–0x018F, правила из конфига + IScheduleProvider) | планировщик из `RTCManager` |
| **LogService** | Журнал событий системы (RAM-кольцо + файл через StorageService) | `LogManager` |
| **TelemetryService** | Временные ряды для графиков: дельта-сжатие, агрегация, JSON для uPlot | `DataLoggerManager` |
| **AuthService** | Единая аутентификация и сессии: пароль, карта, PIN, токены, блокировка после N попыток. Одна система сессий на всю ОС | сессии из `UserManager` + `WebServerManager` |
| **CredentialStore** | База карт/пользователей СКУД (CRUD, типы ключей, сроки) — данные, а не механизмы | `UserManager` (FULL-режим) |
| **HealthMonitor** | ПАЗ-ядро: WDT, heap, температура (подписка на EspTempDriver), здоровье шин и сети (подписки), паника, авто-восстановление. Расширяемый через регистрацию `IHealthCheck` | `PazManager` без доменной логики |
| **UpdateService** | OTA: проверка, загрузка, rollback, история (через StorageService) | `OTAManager` |
| **CounterService** (5.1.0) | Персистентные счётчики: RAM-тень + батч-сброс в NVS (каждые N инкрементов ИЛИ T секунд + по SH_EVENT_SHUTDOWN); PCNT-бэкенд для импульсных счётчиков. Устраняет идиому «cfgGetUInt + setInternal на каждый цикл» (износ flash) | `cycle_count` из монолита, обобщённо |
| **SpeechBuilder** (5.1.0) | Составная речь из папок 05/06 SD-карты: числа (-4999..4999, оба рода), время, единицы с триадами час/минута. Фасад над AudioService::sayRaw; раскладка — константы из manifest.json голосового конвейера | `AudioExtensions` (идея, правильная реализация) |

### 3.5. Доменные сервисы (domain/)

| Модуль | Ответственность | Источник |
|---|---|---|
| **AccessControl** | Логика СКУД: карта → проверка в CredentialStore → реле/дверь; регистрирует в HealthMonitor доменные проверки (залипание реле, дверь открыта слишком долго) через `IHealthCheck` | `notify*` из PazManager + логика из приложений |
| **VoiceAssistant** | Очередь воспроизведения, приоритеты, ночная громкость (подписка на Scheduler), озвучивание чисел/времени/имён | `AudioManager` (политика) + `AudioExtensions` |
| **HaBridge** | Home Assistant: Discovery, маппинг сущностей, троттлинг телеметрии. Клиент MqttTransport | часть `MqttManager` |

### 3.6. Приложения (apps/)

Бизнес-логика конкретного устройства (умный замок, свет, климат, счётчики, погодный шлюз) — как и было задумано в v4.2.2, но теперь опираются на узкие доменные сервисы вместо прямых вызовов менеджеров.

## 5. Единое пространство событий (устранение коллизий)

```
0x0000–0x00FF  Ядро (BOOT, READY, SHUTDOWN, MODULE_*, HEALTH_*)
0x0100–0x01FF  Системные сервисы: CONFIG (0x0100), LOG (0x0110),
               STORAGE (0x0120), TIME (0x0130), AUTH (0x0140),
               HEALTH/ПАЗ (0x0150), UPDATE/OTA (0x0160)
0x0200–0x02FF  Транспорт: NET (0x0200), MQTT (0x0210), HTTP (0x0220)
0x0300–0x03FF  Драйверы: TEMP (0x0300), WIEGAND (0x0310),
               AUDIO (0x0320), BUS (0x0330)
0x0400–0x04FF  Домен: ACCESS (0x0400), VOICE (0x0410),
               HA (0x0420), SCHED (0x0430), TELEMETRY (0x0440)
0x1000–0x1FFF  Приложения (как раньше)
0x09xx         Зарезервировано: CMD_EXECUTE/CMD_RESPONSE (совместимость)
```

Правила: базовый offset выдаётся реестром, диапазоны не пересекаются по построению; `SH_EVENT_MODULE_STATUS` выносится из `0x1000` в диапазон ядра; дубли `TIME_SYNC`/`RTC_SYNCED` и `TEMPERATURE_UPDATE`/`TEMP_UPDATE` сводятся к одному событию владельца.

## 7. Порядок внедрения (фазы)

1. **Фаза 0 — фундамент без ломки API:** ModuleBase + разрешение конфликта макросов LOG_* + единый реестр eventId (устранение коллизий 0x0600 и 0x1000). Все модули компилируются как раньше.
2. **Фаза 1 — шина:** EventBus с подпиской по ID; перевод модулей с ANY_ID на конкретные ID; удаление esp_event-контура и двойной доставки.
3. **Фаза 2 — StorageService + NetworkManager:** пять FS-клиентов переводятся на StorageService; Ethernet и ping собираются в NetworkManager; ConfigManager худеет.
4. **Фаза 3 — расщепление гигантов:** DeviceManager → 3, RTCManager → 3, MqttManager → 2, AudioManager+Extensions → VoiceAssistant, UserManager+WebServer-сессии → AuthService + CredentialStore.
5. **Фаза 4 — ПАЗ:** HealthMonitor + IHealthCheck; доменные notify* уходят в AccessControl; TempSensor понижается до драйвера.
6. **Фаза 5 — полировка:** Scheduler (**сделан в 5.1.0** — ScheduleService), HaBridge, миграция приложений, документация, deprecation-старых API.

Каждая фаза — отдельно тестируемое состояние: система остаётся работоспособной между фазами.

6. **Фаза 6 — профили устройств:** механизм расширений (см. раздел 8), вынос пинов/периферии из кода в профили, перенос бизнес-логики в `profiles/*`.

Правило: **добавление нового устройства = новая папка `profiles/<device>/`**. Файлы `core/`, `services/`, `net/` при этом не редактируются вообще.

### 8.1.1. Аппаратная база: супервизор питания MAX803S

Третий обязательный компонент «железа по умолчанию» (наряду с WT32-ETH01 и DS3231) — супервизор сброса **MAX803S** на линии EN. Для программной платформы он полностью прозрачен: ни пинов, ни драйвера, ни записи в BaseProfile — это чисто аппаратный страж.

**Диагноз, который он закрывает.** При медленном подъёме питания (реальные БП, длинные линии, питание по PoE-подобным схемам) ESP32 может защёлкнуть невалидные strapping-уровни (в первую очередь GPIO0) и повиснуть: в логе `boot:0x3 (DOWNLOAD_BOOT)` вместо штатного `boot:0x13` — до ручного нажатия RESET устройство не стартует. Штатная RC-цепочка EN платы WT32-ETH01 (10 кОм + 0.1 мкФ, τ≈1 мс) слишком быстрая для таких фронтов — Espressif рекомендует 1–10 мкФ, но «лечить ёмкостью» — открытая петля: задержка зависит от крутизны фронта и тормозит ручной сброс.

**Решение — замкнутая петля по напряжению.** MAX803S следит за 3V3: держит RESET активным, пока VCC ниже порога **2.93 В** (Suffix S; T = 3.08 В — тоже допустимо), затем выдерживает фиксированный таймаут **140–560 мс** (240 мс тип.) и отпускает EN. Задержка автоматически подстраивается под скорость подъёма питания — быстрый БП получает минимум, медленный — сколько нужно.

**Выход open-drain (активный низкий)** — принципиальный выбор: MAX809/810 с push-pull не подходят. Открытый сток даёт wire-AND со штатной кнопкой сброса — кнопка продолжает работать параллельно (оба просто тянут EN к земле).

**Разводка (SC70-3 / SOT-23):**
| Вывод | Подключение |
|---|---|
| 1 GND | общая земля |
| 2 RESET | → EN контроллера (штатные 10 кОм на плате работают как pull-up) |
| 3 VCC | → 3V3 **после LDO** (НЕ на 5V!) |

Плюс керамика 0.1 мкФ по VCC у корпуса. Потребление — 12 мкА.

**Бонус — защита при снятии питания.** Выход супервизора валиден вплоть до VCC = 1 В: при пропадании питания контроллер получает RESET раньше, чем flash начнёт «умирающие» записи на догорающем напряжении — класс повреждений LittleFS/NVS при выдёргивании питания закрывается на уровне железа.

**Закупка.** Оригинал — только SC70-3 (у S-версии топ-маркировка «ABC»); в SOT-23 встречаются клоны NCP803/CAT803 — функционально идентичны.

### 8.2. Точки расширения (extension points)

Каждый системный сервис владеет *механизмом*, а модули и профили поставляют *содержимое*:

| Точка расширения | Кто владеет | Что инжектится | Интерфейс |
|---|---|---|---|
| Параметры конфигурации | ConfigService | Поля, умолчания, валидация, UI-группы | `IConfigProvider` |
| HTTP API-эндпоинты | HttpServer | REST-маршруты + описание для API-доков | `IApiProvider` |
| MQTT/HA-сущности | HaBridge | Discovery-описания, топики состояний | `IHaProvider` |
| Каналы телеметрии | TelemetryService | Регистрация sensorId, тип данных | `ITelemetryProvider` |
| Проверки здоровья | HealthMonitor | Доменные проверки (реле, дверь, датчик) | `IHealthCheck` |
| Задачи планировщика | Scheduler | Временные правила (ночной режим и т.п.) | `IScheduleProvider` |
| Драйверы периферии | DriverRegistry | Драйвер + привязка к пинам из манифеста | `IDeviceDriver` |
| Веб-виджеты | UiRegistry (UI-shell ядра) | Карточки, кнопки, статусы, секции UI + роль видимости | `IUiProvider` |

> WebUI 5.0 подробно: `МикроОС_5.0_веб-интерфейс.md` — UI-shell ядра,
> авто-рендер настроек из схемы, ролевая модель GUEST/USER/ADMIN.

### 8.3. Инжекция конфигурации

Модуль объявляет свои поля декларативно — ConfigService хранит, валидирует, показывает в веб-UI и публикует изменения. Ядро о полях не знает:

```cpp
enum class ConfigType : uint8_t { INT, UINT, FLOAT, BOOL, STRING, IP, SECRET };

enum ConfigFlags : uint8_t {
    CFG_NONE     = 0,
    CFG_CRITICAL = 1 << 0,  // изменение требует перезагрузки/переприменения
    CFG_READONLY = 1 << 1,
    CFG_SECRET   = 1 << 2   // не отдаётся в API в открытом виде
};

struct ConfigField {
    const char* key;        // "lock.relay_pulse_ms" — неймспейс = имя модуля
    ConfigType   type;
    const char*  defValue;  // умолчание (строкой, парсится по типу)
    int32_t      min, max;  // для числовых типов
    uint8_t      flags;
    const char*  group;     // "Замок" — группа в веб-интерфейсе
    const char*  label;     // "Длительность импульса реле, мс"
};

class IConfigProvider {
public:
    virtual void registerConfig(ConfigService& cfg) = 0;
};
```

- Ключи **неймспейсированы**: `<модуль>.<параметр>` — коллизии исключены по построению; системные ключи (`net.*`, `mqtt.*`, `hostname`) принадлежат ядру.
- Хранение: единое пространство ConfigService (JSON-секции), значения профиля живут рядом с системными — бэкап/миграция/экспорт получают их бесплатно.
- Изменение поля → событие `CONFIG_CHANGED(key)` → модуль-владелец применяет (или помечает «требуется перезагрузка», если `CFG_CRITICAL`).
- Веб-интерфейс настроек **строится автоматически** из зарегистрированных схем: новая периферия появляется в UI без правки фронтенда.

### 8.5. Профиль устройства (DeviceProfile)

Профиль — композиционный корень устройства, единственное место, где знают про конкретную периферию:

```cpp
class IDeviceProfile {
public:
    virtual const char* profileId() const = 0;          // "smart_lock"
    virtual void describeHardware(HardwareManifest& m) = 0; // пины, шины
    virtual void registerDrivers(DriverRegistry& dr,
                                 const HardwareManifest& m) = 0;
    virtual void registerModules(Kernel& k) = 0;        // доменные сервисы + приложение
};

// profiles/smart_lock/SmartLockProfile.cpp
void SmartLockProfile::describeHardware(HardwareManifest& m) {
    // База WT32-ETH01 + DS3231 уже описана ядром — добавляем только периферию:
    m.wiegand   = {.d0 = 4, .d1 = 5};
    m.dfPlayer  = {.uart = 2, .rx = 14, .tx = 15, .busy = 13};
    m.relayPin  = 2;
    m.doorPin   = 12;
}
void SmartLockProfile::registerDrivers(DriverRegistry& dr, const HardwareManifest& m) {
    dr.add<WiegandDriver>(m.wiegand);
    dr.add<DfPlayerDriver>(m.dfPlayer);
}
void SmartLockProfile::registerModules(Kernel& k) {
    k.registerModule(&AccessControl::getInstance(), 2, 50);
    k.registerModule(&VoiceAssistant::getInstance(), 6, 100);
    k.registerModule(&SmartLockApp::getInstance(), 8, 200);
}
```

Точка входа всего устройства сводится к одной строке — `main.cpp` генерируется шаблонно:

```cpp
void setup() { Kernel::run<SmartLockProfile>(); }
```

Для SmartLight — `Kernel::run<SmartLightProfile>()`; ядро, сервисы, транспорт — те же самые бинарно и по коду.

### 8.6. Расширенный жизненный цикл модуля

Чтобы инжекция происходила до старта сервисов, в жизненный цикл добавляется фаза регистрации:

```
describe()            → модуль объявляет зависимости и возможности
registerExtensions()  → инжекция: конфиг-схема, API, HA-сущности,
                        health-checks, телеметрия
init()                → инициализация ресурсов (значения конфига уже доступны)
start()               → рабочий режим, подписки на события
tick() / stop()       → как раньше
```

Гарантия порядка: все `registerExtensions()` всех модулей завершаются до первого `init()` — к моменту старта веб-сервер видит полную карту API, веб-UI — полную схему настроек, HealthMonitor — полный список проверок.

## 9. Что даёт реорганизация

- **Предсказуемость:** одна очередь событий, доставка только подписчикам — уходит двойная обработка и лишние ~300 байт RAM на событие в полёте.
- **Отладка:** один владелец сети/времени/температуры — один источник истины в логах.
- **Размер:** вынос 15 копий инфраструктурного кода в ModuleBase и 5 FS-реализаций в StorageService сокращает и Flash, и поверхность для багов.
- **Расширяемость:** новое железо = новый драйвер в реестре; новая политика = новый доменный сервис; ядро не трогаем.
- **СКУД и умный дом перестают быть распределёнными** по PazManager, AudioExtensions и MqttManager — у каждого домена появляется свой модуль.
- **Платформенность:** одно универсальное ядро под WT32-ETH01 + DS3231 + MAX803S; новое устройство = новый профиль в `profiles/` с инжекцией конфига, API, HA-сущностей и проверок — без единой правки `core/`, `services/`, `net/`.

# МикроОС 5.0 — Веб-интерфейс: универсальная и профильная части

**Основание:** анализ веб-страницы smart_lock v2.5.0 (3 части, ~890 строк HTML/JS)
**Принцип:** один UI-shell ядра + виджеты профиля; ролевая модель доступа

---

## 1. Что показал анализ монолитной страницы

В странице v2.5.0 уже есть естественное разделение — просто оно не формализовано:

| Универсальное (одинаково у любого устройства) | Профильное (только СКУД) |
|---|---|
| Секция «Связь»: DHCP/Static IP, hostname, MQTT | Гигантская кнопка «ОТКРЫТЬ», чип двери |
| Секция «Админ»: смена пароля | Секции «Замок», «Кнопка выхода», «Пользователи» |
| OTA (проверка с сервера + ручная загрузка .bin) | Режимы NORMAL/ACCEPT/TRIGGER |
| Синхронизация времени | База ключей, мастер-ключ, NVS-бэкап |
| Тёмная тема, PWA, sessionStorage | Погода, приветствие по времени суток |
| Журнал событий (пагинация, очистка) | voice_map.json, тест треков |
| Системная информация (версия, аптайм) | Счётчик циклов замка |
| Каркас ПАЗ (чип-индикатор, сброс флага) | Строки ПАЗ: реле, сеть, чтение карты |
| Авторизация Bearer + роли, 2-мин автологаут, защита полей от перезаписи опросом (userModifiedFields), скрытый инженерный вход (5 тапов) | — |

Вывод: **~55% страницы — универсальная инфраструктура**, которую сейчас пришлось бы копировать в каждое устройство. Выносим её в ядро; профиль декларирует только своё.

## 2. Архитектура WebUI 5.0

```
┌──────────────────────────────────────────────────────────────┐
│ UI-SHELL ЯДРА (core/web/, неизменен для всех устройств)      │
│  · каркас страницы, тема, PWA, навигация-чипсы               │
│  · модальное окно авторизации + движок ролей                 │
│  · диспетчер опроса (единый таймер, per-widget интервалы)    │
│  · рендерер настроек из ConfigService-схем (авто-UI)         │
│  · универсальные секции: Связь / Время / ПО / Система /      │
│    ПАЗ / Журнал                                              │
├──────────────────────────────────────────────────────────────┤
│ ПРОФИЛЬНЫЕ ВИДЖЕТЫ (profiles/<device>/web/)                  │
│  · манифест виджетов (IUiProvider): карточки, кнопки,        │
│    статусы, секции настроек                                  │
│  · статические ассеты профиля (иконки, voice_map.json)       │
└──────────────────────────────────────────────────────────────┘
```

### 2.1. Ключевое решение: настройки рисуются из схемы

Поля, зарегистрированные профилем через `IConfigProvider` (раздел 8.3 базовой архитектуры), **автоматически** появляются в секциях настроек по `group`/`label`. Профилю не нужен HTML для форм — только для «живых» виджетов (большая кнопка, чип двери). Формы СКУД («Замок», «Кнопка выхода») в 5.0 генерируются сами.

Универсальные секции ядра (есть у каждого устройства, admin-only):
- **Связь** — net.*, mqtt.* (генерируется из ядерной схемы);
- **Время** — синхронизация, таймзона;
- **ПО** — OTA check/update, версия;
- **Система** — аптайм, heap, reset reason, перезагрузка;
- **ПАЗ** — статусы всех зарегистрированных IHealthCheck (ядро+профиль единым списком), сброс флагов;
- **Журнал** — LogService (пагинация, очистка admin).

### 2.2. Виджет-манифест профиля (IUiProvider)

```cpp
struct UiWidget {
    const char* id;          // "lock.giant_button"
    UiWidgetType type;       // STATUS_CARD | BIG_BUTTON | CHIP | LIST | SECTION
    const char* title;       // "Исполнитель"
    const char* apiEndpoint; // "/api/lock/status" — источник данных
    uint16_t pollMs;         // период опроса (0 — по событию общего статуса)
    UiAccess   access;       // минимальная роль видимости (см. §3)
    const char* assetFile;   // "lock_widgets.html" — фрагмент верстки (если нужен)
};

class IUiProvider {
public:
    virtual void registerUi(UiRegistry& ui) = 0;
};
```

Виджеты бывают двух сортов:
1. **Декларативные** — status-card, chip, toggle: рисуются ядром по манифесту, без HTML профиля;
2. **Кастомные** — фрагмент HTML+JS из `profiles/<device>/web/` (большая кнопка, база ключей, weather-карточка). Подключаются в shell как изолированные блоки.

## 3. Ролевая модель доступа (уточнение вашего предложения)

| Роль | Кто | Что видит |
|---|---|---|
| **GUEST** (без авторизации) | любой в локальной сети | Профильную часть устройств **кроме охранных**; у СКУД — только окно PIN |
| **USER** (PIN жильца) | жилец | Профильная часть СКУД: кнопка «Открыть», дверь, погода, журнал (без админских действий) |
| **ADMIN** (пароль/мастер-PIN) | администратор | Всё: универсальные секции + админские секции профиля |

Правила:
- **Универсальная часть (настройки, сеть, OTA, ПАЗ, пользователи) — всегда ADMIN**, на любом устройстве экосистемы. Это и есть «видимая только администратору» часть.
- **Профиль сам объявляет** минимальную роль каждого виджета: у smart_light главная панель — `GUEST` (без пароля, как вы предложили), у smart_lock — `USER` (PIN), её админские виджеты (база ключей, мастер-ключ) — `ADMIN`.
- Серверная сторона дублирует права: роль виджета = роль его API-эндпоинта (`UiAccess::USER` ↔ `Role::USER` в `http.addRoute`). Скрытие в UI — не защита; защита — в эндпоинтах (уже заложено в SmartLockApi.cpp).

Из монолита переносим в shell ядра: Bearer-сессии, автологаут по бездействию 2 мин (admin), защиту полей от перезаписи опросом (`userModifiedFields`), fetchWithRetry без ретраев на 401, fullscreen-режим, скрытый инженерный вход (5 тапов) — как опцию `admin.engineer_tap`.

## 4. Раскладка страницы smart_lock v2.5.0 → WebUI 5.0

| Блок v2.5.0 | Куда в 5.0 | Роль |
|---|---|---|
| Гигантская кнопка, чип двери, приветствие, погода | Профильные виджеты (кастомные) | USER |
| Карточки «Исполнитель», «Датчик двери», режим | Профильные status-виджеты | USER |
| Журнал событий (+очистка) | Универсальная секция Журнал | USER читает / ADMIN чистит |
| Секция «Связь» (DHCP, MQTT) | Универсальная секция Связь (авто-UI) | ADMIN |
| Секция «Замок» (время, тип, громкость, тихий, дверь) | Авто-UI из схемы `lock.*` (группы «Замок», «Дверь», «Звук») | ADMIN |
| Секция «Кнопка выхода» | Авто-UI из схемы `lock.exit_*` | ADMIN |
| Секция «Админ» (пароль, мастер-ключ readonly) | Пароль → универсальная «Система»; мастер-ключ → профильный виджет | ADMIN |
| Секция «Пользователи» (CRUD, NVS-бэкап, voice_map) | Профильная кастомная секция | ADMIN |
| Секция «ПАЗ» | Универсальная ПАЗ + доменные строки из IHealthCheck | ADMIN |
| OTA (check + upload), sync_time, тема, системная инфа | Универсальные секции ПО/Время/Система | ADMIN |
| Safe Mode плашка, чип ПАЗ в навигации | Shell ядра (глобальные индикаторы) | все |

## 5. Что это даёт

- **Новое устройство получает полноценный UI бесплатно**: shell + настройки из схемы + ПАЗ + журнал + OTA — без единой строчки HTML.
- **Профиль пишет только уникальное**: пара виджетов и, при необходимости, один кастомный фрагмент.
- **Единый UX экосистемы**: тема, авторизация, навигация, поведение форм идентичны на всех контроллерах.
- **Безопасность симметрична**: роли виджетов и эндпоинтов задаются одной таблицей — рассинхрон «скрыто в UI, но открыто в API» невозможен.

# МикроОС 5.0 — доведение до «максимальных кондиций»
## Предложения по построению и оптимизации (за рамками базовой архитектуры)

Базовая идеология утверждена: единая платформа WT32-ETH01 + DS3231 → неизменное
ядро; периферия → профили. Ниже — 15 предложений системного уровня, сгруппированных
по пяти направлениям. Приоритеты: **P0** — делать в первую очередь (дешёвые,
закрывают реальные риски), **P1** — вторая волна, **P2** — стратегические.

---

## A. Живучесть устройства «в поле»

### A1. Защита от bootloop + A/B OTA — **P0**
Монолит v2.5.0 имеет Safe Mode по кнопке, но нет защиты от циклической
перезагрузки после неудачной прошивки.
- **Bootloop-счётчик** в RTC RAM: kernel инкрементирует на старте, сбрасывает
  после 60 секунд стабильной работы. 3 подряд → автоматический Safe Mode
  (сеть по DHCP, минимум модулей) — без участия человека с кнопкой.
- **A/B разделы OTA** (штатная возможность ESP32): новая прошивка грузится в
  неактивный раздел, первый старт помечается `pending`; если до отметки
  «работаю» дело не дошло — загрузчик сам откатывается на предыдущий раздел.
  Это бесплатно в ESP-IDF, нужно только задействовать.
- **Маркер совместимости FW/FS**: прошивка и образ LittleFS несут `min_fs_version`
  / `min_fw_version` — UpdateService отказывает в несовместимой паре до записи.

### A2. Реестр ресурсов (ResourceManager) — **P0**
Сегодня ничто не мешает двум профилям занять один GPIO или I2C-адрес.
- Ядро ведёт таблицу занятых ресурсов: GPIO, UART, I2C-адреса, NVS-namespace,
  диапазоны событий. BaseProfile регистрирует свои (PHY 16, I2C 32/33, 0x68).
- `describeHardware()` профиля **валидируется при старте**: конфликт пина →
  модуль не стартует, в лог — явная ошибка «GPIO15 занят: lock.relay vs …».
- Бонус: автоматически генерируемый документ «карта занятых пинов» по всем
  профилям — из того же реестра.

### A3. Деградация по уровням (Degraded Mode) — **P1**
Формализовать то, что в smart_lock сделано стихийно (джампер GPIO35):
- Три уровня: FULL (сеть+MQTT) → LOCAL_NET (только веб/API) → AUTONOMOUS
  (только драйверы и бизнес-логика). Каждый модуль объявляет в `describe()`,
  на каком минимальном уровне он работает.
- Падение сети переводит систему на уровень ниже **событиями**, без ребута;
  восстановление — наоборот. Джампер принудительно фиксирует AUTONOMOUS.

## B. Наблюдаемость и диагностика

### B1. Системные метрики как телеметрия — **P0**
HealthMonitor уже собирает heap/температуру — превратить в данные:
- TelemetryService регистрирует системные каналы: `sys.free_heap`,
  `sys.min_heap`, `sys.cpu_temp`, `sys.event_queue_depth`, `sys.tick_overruns`,
  `sys.event_dropped`.
- В HA — автоматические графики здоровья каждого контроллера. Утечка памяти
  или шторм событий видны **до** аварии, а не по ребуту.

### B2. Бюджеты времени исполнения — **P1**
- Kernel замеряет длительность `tick()` и `onEvent()` каждого модуля;
  превышение бюджета (например, 50 мс) → warning в лог с именем модуля.
- Медленный модуль перестаёт быть «невидимой» причиной WDT-ребутов.

### B3. Аудит-лог административных действий — **P1**
- Отдельный защищённый журнал: кто (роль), что (смена конфига, OTA, удаление
  ключа, сброс ПАЗ), когда. Не очищается кнопкой «Очистить журнал».
- Для СКУД это требование, а не опция.

## C. Безопасность

### C1. Provisioning вместо дефолтного пароля — **P0**
В монолите зашит дефолтный хэш админа — это backdoor на всех устройствах.
- Первый старт (или сброс): устройство требует задать пароль через веб до
  начала работы; до provisioning доступна только страница установки.
- Пароль существует только как хэш + соль; хэш никогда не покидает устройство
  (уже так — сохранить принцип).

### C2. Подпись прошивок и шифрование секретов — **P2**
- **Secure Boot v2 + Flash Encryption** (ESP32): прошивка не подписанная
  ключом вендора не стартует; NVS с PIN-хэшами и MQTT-паролем не читается
  при физическом доступе к flash.
- Тяжёлая мера, внедрять на этапе серийного производства.

### C3. Rate-limiting и защита эндпоинтов — **P1**
- В монолите есть CSRF и сессии; добавить: счётчик неудачных попыток
  авторизации с экспоненциальной паузой (уже есть в UserManager 5.0-концепте),
  лимит запросов/с на IP, блокировка `/api/auth` после N провалов.
- Rate-limit на `postEvent` — защита шины от шторма из сети.

## D. Качество производства (DevEx / QA)

### D1. Conformance-тест профиля — **P0**
Профиль — публичный контракт; нужен автоматический экзамен:
- Скрипт проверяет новый профиль: все обязательные провайдеры зарегистрированы,
  диапазон событий не пересекается с реестром, нет прямых вызовов железа
  в обход драйверов (grep-запреты: `digitalWrite`, `Wire.` в `profiles/*` вне
  манифеста), каждый `addRoute` имеет роль, каждый виджет — существующий
  эндпоинт.
- Запускается в CI: профиль, не прошедший conformance, не собирается.

### D2. Host-тесты бизнес-логики — **P1**
- Бизнес-логика профилей (машина доступа, расписания) не зависит от Arduino —
  выносится в чистый C++ и гоняется под PlatformIO `native` на ПК:
  подаём событие `CARD_READ` → проверяем вердикт.
- Драйверы заменяются mock-реализациями по тем же интерфейсам.

### D3. Автогенерация документации из кода — **P1**
- `/api/docs` уже агрегирует `addRoute(..., .desc=...)` — довести до
  OpenAPI-файла при сборке.
- Из `ConfigField[]` — таблица настроек профиля в Markdown.
- Из реестра событий — карта событий. Документация не устаревает никогда,
  потому что генерируется из единственного источника истины.

### D4. Бюджеты ресурсов в CI — **P2**
- При сборке: контроль flash/RAM по бюджету (например, ядро ≤ 60% flash,
  профиль ≤ 15%); превышение — сборка падает. «Расползание» прошивки
  останавливается на коммите, а не в поле.

## E. Экосистема (несколько контроллеров)

### E1. Идентичность устройства — **P0**
- Device ID = `profileId + efuse MAC` (как clientId в монолите) — публикуется
  в MQTT discovery, в ответ `/api/system`, метка на корпус.
- Это основа fleet-операций: обновить «все smart_lock до 5.1», найти
  устройство в сети (mDNS `_microos._tcp`).

### E2. Межустройственные события — **P2**
- Стандартный «мост» событий через MQTT: событие шины с флагом `GLOBAL`
  публикуется в `ecosystem/<event>`; контроллеры-подписчики получают его как
  локальное. Пример: smart_lock `DOOR_ALARM` → smart_light мигает в коридоре.
- Ядро маршрутизирует, профили не знают друг о друге.

### E3. Экспорт/импорт конфигурации устройства — **P1**
- Один файл: системные + профильные поля + список драйверов (без секретов —
  отдельный защищённый раздел). Сценарии: клонирование контроллера,
  замена сгоревшего устройства за 5 минут, бэкап перед OTA.

## Рекомендуемый порядок (после утверждения)

1. **Фаза 0:** A2 (реестр ресурсов), A0 (Kernel Safe Mode — каркас).
2. **Фаза 1:** A1 (bootloop + A/B OTA), B2 (бюджеты времени).
3. **Фаза 2:** C1 (provisioning), E1 (идентичность), C3 (rate-limiting),
   A3 (уровни деградации).
4. **Фаза 3:** B1 (метрики), B3 (аудит-лог), E2 (MQTT-мост событий).
5. **Финальная полировка:** D1–D4, C2 (коммерческая версия), E3.

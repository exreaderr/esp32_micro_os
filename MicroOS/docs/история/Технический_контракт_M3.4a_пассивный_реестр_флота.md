# МикроОС — M3.4a: пассивный реестр флота на home_master

**Дата:** 21.11.2026  
**Статус:** концепция и технический контракт приняты владельцем 21.11.2026; кандидат ещё не собран и не принят  
**База:** принятый `home_master`, ядро **5.9.9**, профиль **0.9.10**, M3.4-Info-IP1  
**Граница работ:** только профиль `home_master`; ядро 5.9.9 не изменяется  

## 1. Основание и утверждённые границы

M3.4a санкционирован владельцем как этап пассивного сбора, систематизации, отображения и публикации данных на мастере. Реестр должен дать единую картину: что это за устройство, где оно сейчас, в каком состоянии находится и какие уже существующие операции для него допустимы.

Разрешено:

- пассивно наблюдать реальные MQTT-публикации устройств на встроенном брокере мастера;
- формировать запись по каноническому `deviceId`;
- показывать descriptor, availability, телеметрию, деградацию и возраст данных;
- назначать человекочитаемые алиасы на стороне мастера;
- предоставлять актуальный IP уже существующему BackupAggregator;
- read-only связывать записи с состоянием существующего OTA-зеркала;
- открывать веб устройства по актуальному IP;
- выполнять проверки новых функций вручную.

Запрещено в M3.4a:

- команды устройствам, групповые операции и групповое OTA;
- автоматические snapshot, restore, OTA, удаление, назначение или иные действия по появлению/изменению записи;
- новые автоматические триггеры для backup/OTA;
- периодический descriptor, descriptor outbox, shadow-replay/rehydrate;
- ожидание устройством регистрации, ответа или разрешения мастера;
- mDNS, активное сканирование сети и опрос устройств ради построения реестра;
- расширение descriptor без отдельного потребителя и обоснования;
- использование alias, hostname или IP как канонической идентичности;
- самостоятельное добавление UI-полировки и активных флот-операций.

«Публикация на мастере» в этом этапе означает выдачу через HTTP API и вкладку «Флот». Новый агрегированный MQTT-топик реестра не вводится.

### 2.1. Достаточность профильных интерфейсов

`projects/home_master/src/BrokerService.h` уже предоставляет:

- `BrokerEventInfo` с типом `Publish` / `RemoveClient`;
- topic, payload, retain, truncated и clientId;
- `addEventHook()` / `removeEventHook()`;
- `hasClient()` для проверки живой сессии;
- `publishLocal()` — в M3.4a для реестра не нужен.

События descriptor/state/telemetry проходят существующий локальный broker hook. Отдельный MQTT-клиент, подписка на верхнем брокере и изменение ядерного `MqttTransport` не требуются.

Хук синхронный и исполняется в контексте broker tick/loopTask. В нём разрешены только быстрые проверки, разбор и копирование в RAM. SD, LittleFS, HTTP и другие сетевые операции в хуке запрещены.

### 2.2. Ёмкость broker hooks

В базе `BROKER_HOOK_MAX = 4`. Активный composition root регистрирует четыре потребителя:

1. BridgeService;
2. JournalService;
3. BackupService;
4. HmArchiveModule.

Таким образом, таблица уже заполнена. WeatherMirror содержит собственный hook, но в текущем `HomeMasterProfile::registerModules()` не зарегистрирован; это существующее состояние базы, не дефект M3.4a и не повод для его изменения.

Для реестра требуется пятый активный слот. Решение: увеличить **профильную** таблицу `BrokerService` до 8 и проверять результат `addEventHook()`. Это не ядерное изменение: `BrokerService` находится в `projects/home_master/src/`. Восемь слотов дают запас без изменения vendored sMQTT и ядра.

### 2.4. Форматы входных данных

Descriptor:

`<mqtt.prefix>/<deviceId>/descriptor`

```json
{"v":1,"id":"3e0f02ded999","profile":"home_master","kernel":"5.9.9","profile_ver":"0.9.10","host":"home_master","ip":"10.146.75.50"}
```

Telemetry:

`<mqtt.prefix>/<deviceId>/telemetry`

```text
uptime, heap, heap_min, bus_dropped, bus_hwm, cpu_t,
degradation, gw_rtt, bootloop, audit_lost
```

Availability:

`<mqtt.prefix>/<deviceId>/state` → `online` / `offline`.

Telemetry публикуется периодически и после MQTT CONNECT. Период настраивается на устройстве через `tel.period_s` в диапазоне 5–300 с. Реестр не должен предполагать фиксированные 15 с.

`BROKER_EVENT_PAYLOAD_LEN = 768` достаточно для существующих descriptor и telemetry. Событие с `truncated=true` не разбирается как JSON и учитывается отдельным счётчиком.

### 2.5. Self-запись мастера

Собственный descriptor мастера публикуется его MQTT-клиентом на верхний брокер и не проходит через локальный BrokerService hook. Поэтому self-запись обязана формироваться из локального фактического состояния:

- `NetworkService::deviceId()`;
- `Kernel::profileId()`;
- `MICROOS_VERSION`;
- `UpdateService::profileVersion()`;
- hostname и IP NetworkService;
- локальная telemetry из TelemetryService;
- фактический статус верхнего MQTT — отдельным диагностическим признаком, а не условием существования self-записи.

Self обновляется при старте реестра, `NET_EVENT_IP_CHANGED`, `SH_EVENT_MQTT_CONNECTED` и в медленном tick. Отсутствие верхнего брокера не делает мастер «offline» в его собственном реестре.

### 2.6. BackupAggregator

Текущий контракт:

- ручной `bk.hosts` содержит CSV IP;
- снимки хранятся в `/backup/<ip>/`;
- API snapshot/files/restore адресуется по IP;
- self — отдельный псевдохост;
- `fleetSilence()` использует тот же ручной список;
- `bk.extras` содержит отдельные `ip:путь` и остаётся legacy-контуром.

Простая подмена CSV не обеспечивает ни устойчивой идентичности, ни совместимости хранилища. Нужна модель target/resolution, описанная ниже.

### 2.7. OTA-зеркало

Текущий контракт:

- `otam.hosts` содержит hostname;
- комплект хранится в `/ota/<hostname>/`;
- устройство запрашивает `version.json`, firmware и LittleFS по hostname;
- FW+FS являются парой;
- мастер сам себя не зеркалирует.

Этот транспортный и storage-контракт сохраняется. Реестр связывается с зеркалом по фактическому descriptor `host`, а alias в технической связи не участвует. Запуск проверки, загрузка и OTA реестром не производятся.

### 2.8. HTTP и UI

`HomeMasterUi::handleApi()` является достаточной точкой для `hm/fleet/...`. Общий JSON buffer HTTP имеет 24 576 байт. Реестр обязан контролировать фактическую длину ответа и не выдавать обрезанный JSON.

Вкладка «Флот» добавляется в существующий `data/web/index.html`. После правок обязательны:

- `node --check` извлечённого JavaScript;
- проверка баланса script-тегов;
- diff против предыдущего принятого кита.

## 3. Модель реестра

### 3.1. Каноническая идентичность

Ключ записи — ровно 12 HEX-символов `deviceId`, полученный из сегмента топика и подтверждённый полем `id` descriptor.

Правила:

- topic id и JSON `id` обязаны совпадать;
- hostname, IP, MQTT clientId и alias — изменяемые свойства, не ключи;
- смена IP обновляет существующую запись;
- смена hostname обновляет transport/display-свойство и OTA-связь;
- alias не передаётся устройству и не влияет на его работу;
- коллизия id с несовместимыми данными не удаляет запись: применяется последний валидный descriptor, увеличивается счётчик конфликтов и выводится предупреждение.

### 3.2. Ёмкость и создание записей

- Статический массив на 12 устройств, соответствующий текущему масштабу брокера.
- Без динамического JSON DOM и без вытеснения существующих записей.
- Валидный state/telemetry может создать provisional-запись с `identified=false`.
- Полный descriptor подтверждает запись и заполняет profile/versions/host/IP.
- Неизвестное устройство сверх ёмкости увеличивает `records_rejected` и пишет warning; существующая запись не перезаписывается.
- Автоматического TTL-удаления записи нет.

Provisional-запись нужна потому, что при CONNECT `state=online` публикуется до descriptor. Она не считается полностью идентифицированной и не даёт backup/OTA-интеграции до получения валидного descriptor.

### 3.3. Состав записи

Минимальный состав:

```text
deviceId
identified / descriptor_present
alias
profile
kernel
profile_ver
hostname
ip
current_client_id

descriptor_last_seen_ms / _unix
availability_last_seen_ms / _unix
telemetry_last_seen_ms / _unix
last_online_ms
availability_state

uptime
heap
heap_min
bus_dropped
bus_hwm
cpu_t
degradation
gw_rtt
bootloop
audit_lost

telemetry_present
identity_conflicts
```

Unix-время заполняется только при достоверном времени (`unix >= 1700000000`). Иначе хранится/показывается только монотонный возраст по `millis()`, без выдуманной календарной даты.

Все вычисления возраста и timeout должны быть устойчивы к переполнению `millis()` через беззнаковую разность.

### 3.4. Разделение свежести данных

Три независимых факта:

- **descriptor_last_seen** — когда получен валидный descriptor;
- **availability_last_seen** — когда получен валидный state;
- **telemetry_last_seen** — когда получена валидная telemetry.

Retained descriptor сам по себе не доказывает текущую доступность. Retained telemetry не доказывает, что устройство сейчас online. Общий `last_seen` может использоваться для сортировки, но не заменяет три отдельных timestamp.

## 4. Availability, reconnect и stale

### 4.1. Состояния

Для обычного устройства:

- `unknown` — availability ещё не получена;
- `online` — последний валидный state online, либо подтверждена активная сессия;
- `offline` — получен валидный offline либо подтверждён уход последней сессии;
- `stale` — последний известный state online, но telemetry/state отсутствуют дольше порога свежести.

Для self:

- запись существует всегда, пока работает реестр;
- сетевой IP и локальная telemetry обновляются непосредственно;
- `upper_mqtt` показывается отдельно;
- потеря верхнего брокера не переводит self в offline/stale.

### 4.2. Порог stale

Базовый порог — **10 минут** без новых state/telemetry при последнем известном online. Это покрывает допустимый `tel.period_s=300` с запасом и не объявляет устройство offline по одному пропущенному снимку.

`stale` — признак устаревания наблюдения, не доказательство отключения питания и не команда для ПАЗ/backup/OTA.

### 4.3. RemoveClient и гонка reconnect

При `RemoveClient` нельзя безусловно хоронить устройство:

1. Найти запись по изученному соответствию clientId/deviceId.
2. Если это не текущий clientId записи — событие старой сессии игнорировать для availability.
3. Если `BrokerService::hasClient(clientId)` возвращает true — устройство уже переподключилось, offline не устанавливать.
4. Если более свежий online уже получен через другой clientId для того же deviceId — старое RemoveClient не должно перезаписать его.
5. Только уход подтверждённой последней сессии переводит запись в offline.

Новый валидный online всегда обновляет current_client_id и availability timestamp. Допустим короткий промежуточный unknown/stale во время гонки; недопустим устойчивый ложный offline после восстановления связи.

### 4.4. Удаление retained descriptor

Пустой payload descriptor — удаление retained-значения:

- `descriptor_present=false`, `identified=false`;
- profile/versions/host/IP как актуальные descriptor-данные очищаются;
- alias и исторические timestamps не удаляются;
- availability/telemetry могут продолжать обновляться отдельно;
- backup resolution по этой записи приостанавливается, чтобы не использовать старый IP;
- запись и алиас автоматически не удаляются;
- новый валидный descriptor повторно идентифицирует ту же запись.

## 5. Persistence и деградация хранилища

### 5.1. RAM-first

Descriptor, availability, telemetry, текущие IP и статусы живут в RAM. На каждую telemetry никаких записей на SD/LittleFS нет. Периодического сохранения реестра нет.

После перезапуска мастера не восстанавливается «призрачный» снимок доступности. Устройства переподключаются к локальному брокеру и заново публикуют state/descriptor/telemetry.

### 5.2. Алиасы

Алиасы — единственные обязательные persistent-данные нового реестра:

- файл в LittleFS мастера, независимый от SD;
- запись только при ручном добавлении/изменении/удалении алиаса;
- атомарная схема `tmp → проверка → rename`;
- пустой alias удаляет только локальное человекочитаемое имя;
- максимум 32 символа, JSON escaping обязателен;
- при ошибке чтения/записи реестр продолжает работать в RAM и честно показывает `alias_persist=false` / ошибку сохранения.

Изменение алиаса — локальная операция мастера, не активная операция над устройством. Вкладка «Флот» остаётся read-only по отношению к флоту: никаких команд и запросов устройствам.

### 5.3. Отсутствие SD

Реестр, API, self и алиасы не зависят от смонтированной SD. Backup/OTA-поля показывают существующие `no_sd`/ошибки своих сервисов. В broker hook обращений к SD нет.

## 6. Read-only HTTP API и вкладка «Флот»

### 6.1. GET `/api/dev/hm/fleet`

Возвращает:

- версию API;
- текущее достоверное unix-время либо 0;
- счётчики records/identified/online/stale/offline;
- counters: accepted/rejected/truncated/identity_conflicts/records_rejected;
- состояние persistence алиасов;
- массив devices.

Для каждого устройства:

```text
id, alias, self, identified, descriptor_present
profile, kernel, profile_ver, host, ip
availability, descriptor_age_s, availability_age_s, telemetry_age_s
telemetry_present, uptime, heap, heap_min, bus_dropped, bus_hwm,
cpu_t, degradation, gw_rtt, bootloop, audit_lost
web_url (только при актуальном валидном IP)
backup { selected, target, resolved_ip, last_ok, err, blocked, storage }
ota { configured, linked, pair_ready, fw_size, fs_size,
      mirror_kernel, mirror_profile_ver, version_relation, last_ok, err }
```

`null` используется для неизвестных чисел; пустые строки не выдаются за измеренные нули. Возраст неизвестного timestamp — `null`, а не 0.

API обязан либо вернуть полный валидный JSON, либо явную ошибку недостаточного буфера. Молчаливая обрезка массива запрещена.

### 6.2. Локальное изменение alias

`POST /api/dev/hm/fleet/alias` с `id` и `alias` меняет только метаданные мастера. Endpoint:

- не отправляет MQTT-команд;
- не выполняет HTTP к устройству;
- не запускает backup/OTA;
- не меняет hostname и конфигурацию устройства;
- требует существующую запись с каноническим id.

Это не fleet-operation, а локальная настройка отображения. Все остальные новые fleet endpoints — GET.

### 6.3. Вкладка

Одна таблица/карточки без панели действий:

- alias и hostname;
- id и профиль;
- версии ядра/профиля;
- availability и возраст наблюдений;
- IP и ссылка на веб;
- degradation, heap/heap_min, uptime, bus_dropped/bus_hwm, cpu_t, gw_rtt;
- последний backup и ошибка;
- состояние OTA-комплекта и расхождение версий;
- признаки provisional, deleted descriptor, stale, конфликт идентичности.

Не добавляются кнопки OTA, restore, удаления, группового выбора и команд. Существующие ручные кнопки на вкладках «Бэкапы»/«OTA» остаются отдельными и не дублируются.

## 7. Интеграция с BackupAggregator

### 7.1. Ручная политика выбора

Появление устройства в реестре не включает его в backup. Существующий список `bk.hosts` остаётся ручной политикой выбора.

Допускаются две формы элемента:

```text
10.146.75.53       — legacy, фиксированный IP
id:3e0f02ded999    — стабильный deviceId, IP разрешается через реестр
```

Переход на `id:` выполняет владелец вручную. Никакой автоматической миграции `bk.hosts` нет.

### 7.2. Разрешение адреса

Для `id:`:

- требуется `identified=true`, `descriptor_present=true` и валидный актуальный IP;
- IP разрешается перед уже существующим плановым/ручным циклом;
- offline/stale не удаляет запись или политику; попытка завершается существующей ошибкой недоступности;
- отсутствие актуального IP даёт явный `fleet_no_ip`, без обращения по старому адресу;
- смена IP не создаёт нового backup-хоста и не запускает внеплановый snapshot;
- событие `CFG_CHANGED` и `fleetSilence()` используют ту же модель разрешения.

Для legacy IP поведение не меняется. Ручной fallback для нестандартных устройств сохраняется.

### 7.3. Совместимость хранилища

В M3.4a не выполняется автоматическое перемещение существующих каталогов.

- Legacy target продолжает использовать `/backup/<ip>/`.
- Новый `id:` target использует стабильный `/backup/id-<deviceId>/`.
- Старые IP-каталоги не удаляются и не присваиваются другому устройству.
- API files/snapshot/restore для `id:` получает отдельный target-идентификатор; старые IP endpoints сохраняются.
- Исторические IP-снимки автоматически не смешиваются с новым id-каталогом: связь старой истории с deviceId в существующих файлах не доказана.
- `bk.extras` в базовом M3.4a остаётся legacy `ip:путь`; автоматическое слежение extras за IP не заявляется.

Такой переход сохраняет рабочие снимки и не требует необратимой миграции.

### 7.4. Запрет новых триггеров

Реестр не вызывает `apiSnapshot()`, restore, fleetSilence или иной backup action. Он предоставляет только resolver/read model. Существующие расписание, `bk.on_change` и ручной «Снять сейчас» сохраняют прежнюю семантику.

## 8. Read-only связь с OTA-зеркалом

Связь выполняется по:

`deviceId → descriptor.host → otam.hosts → HostState OtaMirrorService`.

Показываются:

- configured — hostname входит в `otam.hosts`;
- linked — descriptor host совпадает с зеркалируемым hostname;
- pair_ready — зеркало содержит принятый FW+FS комплект, размеры и версии известны, активной ошибки нет;
- mirror kernel/profile_ver;
- version_relation — `same` / `different` / `unknown` относительно descriptor;
- last_ok и lastErr существующего зеркала.

Ограничения честности:

- descriptor v1 не содержит board/capabilities, поэтому аппаратная board-совместимость реестром **не доказывается**;
- `different` означает различие версий, а не автоматическую рекомендацию обновления;
- `pair_ready` не является разрешением на OTA;
- alias не участвует в связывании;
- hostname остаётся ключом существующего OTA transport/storage;
- мастер не получает вымышленную self-OTA запись.

Реестр не меняет `otam.hosts`, не вызывает `apiCheck()`, не скачивает файлы и не инициирует UpdateService. Для чтения используется RAM-снимок OtaMirrorService; файловая проверка остаётся в существующем OTA API, а не в broker hook.

## 10. План проверки

Host-тесты обязательны, но полевой PASS ими не подменяется.

### 10.1. Host: topic и JSON

1. Валидные descriptor/state/telemetry принимаются.
2. Не-12-HEX id, лишние сегменты, чужой prefix и несовпадение topic id/JSON id отклоняются.
3. `truncated=true` не разбирается.
4. Пустой descriptor удаляет только descriptor-состояние.
5. Неизвестные telemetry-поля игнорируются; отсутствующие поля не превращаются в нули.
6. Строки с escaping/максимальной длиной не портят JSON.
7. Ответ 12 устройств помещается в 24 КБ либо возвращает явную ошибку, но не обрезанный JSON.

### 10.2. Host: идентичность и состояния

1. State до descriptor создаёт provisional; descriptor подтверждает ту же запись.
2. Descriptor `A→B` по IP обновляет IP без новой записи.
3. Смена hostname сохраняет deviceId и alias.
4. Alias не меняет OTA/backup technical key.
5. `RemoveClient` старой сессии после нового online не даёт устойчивый offline.
6. `hasClient=true` подавляет ложный offline.
7. Уход последней сессии даёт offline.
8. Потеря telemetry при online даёт stale только после 10 минут.
9. Unix=invalid не создаёт календарных дат.
10. Переполнение millis не даёт ложного stale/negative age.
11. 13-е устройство не вытесняет существующие записи.
12. Self существует без верхнего MQTT и обновляет IP локально.

### 10.3. Host: backup/OTA

1. Legacy IP target остаётся совместимым.
2. `id:` target разрешается в актуальный IP.
3. Смена IP меняет resolved address, но не запускает snapshot.
4. Provisional/deleted descriptor даёт `fleet_no_ip`/отказ resolution.
5. Offline не удаляет политику и alias.
6. ID target использует стабильный id-каталог; старые IP-каталоги не удаляются.
7. OTA join использует host, не alias.
8. Pair/version/error statuses читаются без вызова check/download/update.
9. Board compatibility не выдаётся за доказанную.
10. Ни один входной MQTT event не вызывает backup/OTA action.

### 10.4. Сборка и статические проверки

1. Первая сборка после распаковки кита — clean.
2. Сборки строго последовательные.
3. Все изменённые файлы проверены grep/diff после каждого редактирования.
4. Все новые `printf/snprintf/log` имеют format/args 1:1.
5. ModuleId уникален; hooks регистрируются без `slots full`.
6. `node --check`, баланс script-тегов и diff UI против 0.9.10 — PASS.
7. В diff нет ядерных файлов, секретов, WiFi/BT, команд устройствам и новых автоматических триггеров.
8. Комплект содержит FW+FS и исходники со структурой репозитория.

### 10.5. Полевая первичная приёмка мастера

Обновляется только home_master, вручную, парой FW+FS. Другие устройства остаются на принятых 5.9.9 и своих профилях.

1. **Boot/self:** self-запись с фактическим id/profile/versions/IP; верхний MQTT отдельно.
2. **Обнаружение:** smart_lock и weather_gate появляются после reconnect; descriptor/state/telemetry имеют раздельные timestamps.
3. **Alias:** назначить, перезагрузить мастер, подтвердить сохранение; hostname устройств не изменился.
4. **Reconnect race:** жёсткий reconnect устройства; после восстановления нет устойчивого ложного offline/дубля.
5. **IP A→B→A:** одна запись на deviceId, актуальный IP и web URL обновляются; descriptor age меняется независимо от availability.
6. **Retained delete:** пустой descriptor снимает identified/IP; alias остаётся; reconnect восстанавливает descriptor.
7. **Верхний брокер недоступен:** локальный реестр и self продолжают обновляться; нет аварийных fleet actions.
8. **Backup legacy:** существующий ручной IP target и история доступны.
9. **Backup id:** вручную задать `id:`, выполнить ручной snapshot; после смены IP новый ручной snapshot идёт по актуальному IP. По событию смены IP автоматического snapshot нет.
10. **OTA read-only:** linked/pair/version statuses совпадают с существующей OTA-вкладкой; реестр не вызывает check/OTA.
11. **SD absent/degraded:** реестр/UI/self работают, broker hooks не обращаются к SD; ошибки backup/OTA честно видны.
12. **Нет активных операций:** журналы подтверждают отсутствие команд, snapshot, check и OTA, инициированных реестром.
13. **UI:** вкладка работает при фактическом флоте, JSON валиден, старые вкладки и API сохранены.

### 10.6. Длительная приёмка

После первичного PASS начинается отдельный пассивный soak 24/48/72 часа без смешивания с новыми экспериментами.

На каждой точке фиксируются:

- heap, heap_min, max free block;
- clients, retained, broker rx;
- M2 up/down/loss/synth;
- число записей и counters реестра;
- отсутствие роста записей при reconnect/IP changes;
- отсутствие неожиданных backup/OTA actions;
- открытые/закрытые TICK_OVERRUN парно и честно;
- SD, backup, OTA mirror, NTP и ПАЗ.

Кратковременный heap-минимум не объявляется утечкой без продолжения ряда. Последний открытый overrun не записывается как закрытый. Финальный срез без следующего не выдаётся за наблюдённое восстановление.

## 11. Критерии готовности M3.4a

Этап считается реализованным только когда:

1. Весь новый сбор проходит через существующие публикации и self-источники; устройства самодостаточны.
2. Нет ни одного нового автоматического действия над флотом.
3. `deviceId` сохраняет запись при reconnect, смене IP/hostname и alias.
4. Descriptor, availability и telemetry не смешиваются по смыслу и свежести.
5. Backup получает актуальный IP только для вручную выбранных `id:` targets, с legacy fallback.
6. OTA-зеркало только читается; никакая board-совместимость не выдумывается.
7. Реестр переживает отсутствие SD и потерю верхнего брокера без отказа основных функций мастера.
8. Ядро 5.9.9 не изменено; обновлён только профиль мастера.
9. Первичная полевая приёмка и отдельные точки 24/48/72 документированы без подмены полевых результатов host-тестами.

До выполнения этих пунктов документ является контрактом и планом, а не нотой о принятии M3.4a.

## 12. Рекомендация на этап активных действий с флотом: Fleet Lifecycle

**Решение владельца 21.11.2026:** пункт рекомендован к реализации при последующем переходе к активным действиям с флотом. В пассивный M3.4a он не входит; возвращаться к переработке принятого пассивного реестра ради него не требуется.

Назначение рекомендации — не допустить накопления непонятных «мёртвых» записей после аппаратной замены контроллера. Новый контроллер всегда получает новый уникальный `deviceId`; восстановление конфигурации, прежнего hostname, профиля или функции устройства не объединяет его автоматически со старой записью.

В будущем активном этапе предусмотреть:

- раздельные `availability` (`online/stale/offline/unknown`) и `lifecycle` (`active/long_absent/retired`);
- сигнал владельцу о длительном отсутствии устройства: «обрати внимание и прими решение»;
- ручную отметку старого `deviceId` как выведенного из эксплуатации;
- ручную связь `replaced_by=<новый deviceId>` без автоматического объединения записей;
- сохранение старой истории и backup до отдельного ручного решения;
- возможность скрыть `retired` из основного представления без удаления записи.

Для достоверного учёта длительного отсутствия между перезапусками мастера в будущем расширении понадобится минимальный persistent-каталог: `deviceId`, alias, profile/last hostname, `last_activity_unix`, `offline_since_unix`, lifecycle и `replaced_by`. Запись — не на каждую telemetry, а только при ручных lifecycle-изменениях, подтверждённых переходах и редком суточном уточнении timestamps. Сохранённое прошлое состояние после перезапуска не выдаётся за текущую availability.

Никакой автоматики решений не допускается даже в будущем активном этапе без отдельной санкции: система только сигнализирует, владелец вручную решает судьбу записи. Автоматические удаление, объединение, перенос alias/backup/OTA-политик и любые команды устройствам не предполагаются.

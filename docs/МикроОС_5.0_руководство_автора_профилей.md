# МикроОС 5.0 — Руководство автора профилей

> **Актуализировано под ядро 5.7.0 (13.08.2026):** бюджет таблицы конфига
> (§4.4), актуальный контракт `IUiProvider::handleApi` с `ShUiRequest` (§4.8),
> состав сервисов (§4.9), новые уроки (§8).
>
> **Для кого этот документ.** Вы создаёте новое устройство экосистемы
> на платформе WT32-ETH01 + DS3231 + MAX803S: реле, термостат, контроллер полива,
> СКУД, что угодно. Ядро трогать **нельзя** — всё устройство описывается
> **профилем**: манифестом железа, настройкой драйверов, модулем
> бизнес-логики и (опционально) веб-UI. Этот документ — полный маршрут
> от пустой папки до профиля, проходящего стенд соответствия.
>
> Дополнительно: `МикроОС_5.0_справочник_платформы.md` — сгенерированные
> из кода таблицы событий, модулей, конфиг-полей и эндпоинтов.

## 1. Идеология за пять минут

```
┌─────────────────────────────────────────────────────────────┐
│  ЯДРО (неизменное для всех устройств)                       │
│  Kernel · EventBus · ResourceManager · ModuleBase           │
│  Сервисы: Storage · Config · Auth · Time · Network ·        │
│  Telemetry · Audit · Log · Update · Health · MQTT · HTTP    │
│  Драйверы: EspTemp · Ds3231 · DfPlayer · Bus/I2C            │
├─────────────────────────────────────────────────────────────┤
│  КАТАЛОГ ПЕРИФИИ (библиотека src/catalog/) — берёте по желанию    │
│  wiegand/ (СКУД, ворота, сейфы) · будущие редкие драйверы   │
├─────────────────────────────────────────────────────────────┤
│  ПРОФИЛЬ (ваш код, папка profiles/<device>/)                │
│  Манифест железа · конфиг драйверов · бизнес-логика · UI    │
└─────────────────────────────────────────────────────────────┘
```

**Главный закон:** новое устройство = новая папка профиля. Если вам
захотелось отредактировать файл ядра — остановитесь: почти наверняка
существует точка инжекции (конфиг-схема, события, UI, драйвер, healthcheck).
Если точки нет — это повод для разговора с архитектором ядра, а не для патча.

**Три точки инжекции профиля** (все через `registerExtensions()` вашего модуля):

| Что | Куда | Как |
|---|---|---|
| Параметры | ConfigService | `addFields()` — веб-UI построится сам |
| События | ResourceManager | `claimEventRange()` — свой диапазон ID |
| Веб-UI | HttpService | `setUiProvider()` — публичная секция + API |

## 3. Жизненный цикл: что ядро вызывает и когда

Ядро прогоняет все модули через фазы **в порядке приоритета**
(меньше число — раньше; профильные приложения — приоритет 10+):

```
describe()            — модуль называет себя; регистрирует драйверы.
                        ТОЛЬКО метаданные, железо не трогаем.
registerExtensions()  — ТОЧКА ИНЖЕКЦИИ: конфиг-схемы, UI, healthchecks,
                        диапазоны событий. Конфиг уже загружен из JSON —
                        можно читать значения, НО нельзя трогать железо.
init()                — применение конфигурации, инициализация железа
                        (драйверы делают это сами через init() реестра).
start()               — подписки на события, запуск активности.
tick()                — периодическая работа. БЮДЖЕТ 50 мс (B2)!
stop()                — остановка (Safe Mode, shutdown).
onEvent()             — события по подписке. БЫСТРО: это контекст
                        диспетчера шины, бюджет тот же 50 мс.
```

**Дисциплина бюджетов** (нарушение = `SH_EVENT_TICK_OVERRUN` в логе):

- `tick()` и `onEvent()` — до 50 мс. Тяжёлое — в отложенную обработку
  (флаг → следующий tick) или в задачу FreeRTOS.
- Никогда не блокируйтесь: ни `delay()`, ни ожидания ответа железа
  «на месте». Автомат состояний вместо блокировок (образец — DfPlayerDriver).

## 4. Шаг за шагом: устройство «my_relay»

Делаем реле с кнопкой, датчиком на I2C и расписанием. Полный маршрут.

### 4.1. Манифест железа

Манифест — декларация «какая периферия у устройства». Ядро валидирует
его реестром ресурсов (A2) **до инициализации**: конфликт пинов ловится
при старте, а не через неделю в поле.

```cpp
void describeHardware(HardwareManifest& m) override {
    // Системная кнопка Safe Mode (обрабатывает ЯДРО, не профиль!):
    // удержание 3 с → recovery-режим. Выберите физически доступную
    // кнопку устройства. Правила: не 0/12 (страппинг), не пины платформы.
    m.safeModePin = 14;

    // Произвольные GPIO: пин + имя владельца (для реестра и отчётов)
    m.addGpio(13, "relay.out");     // выход на реле
    m.addGpio(15, "button.in");     // кнопка (мягкий страппинг — допустимо,
                                    // но знайте: pull-up при boot)
}
```

**Запрещённые пины** (заняты платформой, стенд D1 их отвергнет):
`16` (PHY power), `18 19 21 22 23 25 26 27` (RMII), `32 33` (I2C DS3231).
**Критичные страппинги:** `0`, `12` — не использовать никогда.
Свободные и безопасные: `2 4 5 12* 13 14 15 17 35 36 39`
(35/36/39 — только входы; \*12 — нет).

### 4.2. Драйверы: использовать существующие

Драйвер ≠ сервис. Драйвер — тонкий слой к железу: читает/пишет и
публикует события `DRV_EVENT_*`. Политика — в вашем модуле.

**Трёхуровневая драйверная модель** (критерий: скольким устройствам нужен):

| Уровень | Что | Где живёт | Примеры |
|---|---|---|---|
| 1. Платформа | есть в КАЖДОМ устройстве на WT32-ETH01+DS3231+MAX803S | ядро, поднимается само | EspTemp, Ds3231, BusManager |
| 2. Общая периферия | нужна МНОГИМ устройствам (свет, климат, счётчики, СКУД) | ядро, активирует профиль через `configure()` | DfPlayer |
| 3. Спецпериферия | нужна ОДНОМУ семейству устройств | **каталог библиотеки `src/catalog/<name>/`**, подключает профиль | Wiegand (только СКУД) |

Правило уровня 3: неиспользуемый драйвер каталога линкер выбрасывает
из прошивки — устройства без этой периферии не платят ни байтом Flash,
ни пином. Пины такого драйвера объявляются через `m.addGpio(pin, role)`
(типизированных полей в манифесте у каталожной периферии нет).

| Драйвер | Уровень | Назначение | Настройка в `registerDrivers()` |
|---|---|---|---|
| EspTempDriver | 1 | температура кристалла (60/75°C) | ядром, ничего не надо |
| Ds3231Driver | 1 | RTC | ядром (BusManager I2C 32/33) |
| BusManager | 1 | владелец I2C + recovery | ядром |
| DfPlayerDriver | 2 | звук (клон MP3-TF-16P!) | `configure(uart, rx, tx, busy, cloneMP3TF16P())` |
| WiegandDriver | 3 | считыватели W26–W56 (СКУД) | `#include "../drivers/wiegand/WiegandDriver.h"` + `configure(d0, d1, Config{...})` |

Пример (реле молчит и периферии каталога не имеет — оставляем пустым):

```cpp
void registerDrivers(const HardwareManifest& m) override {
    // Типизированная периферия — если есть:
    // DfPlayerDriver::getInstance().configure(
    //     m.dfPlayerUart, m.dfPlayerRx, m.dfPlayerTx, m.dfPlayerBusy,
    //     DfPlayerDriver::cloneMP3TF16P());   // клон! не genuine!
    (void)m;
}
```

### 4.3. Если нужен НОВЫЙ драйвер

Контракт `IDeviceDriver`: `driverName/init/poll/getPollIntervalMs/isHealthy`.
Правила железа:

1. **ISR — только накопление.** Никаких `getInstance()` внутри ISR
   (статический локал с guard — опасное размещение вне IRAM!): указатель
   на экземпляр — файловая статика, выставленная в `init()`.
2. **`millis()` в ISR запрещён** — она во flash. Только
   `xTaskGetTickCountFromISR() * portTICK_PERIOD_MS`.
3. События из ISR — через `EventBus::postFromISR()`, без heap.
4. I2C-устройства — ТОЛЬКО через BusManager (мьютекс шины + recovery);
   адрес регистрируется в ResourceManager.
5. Драйвер **не подписывается** на события и не содержит политики.
   Если руки тянутся добавить «а вот тут включим реле» — это бизнес-логика,
   ей место в вашем модуле.

### 4.4. Конфиг-схема (инжекция параметров)

Параметры устройства — декларативные поля. Веб-админка (`/admin` →
«Настройки») построится по схеме **автоматически**, со своей группой,
виджетами по типу и валидацией min/max.

```cpp
void registerExtensions() override {
    ConfigService::getInstance().addFields("Реле", {
        { "relay.schedule_on",  ConfigType::STRING, "08:00", 0, 0, CFG_NONE,
          "Реле", "Время включения (ЧЧ:ММ)" },
        { "relay.schedule_off", ConfigType::STRING, "20:00", 0, 0, CFG_NONE,
          "Реле", "Время выключения (ЧЧ:ММ)" },
        { "relay.max_on_min",   ConfigType::UINT, "600", 1, 1440, CFG_NONE,
          "Реле", "Макс. непрерывная работа, мин" },
        { "relay.invert",       ConfigType::BOOL, "false", 0, 0, CFG_CRITICAL,
          "Реле", "Инверсия выхода (применяется после ребута)" },
    });
}
```

Справка по полям: типы `INT UINT FLOAT BOOL STRING IP SECRET`;
умолчание — всегда строкой; `min/max` — для чисел;
флаги: `CFG_CRITICAL` (изменение = нужен ребут/переприменение),
`CFG_READONLY` (только чтение), `CFG_SECRET` (только NVS, не JSON,
не API — для паролей/токенов).

**Бюджет таблицы полей (урок бенча 5.6.0, фикс 5.6.1).** Таблица ОБЩАЯ на
всё устройство: `CFG_MAX_FIELDS = 96` (было 64 — не хватило). `addFields()`
— fail-fast: первая же не влезшая запись обрывает ВСЮ группу (в логе одна
строка `[E] ... field table full`, остальные поля группы молча теряются,
устройство живёт на вшитых умолчаниях). После добавления схемы смотрите
бут-лог: `init: N fields registered` и отсутствие `field table full`.
Цена поля ~76 Б статики + ~250 Б в JSON-схеме панели (поэтому пропорция
связана с `HTTP_JSON_BUF = 24 КБ` — при росте `CFG_MAX_FIELDS` проверяйте
и его: усечение схемы ловится стражем, но лучше не доводить).

Чтение значений: глобальные `cfgGetBool/cfgGetUInt/cfgGetInt/cfgGetStr`
или типизированные геттеры ConfigService. Изменение значения приходит
событием `CFG_EVENT_CHANGED` (payload — ключ) — можно реагировать живьём.

### 4.5. Диапазон событий профиля

События профиля — из диапазона приложений `0x1000+`. Оформление:

```cpp
// В registerExtensions():
uint16_t base = 0;
ResourceManager::getInstance().claimEventRange("my_relay", 16, base);
// base = 0x1000, 0x1040, ... — фундамент ваших констант:
// RELAY_EVENT_ON = base + 0, RELAY_EVENT_FAULT = base + 1 ...
```

Имена событий — `<ДОМЕН>_EVENT_<ГЛАГОЛ>` (`RELAY_EVENT_OVERHEAT`).
Коллизий с v4.2.2 больше нет: реестр диапазонов обязателен.

### 4.6. Модуль бизнес-логики

```cpp
class MyRelayApp : public ModuleBase {
public:
    static MyRelayApp& getInstance() { static MyRelayApp i; return i; }
    const char* getName() const override { return "MyRelayApp"; }
    const char* getVersion() const override { return "1.0.0"; }
    ModuleId getModuleId() const override { return 0x1000; }  // 0x1000+

    void registerExtensions() override { /* 4.4 + 4.5 */ }

    void init() override {
        _initialized = true;    // ОБЯЗАТЕЛЬНО выставить!
    }

    void start() override {
        EventBus& bus = EventBus::getInstance();
        bus.subscribe(CFG_EVENT_CHANGED, this);
        bus.subscribe(SH_EVENT_DEGRADED_LEVEL, this);
        bus.subscribe(TIME_EVENT_SYNCED, this);
        _started = true;        // и это тоже!
    }

    void tick() override {
        // расписание: TimeService::isTimeInInterval("08:00","20:00")
        // автомат состояний, без delay()!
    }
    uint32_t getTickIntervalMs() const override { return 100; }

    void onEvent(int32_t id, const ShEventData* d) override {
        if (id == SH_EVENT_DEGRADED_LEVEL && d) {
            // A3: сеть упала — профиль решает САМ, но обязан решить
            // осознанно. Реле полива: автономное расписание продолжаем.
        }
    }
    bool canHandleEvent(int32_t id) const override {
        return id == CFG_EVENT_CHANGED || id == SH_EVENT_DEGRADED_LEVEL ||
               id == TIME_EVENT_SYNCED;
    }
};
```

**Правила ModuleBase:** `_initialized/_started` выставляются вами;
`log()`/`postEvent()`/`publishError()` — наследуемые инструменты;
payload события — 48 байт (`ShEventData`), больше — через конфиг/файл.

### 4.8. Веб-UI профиля (опционально)

Публичная страница `/` покажет вашу секцию; API — под `/api/dev/*`.
Актуальный контракт (ядро 5.x, проверено по `src/services/IUiProvider.h`):

```cpp
class MyRelayWebUI : public IUiProvider {
public:
    const char* uiTitle() const override { return "my_relay"; }
    size_t renderPublicHtml(char* buf, size_t size) override {
        return snprintf(buf, size,
            "<b>Реле</b><p>Состояние: %s</p>"
            "<p><button onclick=\"fetch('/api/dev/relay/toggle',{method:'POST'})"
            ".then(()=>location.reload())\">Переключить</button></p>",
            _on ? "ВКЛ" : "ВЫКЛ");
    }
    // Запросы "/api/dev/<pathTail>" приходят сюда. Ответ — ВСЕГДА JSON
    // в буфер вызывающего (application/json, бюджет HTTP_JSON_BUF = 24 КБ);
    // statusCode — HTTP-код. true — обработан; false — 404 ядра.
    bool handleApi(const char* pathTail, const ShUiRequest& req,
                   char* responseBuf, size_t bufSize,
                   int& statusCode) override {
        if (strcmp(pathTail, "relay/toggle") == 0) {
            // АРГУМЕНТЫ: req.getArg("name") — указатель ТРАНЗИЕНТЕН
            // (кольцевой буфер транспорта): живёт до следующего вызова
            // getArg. Копируйте значение СРАЗУ в локальный буфер/число,
            // и только потом читайте следующий аргумент.
            statusCode = 200;
            snprintf(responseBuf, bufSize, "{\"ok\":1}");
            return true;
        }
        return false;  // неизвестный путь -> 404 ядра
    }
};
// В registerExtensions():
static MyRelayWebUI ui;
HttpService::getInstance().setUiProvider(&ui);
```

`ShUiRequest` несёт `method`, `token` ядерной админ-сессии (проверка —
`HttpService::isAdminToken(req.token)`) и колбэк аргументов — транспорт
в интерфейс не тащится, провайдер остаётся host-тестируемым.
Эталон сложного провайдера с пагинацией и санитизацией параметров —
`HomeMasterUi` (API журнала M3.2: files/tail/read с байтовым курсором).

Политика доступа: публичная часть открыта всем (для СКУД — профильный
ПИН: свой ключ rate-limiter'а AuthService, например `noteFailure("user")`).

### 4.9. Ядерные сервисы, полезные профилю (по состоянию на 5.7.0)

**Журнал парка (M3, мастер).** Профилю делать ничего не надо: события,
опубликованные в MQTT-топики по фильтру мастера (`journal.topics`,
по умолчанию `microos/+/events/#,microos/+/state`), мастер пишет на SD
суточными сегментами; смотрятся во вкладке «Журнал» панели мастера
(API: `/api/dev/hm/journal/files|tail|read`). Вывод: публикуйте события
осмысленно — они станут историей парка.

**ScheduleService** — временные правила без своего кода. Правила задаёт
пользователь из панели (группа «Планировщик», формат `имя|С|ПО|дни|код`,
пустое «ПО» — точечное срабатывание) или профиль — статически через
`IScheduleProvider` (`ScheduleService::setProvider()` до старта сервиса).
Реакция — подпиской: `SCHED_EVENT_PERIOD_CHANGED` (code: 0 = вышли,
N = вступили в период с кодом N; payload — имя) и `SCHED_EVENT_RULE_FIRED`,
или опросом `isRuleActive("ночь")` / `isPeriodActive(1)`. Fail-Safe: при
недостоверном времени (мёртвый RTC без NTP) все периоды неактивны —
профиль должен решать поведение так же, как сегодня решает кнопку выхода.
Сервис — датчик периодов: сам ничего не включает, политика у подписчиков.

**CounterService** — долгоживущие числа без износа flash. НЕ пишите
`cfgGetUInt + setInternal` на каждый инкремент (урок cycle_count: flash
писался на каждый цикл замка). Вместо этого:
`CounterService::incrementCfg("my.counter")` — тень конфиг-ключа
(CFG_READONLY-поле видно в панели как раньше); `increment("name")` —
автономный счётчик в NVS ns «cnt». Сброс батчами: `cnt.flush_every` /
`cnt.flush_interval_s` + принудительно при штатном ребуте; потолок потерь
при обесточке — min(N инкрементов, T секунд). Импульсные счётчики
(вода/газ/свет): `attachPcnt("water", GPIO)` — аппаратный счёт без CPU.

**MQTT outbox** — просто работает: `publishRaw()`/`publishStateSuffix()`
при разрыве брокера вернут `true` («принято к доставке») и сообщение
уйдёт replay'ем при reconnect. Retained дедуплицируется (свежее состояние
замещает лежащее в очереди). Диагностика: `outboxSize()`,
`outboxDropped()`. Помните: очередь — RAM, офлайн-ребут её теряет.

**SpeechBuilder** — составная речь (SD папки 05/06, генерируются голосовым
конвейером): `SpeechBuilder::sayNumber(n, SB_MASC/SB_FEM)`,
`sayTime(hh, mm)`, `sayNumberUnit(n, gender, SB_UNIT_HOUR_ONE, 0)` для
триад час/минута, сахар `sayDegrees/sayPercent/sayCubicMeters/sayKwh`.
Числа −4999..4999. `false` — звук выключен/нет плеера: молчание —
легитимный фолбэк. Цепочка (≤6 треков) ставится одним вызовом; вклиниться
может только фраза строго выше приоритетом (это фича арбитража).

## 5. Safe Mode и деградация: обязанности профиля

- **Kernel Safe Mode** (bootloop ×3, кнопка 3 с, команда, паника):
  профильные модули **не стартуют вообще**. Работают сеть, веб (recovery),
  OTA, конфиг. Ваш код не должен рассчитывать на «частичный» Safe Mode.
- **A3**: подпишитесь на `SH_EVENT_DEGRADED_LEVEL` и осознанно решите
  поведение без сети. Для СКУД — Fail-Safe по локальной базе; для полива —
  автономное расписание. «Зависнуть в ожидании MQTT» — не ответ.

## 6. Тестирование профиля (D1 + D2)

1. **Стенд соответствия (D1).** Подставьте профиль в тестовый скетч —
   при старте Serial покажет PASS/FAIL: манифест (пины, safe_mode_pin),
   ноль конфликтов реестра, контракт модулей. Профиль принимается
   **только с полным PASS**.
2. **Host-тесты (D2).** Чистую логику (декодеры, расписания, парсеры)
   выносите в заголовки без зависимостей (образец: `WiegandFormats.h`,
   `TimeInterval.h`, `BcdUtils.h`) и покрывайте в `host/tests.cpp`:
   `g++ -std=c++17 -I shim tests.cpp ../core/ResourceManager.cpp -o tests`.
3. **Фиксация сборкой.** Каждая порция — сборка ядра+профиля
   (`arduino-cli compile`). Линковщик — честный рецензент: он поймал уже
   десяток дефектов, включая несуществующий датчик температуры.

## 8. Топ-9 ошибок (все уже пойманы на этом проекте)

1. `getInstance()` внутри ISR → «dangerous relocation» — файловая статика.
2. `millis()` внутри ISR → то же самое — `xTaskGetTickCountFromISR`.
3. Две правки одного файла в одном сообщении → потерянные инклуды —
   правим последовательно.
4. API ESP-IDF 4.x в ядре 3.x (WDT и др.) — проверяем сигнатуры по
   заголовкам установленного ядра, не по памяти.
5. Коллизии имён с библиотеками ядра (NetworkManager, MQTT_EVENT_*) —
   префиксы и проверка сборкой.
6. Драйвер с политикой → переписывание под каждое устройство —
   политика в профильный модуль.
7. Документ вручную → устарел за неделю — генератор `tools/gen_docs.py`.
8. `req.getArg()` без немедленного копирования → следующий вызов затирает
   значение (кольцевой буфер транспорта). Копируй в локал СРАЗУ (M3.2).
9. `addFields()` «на вырост» без контроля бут-лога → половина группы
   молча не зарегистрировалась (fail-fast, таблица общая на 96 полей).
   После каждой новой схемы: `init: N fields registered` (урок 5.6.0/5.6.1).

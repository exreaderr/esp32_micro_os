# Правила обновления, доставки и приёмки

**Актуализировано:** 24.11.2026  
**Область:** МикроОС 5.9.9 и профили флота  
**Статус:** действующий эксплуатационный протокол

## 1. Основная последовательность

Для изменённого артефакта сохраняется последовательная цепочка:

```text
получить обновления → собрать → синхронизировать общее хранилище
→ прошить устройство → запустить проверку
```

Нельзя пропускать этапы или смешивать новые эксперименты с уже идущей длительной приёмкой.

**Торопиться — не наш метод.**

## 2. До изменения кода

1. Сформулировать задачу и границы этапа.
2. Определить, требуется ли профильное изменение или доказана необходимость ядра.
3. Зафиксировать критерии приёмки.
4. Не приписывать отсутствие функции к дефекту без воспроизводимого доказательства и локализации.
5. Не добавлять UI-полировку, fleet-активность или смежные задачи самостоятельно.
6. Отложенные задачи другого профиля не начинать внутри текущего этапа.

## 3. Правила редактирования

- **NEVER parallel-edit same file.**
- После каждой правки выполнить grep-verify и проверить отсутствие «гремлинов».
- Проверить printf-format и аргументы **1:1**.
- Новые поля конфигурации добавлять **в конец схемы**.
- В клон руками не лезем: изменения поступают контролируемым комплектом.
- Не перезаписывать владельческую ноту старой версией.
- После внешнего изменения ноты использовать её текущую владельческую версию как baseline.
- Не менять ядро ради профильной задачи без доказанной необходимости.

## 4. Версии и состав кита

- При любом kernel-touching ките увеличить `MICROOS_VERSION_STR`.
- Версия профиля изменяется при изменении профиля.
- Ядро и профиль указываются раздельно: `kernel/profile`.
- Доставка исходниками со структурой репозитория.
- Прошивка и FS поставляются и шьются парой.
- В кит включаются фактические источники, бинарники, паспорт, протокол, журналы сборки и контрольные суммы.
- Документные ожидания, например число модулей, сверяются с фактической сборкой.

## 5. Сборка

- Сборки выполняются **строго последовательно**.
- Staging только на `/mnt` или `/tmp` в рабочей среде.
- Первая сборка после распаковки кита — **clean build**.
- Используются фактические данные `projects/<profile>/data/` для FS.
- После сборки проверяются маркеры версий, размеры и отсутствие старых маркеров.
- LittleFS проходит round-trip и побайтовую сверку ключевых файлов.
- Ошибка toolchain или окружения сначала исправляется как ошибка среды, а не маскируется изменением исходников.

## 6. Проверки до поля

Минимальный набор определяется изменением, но может включать:

- host strict;
- ASan/UBSan;
- статический аудит идентификаторов, hooks, лимитов и буферов;
- проверку неизменности файлов ядра при профильном этапе;
- browser mock реальной embedded HTML;
- контрольную распаковку ZIP, CRC и SHA-256-сверку.

Host и browser проверки не заменяют полевой PASS.

После правок `index.html` обязательны:

```text
node --check
баланс script-тегов
diff против предыдущего кита
```

## 7. Доставка файлов

Для каждого файла сохраняется протокол:

```text
rm + cp.tmp + sync + mv + cmp
```

Назначение: исключить частично записанные или непроверенные deliverable. После упаковки выполняется контрольная распаковка и сравнение содержимого.

## 8. GitHub и секреты

- Browser-сессия GitHub не аутентифицирует `git push`.
- Пароль аккаунта при 2FA не используется для Git over HTTPS.
- Применяются GitHub CLI, настроенный credential helper, SSH или иной штатный метод.
- GitHub PAT никогда не запрашивается в переписке и не отображается.
- Пароль брокера маскируется; credentials не запрашиваются и не повторяются.
- `/mnt/agents/output/conveyor/config.json` может содержать plaintext MQTT credentials: содержимое не выводится.
- Полные backup-снимки с секретами не публикуются в общем репозитории.

Перед Sync проверяется список изменений. Документационный Sync не должен содержать неожиданных изменений кода или бинарников.

## 9. Прошивка флота

- Wi-Fi/BT off fleet-wide.
- FW+FS шьются парой.
- Если затронуто ядро, перешивается весь флот; **мастер первым, вручную**, если владелец отдельно не утвердил иной порядок.
- Исторический порядок M3.4-Info-IP1 `smart_lock → weather_gate → home_master` был отдельным исключением и не отменяет общего правила.
- Профильный этап только мастера не требует перепрошивки клиентов.
- Наличие комплекта в OTA-зеркале не является командой OTA.

## 10. Первичная полевая проверка

После прошивки:

1. Проверить версии, deviceId, hostname/IP и состав модулей.
2. Проверить сеть, MQTT, state, telemetry и descriptor.
3. Проверить ПАЗ, SD/FS и профильные функции.
4. Выполнить предусмотренное восстановление конфигурации.
5. Выполнить контрольную загрузку после стабилизации.
6. Только затем зафиксировать начало пассивного прогона.

Плановые загрузки записываются явно, чтобы последующие `ESP-ROM` не смешивались со спонтанными reset.

## 11. Длительная приёмка

Типовые контрольные точки для изменённого эксплуатационного артефакта: **24/48/72 часа**.

На каждой точке проверяются:

- uptime и все загрузки;
- clients, reconnect, client left, retained и RX;
- M2, auth/limit, потери и synthetic offline;
- heap, watermark, max block и sockets по продолжению ряда;
- WDT, panic, allocation failure и HEAP low;
- overrun, их максимумы и закрытия;
- SD/FS, backup, архив, NTP и OTA-зеркало;
- fleet presence, deviceId, дубли и identity conflicts;
- отсутствие несанкционированных активных действий.

Правила честной интерпретации:

- кратковременный heap-минимум не объявляется утечкой без продолжения ряда;
- финальный срез без следующего не выдаётся за восстановление;
- открытый overrun остаётся открытым наблюдением;
- технический PASS точки не подменяет итоговый PASS кандидата;
- новый soak без изменения артефакта не назначается.

## 12. Внешнее прерывание прогона

При сбое питания или монитора порта фиксируются:

- дата и ориентировочное время;
- известная продолжительность;
- какие устройства перезагрузились;
- наличие или отсутствие boot-фрагмента и `reset reason`;
- uptime после восстановления;
- состояние ПАЗ, флота, MQTT и ресурсов.

Если владелец принимает прерванный прогон, итог формулируется как **PASS с оговоркой**. Нельзя заявлять непрерывный uptime, если счётчик был обнулён. Причина события не выдумывается по косвенным признакам.

Для M3.4a принят календарный 72-часовой прогон с внешним сбоем питания и успешным восстановлением; непрерывный 72-часовой uptime не заявлен.

## 13. Закрытие этапа

1. Разобрать все контрольные точки.
2. Зафиксировать открытые наблюдения и документные ошибки.
3. Составить итоговую ноту.
4. Разместить ноту в `docs/ноты/`.
5. Обновить `docs/ПАСПОРТ.md` и действующие документы.
6. Прежние концепции при необходимости сохранить в `docs/история/`.
7. Выполнить Sync и проверить, что состав изменений соответствует этапу.
8. Заморозить принятую базу; следующая задача начинается отдельно.

## 14. Документационные изменения

Документационный этап сам по себе не требует:

- новой прошивки;
- чистой embedded-сборки;
- OTA;
- 24/48/72-часового soak.

Для него обязательны сверка с исходниками, проверка ссылок и структуры, контрольная распаковка пакета и отсутствие изменений кода.

# Флот, идентичность и M3.4a

**Дата актуализации:** 24.11.2026  
**Действующая база:** МикроОС 5.9.9  
**Профиль реестра:** home_master 0.9.11  
**Статус:** действующий контракт; M3.4a закрыт

## 1. Основной принцип

Устройства самодостаточны. Мастер наблюдает флот и систематизирует данные, но не является источником разрешения на работу устройства.

Ни descriptor, ни запись в реестре, ни alias, ни доступность мастера не должны требоваться для выполнения устройством его локальных функций.

## 2. Каноническая идентичность

### 2.1. deviceId

`deviceId` — единственный канонический ключ устройства:

- ровно 12 HEX-символов;
- формируется из MAC;
- не изменяется при смене IP, hostname или версии;
- используется в MQTT-топике и descriptor JSON;
- используется как ключ записи реестра мастера.

Не являются идентичностью:

- hostname;
- IP;
- MQTT clientId;
- локальный alias;
- профильное отображаемое имя.

### 2.2. Descriptor v1

Топик:

```text
<mqtt.prefix>/<deviceId>/descriptor
```

Пример структуры:

```json
{
  "v": 1,
  "id": "3e0f02ded999",
  "profile": "home_master",
  "kernel": "5.9.9",
  "profile_ver": "0.9.11",
  "host": "home_master",
  "ip": "10.146.75.50"
}
```

`id` в топике и теле обязан совпадать. Descriptor retained, публикуется устройством после MQTT CONNECT и при смене IP. Периодическая публикация, ожидание ответа и descriptor outbox не используются.

### 2.3. Изменение сетевых параметров

- `0→A` — адрес acquired;
- `A→B` — адрес changed, запись сохраняет прежний `deviceId`;
- `A→0` — адрес lost;
- `A→A` — повтор не создаёт событие смены;
- новый IP или hostname не создаёт новую fleet-запись.

Retained descriptor может содержать старое время публикации. Его возраст сам по себе не означает offline или зависание, если state/telemetry продолжают поступать.

## 3. State, telemetry и availability

Descriptor, state и telemetry имеют раздельные timestamps.

Availability реестра:

| Значение | Смысл |
| --- | --- |
| `unknown` | данных ещё недостаточно для вывода |
| `online` | имеются актуальные признаки доступности |
| `offline` | получено или сохраняется подтверждённое состояние offline |
| `stale` | данные устарели, но это не доказывает offline |

Для M3.4a `stale` наступает после 10 минут без свежих state/telemetry, если последним известным состоянием было online. `stale` не запускает команды, OTA, backup, удаление или другие действия.

Возрасты и timeout рассчитываются устойчиво к переполнению `millis()`. Unix-время считается достоверным только при `unix >= 1700000000`; неизвестный age представляется как `null`.

Self мастера формируется локально, обновляется по событиям и каждые 15 секунд в медленном цикле. Self не зависит от верхнего MQTT и не проходит через локальный broker hook.

## 4. Пассивный реестр home_master

### 4.1. Хранение

- 12 статических записей;
- RAM-first, без динамического JSON DOM во firmware;
- descriptor/state/telemetry и запись не сохраняются на FS при каждом обновлении;
- записи не удаляются автоматически по TTL;
- persistent только локальные алиасы мастера в LittleFS;
- потеря верхнего брокера не должна разрушать локально формируемый self.

### 4.2. Identity conflict

Если под существующим `deviceId` получен другой несовместимый `profile`:

- запись сохраняется;
- alias сохраняется;
- последний валидный descriptor применяется;
- увеличиваются `Record.identityConflicts` и `Counters.identityConflicts`;
- новая запись не создаётся только из-за конфликта.

Это диагностический сигнал владельцу, а не автоматическое разрешение коллизии.

### 4.3. HTTP API

```text
GET  /api/dev/hm/fleet
POST /api/dev/hm/fleet/alias
```

`POST` изменяет только локальный alias мастера и не отправляет команду устройству.

Правила JSON:

- либо полный валидный ответ, либо явная HTTP-ошибка;
- молчаливая обрезка запрещена;
- неизвестный age — `null`;
- отсутствующая telemetry — `null`;
- отсутствующие optional `bootloop`/`audit_lost` — `null`;
- измеренный `audit_lost=0` остаётся числом 0;
- `web_url=null`, если нет актуального identified descriptor с валидным IP;
- `board_compatible=null`, поскольку descriptor v1 не содержит board/capabilities.

## 5. Вкладка «Флот»

Вкладка отображает:

- alias и канонический `deviceId`;
- профиль, hostname и IP;
- версии ядра и профиля;
- возраст descriptor/state/telemetry;
- uptime, heap, heap_min, CPU, degradation и RTT шлюза;
- EventBus dropped/HWM, bootloop и audit lost при наличии;
- backup target, актуальный IP, хранилище, последний снимок и состояние;
- OTA-связь, комплект, версии, размеры, сверку и ошибку.

Действия вкладки ограничены обновлением, локальным сохранением alias и открытием web-ссылки. Она не содержит fleet-команд, групповых действий, удаления, объединения или OTA.

## 6. Read-only связь с backup

`bk.hosts` остаётся ручной политикой. M3.4a не выбирает новые устройства для snapshot и не создаёт backup-триггеры.

Для уже существующих вручную выбранных задач:

- legacy IP-target продолжает использовать свой прежний путь;
- id-target может получить актуальный IP из descriptor;
- resolution требует `identified=true`, `descriptorPresent=true` и валидный IP;
- unresolved id-target получает состояние `fleet_no_ip`;
- смена IP не запускает snapshot;
- `bk.extras` остаётся legacy;
- self остаётся отдельным псевдохостом;
- `fleetSilence()` использует общий resolver.

Существующие ручные и плановые backup-операции не считаются новой fleet-автоматикой.

## 7. Read-only связь с OTA-зеркалом

Цепочка проекции:

```text
deviceId → descriptor.host → otam.hosts → OtaMirrorService::HostState
```

Правила:

- транспорт и storage остаются hostname-based;
- alias техническим ключом не является;
- Fleet API не вызывает существующий OTA `apiStatus()`, который может читать SD;
- per-device проекция использует только RAM;
- self не получает вымышленную OTA-запись;
- ручная загрузка существующей пары FW+FS в зеркало не является OTA устройства.

`pair_ready` требует:

- linked;
- известные mirror kernel/profile version;
- ненулевые размеры FW и FS;
- пустой `lastErr`.

`version_relation=same/different/unknown` описывает только отношение версий. `different` не является рекомендацией обновления, а `pair_ready` не является разрешением на OTA.

## 8. Двухброкерная топология и M2

- Устройства подключаются к локальному брокеру мастера.
- M2 передаёт предусмотренные данные на вышестоящий брокер и команды вниз по существующим whitelist-правилам.
- Прохождение сообщения через M2 не создаёт второе устройство.
- Для M3.4a не добавляются shadow-replay/rehydrate и публикация descriptor от имени других устройств.
- Потери M2, synthetic offline, reconnect и retained наблюдаются отдельно при полевой приёмке.

## 9. Что остаётся за пределами M3.4a

- активные fleet-операции;
- групповые OTA;
- автоматические snapshot/restore;
- автоматическое удаление и объединение;
- Fleet Lifecycle;
- mDNS;
- UI-полировка;
- автоматическая реакция на stale/offline/identity conflict.

### Будущий lifecycle-задел

Для отдельного будущего этапа согласовано рассмотреть только ручные `retired` и `replaced_by` как средство работы с «мёртвыми» записями. Система может сигнализировать владельцу, но решение и действие остаются ручными. В home_master 0.9.11 этот lifecycle не реализован.

## 10. Полевой результат

M3.4a подтверждён на флоте home_master, smart_lock и weather_gate:

- три стабильные записи без дублей;
- сохранение aliases и canonical IDs;
- свежая telemetry и корректная availability;
- правильные backup и OTA-проекции;
- отсутствие команд устройствам и новых активных fleet-операций;
- 24/48 часов — PASS;
- 72 часа — PASS с оговоркой о внешнем сбое питания и успешном восстановлении.

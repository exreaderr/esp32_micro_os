# Комплект: home_master 0.6.7 — ручная загрузка OTA + otam.src + host в манифесте

**Ядро:** МикроОС 5.8.6 (без изменений — замок и шлюз НЕ трогаем).
**Профиль:** home_master 0.6.6 → **0.6.7**. OtaMirrorService 0.1.1-om2 → **0.2.0-om3**.

## Что нового (сценарий «соседа», владелец 07.09.2026)

### 1. Ручная загрузка комплекта прошивки в зеркало (вкладка «Бэкапы»)

Карточка «Загрузить обновление вручную»: выбрать устройство, указать
version.json + firmware.bin + littlefs.bin (можно по одному, в любом порядке)
— мастер принимает файлы в staging на SD и «в строй» ставит только ПОЛНЫЙ
СОГЛАСОВАННЫЙ комплект. Проверки против человеческого фактора:

1. **Привязка к устройству:** поле `host` манифеста == выбранному устройству
   (иначе «ОТКЛОНЕНО: комплект для "weather_gate", а выбрано "smart_lock"»);
2. **md5 прошивки и ФС** против fw_md5/fs_md5 манифеста (битые/чужие файлы);
3. **Метка версии:** тег MICROOS|x.y.z|END внутри firmware.bin == version
   манифеста (манифест от одной версии, бинарник от другой).

Отклонённый комплект удаляется из staging целиком, зеркало продолжает
раздавать ПРЕЖНЮЮ целую тройку. Принятая тройка вытесняет старую в
`/ota/<host>/archive/` — «загрузил не то» обратимо.

Приём идёт на порту :8123 с админ-токеном: чтение раздачи для флота — по-
прежнему открытое, ЗАПИСЬ — только по токену. CORS для панели (:80 → :8123)
учтён.

### 2. otam.src — источник-переопределение (группа «OTA-зеркало», живое)

Пусто (по умолчанию) — как раньше, с HA. Задано (напр.
`http://192.168.1.10:8123`) — мастер зеркалирует с этого адреса: сценарий
«просто компьютер с веб-сервером» без HA вообще. Структура путей та же:
`/local/ota/<хост>/`.

### 3. Build Master: поле "host" в version.json

`conveyor/build_ota.sh` теперь пишет в манифест `"host": "<имя папки
зеркала>"` — это и есть подпись привязки для проверки №1. Старые манифесты
без host мастер принимает (проверка №1 просто не срабатывает), но все новые
релизы будут подписаны.

## Как обновляться

1. Раскатать файлы в клон репозитория (структура сохранена) + build_ota.sh
   в conveyor на компьютере сборки.
2. Менялись и прошивка, и ФС — **шьём ПАРОЙ** (прошивка + LittleFS).

## Проверка

1. Вкладка «Бэкапы»: появилась карточка «OTA-зеркало парка» (она пропадала —
   восстановлена) и «Загрузить обновление вручную».
2. Загрузить тройку smart_lock (из ~/Arduino/ota/smart_lock): вердикт
   «ПРИНЯТО: версия …», в карточке зеркала версия/размеры обновились.
3. Контрпроверка: ту же тройку загрузить, выбрав weather_gate →
   «ОТКЛОНЕНО: комплект для "smart_lock"…» (сработает, когда манифест со
   свежим полем host; на старом манифесте — отклонит по md5/версии, если
   файлы перепутаны).
4. Загрузить заведомо битый файл (обрезать firmware.bin) → «ОТКЛОНЕНО: md5…».
5. Штатный путь не сломан: «Проверить сейчас» в зеркале — опрос HA,
   устройство обновляется с мастера.

## ПРАВКА 1 (приёмка 07.09): «version.json: auth» — загрузки отклонялись по 401

**Корень:** ESP32-WebServer собирает только ЯВНО объявленные заголовки;
`X-Auth-Token` не был объявлен через `collectHeaders()` на сервере :8123 →
токен до handler'а не доходил → 401 «auth» на любом файле. (Отклонения,
увиденные при прогоне неподписанных комплектов, были этой же ошибкой —
проверки комплекта до дела не доходили.)
**Правка:** `collectHeaders(X-Auth-Token)` в attachRoutes + панель дублирует
токен в query-аргументе (двойной канал). Прошивка + ФС — парой.
**Повторная проверка:** пп. 2–4 основного паспорта (ПРИНЯТО / ОТКЛОНЕНО
по host / ОТКЛОНЕНО по md5) — теперь доходят до настоящей верификации.

## ПРАВКА 2 (07.09): bk.admin_pin — пароль лежал открытым текстом → в NVS

**Дырочка:** поле было объявлено `ConfigType::SECRET`, но БЕЗ флага
`CFG_SECRET`. Урок: тип сам по себе ничего не делает — NVS-хранение,
маскировку в панели и исключение из config.json включает именно ФЛАГ.
Пароль администратора парка лежал в config.json и светился в панели.
**Правка:** флаг `CFG_SECRET | CFG_NONE` — значение живёт только в NVS,
в панели «задан (скрыт)», write-only. Аудит схемы: других незакрытых
секретов нет (broker.pass закрыт в 0.6.6, больше SECRET-полей без флага
не найдено).
**Разовое действие после прошивки:** старое значение жило в config.json
и в NVS само не переедет — ПИН нужно ввести заново (Настройки → Бэкапы).
До ввода бэкапы устройств парка будут падать с «no_pin» — это ожидаемо.
**Прошивка:** только firmware (index.html не менялся этой правкой; если
ПРАВКА 1 ещё не прошита — шьём парой, она покрывает обе).






# ПАСПОРТ — home_master 0.6.8 «hm.fleet + гистерезис ПАЗ»

Дата: 07.09.2026. База: ядро 5.8.6 (НЕ тронуто, флот не прошивается).
Прошивается ТОЛЬКО мастер, и только firmware (index.html/data не менялись).

## Что нового

### 1. hm.fleet — присутствие парка в ПАЗ (копилка M5)
Закрывает дыру приёмки M3.3: «брокер видит отсутствие замка, а ПАЗ
здорова» — ПАЗ следил за МАСТЕРОМ, но не за парком.
- Ожидаемый состав: реестр bk.hosts (кроме self).
- Факт присутствия: активные MQTT-сессии брокера мастера
  (clientId устройства = его hostname, ядро так делает всегда).
- Хосты без известного hostname (ещё ни одного снимка) не проверяются:
  «нет данных» ≠ «молчит» — свежий мастер не поднимет ложную тревогу.
- Семантика (утверждена владельцем 07.09.2026):
  · bk выключен или имён нет → Ok (нет данных);
  · ЧАСТЬ парка молчит → Warning с именем первого молчащего;
  · молчат ВСЕ → Critical «молчит весь парк (N)» — это похоже на
    сломанный брокер/сеть, ситуация защитная.
- В панели появляется во вкладке ПАЗ автоматически (через /api/health) —
  UI не менялся. Это же — будущий корм третьего пикселя светофора.

### 2. Гистерезис доменных проверок ПАЗ (вариант Б)
Долг из приёмки M3.3: hm.bk клацал Warning/recovered на «мигающем»
хосте (offline→ok→offline), счётчик warn рос на шуме (1/мин).
- Беда признаётся бедой после 3 подряд плохих прогонов (~3 мин при
  прогоне 60 с), восстановление — после 2 подряд хороших (~2 мин).
- Применено к hm.bk, hm.ota и hm.fleet (общий ConfirmState в профиле).
- Ядро НЕ тронуто: при переезде флота на 5.8.7 механизм переедет в
  HealthMonitor (общий для всех проверок), тогда же порог «молчит»
  уйдёт в конфиг (решение владельца 07.09.2026). Из профиля — уберём.

## Приёмка

## Ядро 5.8.8 — двухполевая версия OTA

1. **Version.h**: `MICROOS_VERSION_STR "5.8.8"`. Если профиль объявил
   `#define MICROOS_PROFILE_VER x.y.z` ДО включения ядра (шапка App.h),
   в .bin зашивается ПОЛНАЯ метка `MICROOS|ядро|профиль|END` рядом с
   ядерной `MICROOS|ядро|END`. Проверено grep'ом по готовым образам —
   обе метки на месте во всех трёх профилях.
2. **UpdateService**: `setProfileVersion()` (профиль зовёт в init из
   `getVersion()`), сверка манифеста: обновление есть, если ядро новее
   ИЛИ (ядро равно И profile_version новее). Даунгрейд по ЛЮБОМУ полю не
   предлагается. Манифест без profile_version — сравнение только по ядру
   (обратная совместимость). `/api/ota/info` отдаёт `profile` (локальный)
   и `remote.profile_version`.
3. **OtaMirrorService**: читатель меток сканирует ВСЕ вхождения `MICROOS|`,
   предпочитает 4-полевую, 3-полевая — запасная. Приём комплекта: если в
   манифесте есть `profile_version`, метка в прошивке ОБЯЗАНА совпасть —
   иначе `reject:fw_prof:<tag|none>`.
4. **Панель мастера**: карточка OTA показывает «ядро · профиль» с двух
   сторон, различает «Доступно обновление ядра!» / «…профиля!»; вердикт
   `reject:fw_prof` переведён на русский.

## Урок 5.8.8 (в копилку)

`__attribute__((used))` НЕ спасает строку от `--gc-sections` без живой
ссылки: локальный volatile-указатель LTO выкидывает. Рабочая ссылка —
передача адреса во внешний вызов (printf/log). Ядерная метка выживала
именно потому, что Kernel.cpp её печатает; полная метка без ссылки молча
исчезала из .bin (поймано grep'ом образа при сборке).

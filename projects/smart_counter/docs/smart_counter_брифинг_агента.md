# БРИФИНГ АГЕНТА: профиль smart_counter (МикроОС 5.0)

> Назначение документа: холодный старт ветки разработки smart_counter.
> Прочитав его (и пакет документации репозитория целиком), агент обязан
> работать так, будто участвовал в проекте с начала.
> Документ написан из «ядерной» ветки (smart_lock + home_master).
> Первая редакция: 31.08.2026, ядро **5.8.4** (на soak 72 ч перед тегом).
> Это не DIY-поделка: «хоть и гаражный» проект, но с промышленной
> дисциплиной качества.
>
> **Статус запуска:** ветка стартует с КОНЦЕПТ-НОТЫ (см.
> `smart_counter_постановка_ветке.md` — обязателен к прочтению первым).
> Код профиля — только после тега v5.8.4 и рецензии концепт-ноты
> ядерной веткой. «Торопиться — не наш метод» (владелец).

## 1. Что это за проект

**МикроОС 5.0** — модульная ОС для экосистемы умного дома автора.
Неизменяемое ядро + подключаемые профили устройств.

Философия (не нарушать):

- **Ядро неизменяемо.** Профиль подключается через точки инжекции данными,
  а не правками ядра. «Чешется» править ядро — вопрос выносится в ядерную
  ветку как запрос сервиса/данных (Issue #1, с доказательной цепочкой).
- **Самодостаточность (принцип владельца, дословно):** «любое
  устройство/контроллер абсолютно самодостаточен, ничего нет — сам всё
  делаю, есть сеть и окружение — функционал только расширяется».
  Архитектурный закон. Для счётчика это значит: показания и тарификация
  живут на устройстве, переживают панику и офлайн; сеть только расширяет.
- **Параноидальный проводной контур.** WiFi/BT глушатся на ВСЕХ
  устройствах «отсутствием кода», только провода. У счётчика радио-
  исключений нет вообще (в отличие от receive-only CC1101 у weather_gate).
- **Параноидальная безопасность.** Секреты — только в NVS, никогда в JSON.
- **Детерминизм.** Никакого `localtime_r`/TZ-окружения, никаких «обычно
  работает». Уроки записываются прямо в код комментариями.

## 3. Что УЖЕ есть в ядре под smart_counter (не изобретать)

Прежде чем проектировать свой механизм — проверь этот список.

- **ConfigService** — схема+валидация, NVS-секреты, CFG_EVENT_CHANGED,
  классы полей (CFG_CRITICAL → ребут / CFG_NONE — на лету). Коэффициенты,
  тарифы, начальные показания, пороги — ВСЁ в конфиг, не константы.
  Новые поля — СТРОГО В КОНЕЦ схемы. Префикс ветки: `sc.`.
- **CounterService (ядро)** — проверить первым делом: сервис счётчиков
  уже существует (используется флотом). Монолитные наработки по учёту
  импульсов сопоставлять с ним, а не писать параллельный механизм.
- **DataLogService + DataLogCore** — временные ряды: RAW-кольцо в RAM
  (6 ч), ярусы HOUR (31 сутки) и DAY (год) в LittleFS. Расход по часам/
  суткам — готовые каналы, своё кольцо писать ЗАПРЕЩЕНО. 8 каналов
  максимум — планировать (электро/вода/газ + тарифы).
- **MqttTransport** — outbox-реплей при офлайне (доказан стендами),
  BOOT-события, LWT `<prefix>/<id>/state`. Свои MQTT-клиенты запрещены.
  **Учёт результата публикации обязателен** (урок weather_gate 0.3.8:
  молчаливый отказ publishRaw недопустим; переходы ok↔fail — в журнал).
- **TelemetryService** — периодический статус вверх; величины профиля
  регистрируются телеметрийными айтемами.
- **HttpService + IUiProvider** — панель и API профиля; getArg транзиентен
  (правило 17); uPlot для графиков расхода — из эталона.
- **HealthMonitor** — ПАЗ: WDT, IHealthCheck-проверки профиля (молчание
  канала при заведомо идущем расходе? частотный анализ помех?).
- **UpdateService** — A/B OTA + bootloop→Safe Mode. Из коробки.
- **StorageService.atomicWrite** — персистентность накопителей показаний
  (критичнейший паттерн ветки: показания НЕ откатываются при панике).
- **TimeService** — NTP+RTC, детерминированный пояс; границы суток/
  месяца/тарифных зон считать только через него. Warn-и NTP-ретраев
  (1–3 на цикл) — документированная норма, не дефект.
- **Мост M2 на мастере** — транзит вверх/вниз к HA из коробки; synth
  offline со стражем гонки (0.5.1-m3). Ветке ничего не нужно: публикации
  уезжают в HA сами при живом HAOS.
- **projects/test_rig** — скелет профиля на той же плате; старт ветки —
  копия test_rig, а не пустой каталог. **weather_gate — второй образец**:
  свежий профиль, прошедший весь путь до прода (декодер эфира, AGC-эпопея,
  discovery в HA) — его структура (App/Config/Ui/HealthChecks) — ближайший
  референс ветки.

## 4. Железные правила (уроки, высечены в коде)

Полный журнал — `docs/МикроОС_5.0_дорожная_карта_кондиций.md`. Здесь —
бьющие по ветке напрямую:

1. **Время — детерминированное** (`gmtime_r(unix + tz*3600)`), RTC = UTC.
2. **printf-формат и аргументы — 1:1, глазами, после КАЖДОЙ правки.**
3. **CFG_READONLY тоже персистится** (показания счётчиков — это
   счётчики!). Накопители — atomicWrite, сброс в NVS «каждые N инкрементов
   или T секунд, что раньше» (паттерн weather_gate, перенять).
4. **ETH.setHostname — ПОСЛЕ ETH.begin.**
5. **Новые поля — в КОНЕЦ схемы**; новые поля JSON-статуса — в конец.
6. **Секретам не место** в JSON/логах/скриншотах.
7. **Панель кэшируется агрессивно**: менял data/web — bump CACHE_NAME
   в sw.js.
8. **Никаких String/std::map/std::vector в горячих путях.** Импульсы и
   счёт — фиксированные POD-буферы, прерывания — только флаги/счётчики,
   тяжёлое — в tick.
9. Хост-тесты — до прошивки, всегда. Новая чистая логика без новых
   тестов не принимается.
10. ПАЗ-пороги и «ручки» — в конфиг с валидацией, не константы. Нормы
    профиля (например, допустимая частота импульсов) — в конфиге профиля,
    НЕ константой ядра (прецедент: коридор dup/pkt шлюза).
11. **app.bin никогда без своей таблицы разделов**; смена разметки =
    erase + flash_full.
12. **Буферы >4 КБ — только в куче/статике, не на стеке.**
13. **Две системы нумерации SPI** (Arduino vs IDF) — актуально, если
    появится внешняя периферия на SPI.
14. **WiFi/BT — отсутствием кода**, «выключатели» запрещены.
15. **CFG_MAX_FIELDS=96 на все профили в сборке** — поля планировать
    заранее (~20–30).
16. **mklittlefs недетерминирован** — доказательство изменения ФС только
    round-trip.
17. **getArg() транзиентен** — копировать в локал сразу.
18. **Веб грузится через 10 с после сети** — гард от бут-шторма, не
    «чинить».
19. **Один файл — одна правка за раз**, никаких параллельных edit-ов.
20. **НОВОЕ (5.8.4): после распаковки кита первая сборка — чистая
    (--clean)** или touch всех исходников: zip восстанавливает старые
    mtime, timestamp-кэш arduino-cli может слинковать протухшие объекты
    (урок 29.08: «undefined reference» при правильных исходниках).
21. **НОВОЕ (HA-discovery, уроки 0.3.8/0.3.9):** discovery публикуется на
    событии MQTT_CONNECTED (ре-анонс на каждой сессии), availability —
    на ядерном LWT `<prefix>/<id>/state`; **единицы ТОЛЬКО каноничные**
    (kWh, m³, W, m³/h — HA молча отбрасывает конфиги с «кВт·ч»/«м³»);
    результат publishRaw учитывать всегда.
22. **НОВОЕ (процессное):** запросы к ядерной ветке — через Issue с
    доказательной цепочкой (образец — репорт о гонке synth offline:
    симптом + механизм + доказательства + предложение). Такие репорты
    чинятся за один заход.

## 6. Аппаратура smart_counter (предложение, финал — с владельцем)

**Плата: WT32-ETH01** (как замок/шлюз: ESP32-classic, 4 МБ, LAN8720,
системная I2C SDA=32/SCL=33). Разметка — как у smart_lock.

Периферия профиля (уточнить по факту объекта в первой сессии):

- импульсные выходы счётчиков (S0, «сухой контакт»/открытый коллектор) —
  сколько каналов реально: электро/вода холод./горяч./газ;
- PCNT-аппаратура ESP32-classic (аппаратные счётчики импульсов) —
  кандидат №1; антидребезг — аппаратный фильтр PCNT + программный;
  глазами проверить разводку: длинные линии → оптроны/подтяжки/гистерезис;
- резерв: UART/RS-485 счётчики (если есть на объекте) — отдельной строкой
  в концепт-ноте.

Пин-план: предложить через ResourceManager, страппинг-пины 0/2/12/15
учитывать, PHY не трогать, input-only 35/36/39 — под импульсные входы
в самый раз (прецедент: GDO у шлюза).

## 7. Архитектура данных (закон самодостаточности)

```
  Счётчики (S0/импульсы) ──> smart_counter (WT32-ETH01)
                                │ сам: счёт (PCNT), тарификация,
                                │ показания (NVS+atomicWrite), история
                                │ (DataLog 6ч/31сут/год), панель, ПАЗ
                                │ провод (MQTT через MqttTransport)
                     ┌──────────┼──────────────┐
                     ▼          ▼              ▼
               home_master   smart_lock?     HA (транзитом через
               (журнал       (расход на      мост M2, когда жив;
                событий)      экран? — опц.)  не нужен для учёта)
```

- **Без сети/мастера/HA:** полный учёт, тарификация, история, панель —
  ничего не деградирует.
- **Офлайн верха:** импульсы не теряются никогда; публикации — outbox/
  retained (выбрать семантику и обосновать в концепт-ноте).
- **Паника/ребут/сбой питания:** показания не откатываются — этому
  отдельный раздел концепт-ноты и отдельные стендовые сценарии
  (дёрганье питания в момент записи!).
- **HA — надстройка:** discovery + сущности по §4.21; решение о
  совместимости топиков с монолитным «Smart Counter» (14 объектов) —
  сохранить или чистая миграция — в концепт-ноте, с обоснованием.

## 8. Первые задачи ветки (предложение ядерной ветки)

Стадии C0–C4; каждая — со своими хост-тестами, сборкой и стендом.
Ворота качества (§9) не пропускаются.

0. **C0. Концепт-нота** (этот этап, до тега v5.8.4 код не пишем):
   ревизия монолита (три списка), манифест пинов, схема конфига `sc.*`,
   HA-сущности + решение по топикам, раздел самодостаточности,
   персистентность показаний. Рецензия ядерной веткой — обязательна.
1. **C1. Скелет + импульсный ввод.** Копия test_rig →
   projects/smart_counter; boardId WT32-ETH01; пин-план через
   ResourceManager; ScPulseCore (чистая логика: счёт, антидребезг,
   окна) + хост-тесты (вектора: дребезг, залипание, переполнения).
   Стенд: генератор импульсов/кнопка, сверка с эталонным подсчётом.
2. **C2. Учёт и персистентность.** Показания+тарифы, NVS-сбросы по
   паттерну шлюза, atomicWrite; хост-тесты математики тарификации
   (границы суток/тарифных зон, переносы). Стенд: 24 ч с дёрганьем
   питания в случайные моменты — показания не откатываются ни на импульс.
3. **C3. Профиль по руководству.** SmartCounterApp/Config/Ui: схема
   конфига, панель с uPlot (расход), телеметрия, discovery в HA,
   IHealthCheck-и. Приёмка: «HA выключен — учёт и панель полны».
4. **C4. Интеграции + soak.** Публикации вверх (мост M2), сверка с
   монолитным Smart Counter в HA (параллельная работа на переходный
   период), soak 72 ч минимум с heap-watermark и журналом ПАЗ.

- **Ворота 1 — хост-тесты:** норма на 31.08 — ядро 43351 PASS,

## 10. Рабочий процесс (не ломать)

- Код ядра — в `src/`, профиль — в `projects/smart_counter/`; ядро
  профилем не правится. Запросы на ядро — Issue #1, доказательная
  цепочка (правило 22).
- Общение по проекту: Issue #3 «smart_counter» (техническая линия
  ветки); Issue #2 — доска актуальности версий (шапку обновляет владелец
  по факту выдач).
- Пины — через ResourceManager (конфликт = лог CONFLICT).
- Чистая логика отделяется от железа (паттерн *Core.h): всё, что можно
  посчитать без Arduino, считается без Arduino и тестируется на хосте.
- Хост-тесты зелёные → сборка → верификация ФС → стенд → запись в
  дорожную карту. Per-file доставка: rm + cp.tmp + sync + mv + cmp;
  деревья — diff -r MATCH.
- Каждый инцидент в поле — урок: комментарий в код + (обычно) тест +
  строка в дорожной карте.
- Секреты не покидают устройство. Восстановление из бэкапа — только
  осознанно, «без всяких предупреждений, понимая что делаешь».
- Стиль общения с автором: русский, по делу, уроки нумеруем и помним.

**Статус:** рабочий журнал векторов профиля. Эталон для `host/tests.cpp`
(92 PASS / 0 FAIL на 04.09.2026, стадия C1).

## Источники и доверие

| Источник | Что берём | Доверие |
|---|---|---|
| Продакшн-монолит v4.4.2 (годы в работе) | CRC16, bcdToF, байтовые смещения ответов 0x63/0x27/0x2F/0x37 | Высокое — эталон для host-тестов |
| Каталог CRC (CRC-16/MODBUS) | Контрольный вектор `0x4B37` | Высокое |
| `Журнал Меркурий-206.pdf` | Только список возможностей прибора (журналы 64/256, профиль 30 мин × 6 мес, ПКЭ) | **Низкое** — это пересказ ответов ИИ, содержит прямые ошибки |
| Стенд C1 с реальным счётчиком | Финальная сверка всех смещений и длин | Обязательна |

**Известные ошибки «Журнала» (не копировать в код/тесты):**
1. Адрес для SN 12345678 указан как `0C 23 45 67` — правильно `12 34 56 78` (сам журнал ниже даёт верно).
2. Пример напряжения «байты `02 31` → 231.0 В» — с его же функцией деления на 10 это 23.1 В.
   Правильный кадр для 231.0 В — `23 10` (U передаётся ×10 четырьмя BCD-цифрами).
3. «Ответ 0x63 — 12 байт» противоречит его же байтовой сетке (байты 0..14 = 15 байт).
   Монолит (продакшн) парсит U2+I2+P3 → полный кадр 14 байт. Сверить на стенде.
4. Формулировка «полином 0x8005» и одновременно код с `0xA001` — это один и тот же
   полином в прямой и реверсивной записи; противоречия нет, но формулировка путает.

## Группа 1. CRC16 (MODBUS, init 0xFFFF, полином 0xA001)

| Вход | Ожидание | Комментарий |
|---|---|---|
| ASCII `123456789` | `0x4B37` | контрольный вектор каталога CRC — вычислено и подтверждено |
| `12 34 56 78 63` | `0x0A10` (в кадре: `10 0A`, lo first) | запрос мгновенных |
| кадр + свой CRC | `0x0000` | резидуальный трюк парсера ответов — подтверждён вычислением |

## Группа 2. Кадры запросов (SN = 12345678 → адрес `12 34 56 78`)

Все кадры ниже **сгенерированы функцией `scm::buildRequest` и проверены CRC-резидуалом**.

| Команда | Полный кадр (hex) |
|---|---|
| 0x00 тест связи | `12 34 56 78 00 50 23` |
| 0x63 мгновенные | `12 34 56 78 63 10 0A` |
| 0x27 энергия, текущие | `12 34 56 78 27 00 38 CC` |
| 0x27 энергия, на начало суток | `12 34 56 78 27 0F 78 C8` |
| 0x21 время | `12 34 56 78 21 90 3B` |
| 0x2F серийник | `12 34 56 78 2F 11 FF` |
| 0x37 профиль за 05.03.26 | `12 34 56 78 37 00 05 03 26 84 25` |

Негативные векторы: любой кадр с одним инвертированным битом → `isFrameValid == false`;
кадр с чужим кодом команды в байте 4 → `false`; усечённый кадр (< min len) → `false`.

## Группа 3. bcdToF / bcdToU32 (алгоритм продакшн-монолита)

| Входные байты | Делитель | Ожидание |
|---|---|---|
| `23 10` | 10 | 231.0 (напряжение) |
| `15 20` | 100 | 15.20 (ток) |
| `00 35 00` | 100 | 35.00 (НЕ 3500 — ошибка «Журнала», поймана тестом C1) |
| `35 00 00` | 100 | 3500 (мощность, Вт) |
| `00 12 34 56` | 100 | 1234.56 (энергия, кВт·ч) |
| `99 99 99 99` (bcdToU32) | — | 99999999 (граница 8 цифр) |
| `00 00 00 01` (bcdToU32) | — | 1 |

## Группа 4. Разбор ответов (синтетические кадры с валидным CRC)

Собираются в тесте через `buildRequest`-подобную обёртку (addr + cmd + payload + CRC),
после чего подаются в парсеры. Ожидания:

- `parseInstant`: payload `23 10 | 15 20 | 00 35 00` → 231.0 В / 15.20 А / 3500 Вт.
- `parseEnergyTotal`: payload T1 `00 12 34 56` + T2..T4 нули → 123456 (сотые кВт·ч) = 1234.56 кВт·ч.
- `parseSerial`: payload по сетке монолита (байты [2..7] ответа) `12 34 56 78` + дата выпуска →
  адрес `12 34 56 78`, строка SN `"12345678"`; с ведущими нулями `00 00 12 34` → `"1234"`.
- `parseProfile`: пары big-endian `00 64` (10.0 Вт) ×N, терминатор `FF FF` → N точек;
  кадр без терминатора → разбор до конца данных; битый CRC → −1.

## Группа 5. ScPulseCore (host-тесты)

- `debounceAccept`: импульс через 199 мс после предыдущего → отклонён; через 201 мс → принят;
  wrap счётчика микросекунд → корректно.
- `isNoiseRate`: 60 принятых импульсов за 1 с при max_hz=50 → шум; 40 за 1 с → норма.
- `pulsesToM3`: 12345 имп при 1 имп/л → 12.345 м³; imp_per_l=0 → 0 (защита от деления).
- `LeakDetector`: 6 «мокрых» часов со средним ≥ threshold → событие 1 (LEAK);
  затем сухой час → событие 2 (CLEARED); микропоток ниже threshold 24 часа → тревоги нет.
- `emaUpdate`: первый отсчёт 4.1 при prev=0 → 4.1 (без «сползания»); alpha=0.15 сходится.

## Группа 6. ScBillingCore (host-тесты)

- `computeBill`: total 100.0, base 80.0, price 6.5 → 20.0 м³ / 130.0; base > total → 0.
- `isReportDue`: reportDay=24; сегодня 24-е, lastYmd=вчера → true; повторный вызов в тот же
  день → false (урок: lastResetDay в RAM у монолита давал повторный сброс после ребута).
- catch-up: lastYmd=20-е, сегодня 26-е → true; `catchupBase`: снимок 99.5 ≤ total 101.2 → база 99.5;
  снимок невалиден → база = текущие показания.
- `filterWarningStep`: remaining ≤ 0 → событие 1 ровно один раз; после замены → событие 2.

## Что НЕ покрыто векторами (только стенд C1)

1. Точная длина/сетка ответа 0x63 на реальном приборе (расхождение журнала и монолита).
2. Поведение широковещательного адреса `00 00 00 00` при >1 приборе на шине (у нас шина точка-точка).
3. Реальные тайминги ответа при 9600 8N1 и влияние паузы 50–100 мс между кадрами.
4. Сценарий «ребут при живом RS-485-трафике» — план стенда C1, пункт из §10 концепт-ноты.

# ПАСПОРТ КИТА — МикроОС 5.8.8 / smart_lock 0.5.15 «Двухполевая версия OTA»

Дата сборки: 08.09.2026
Основание: одобрено владельцем 08.09.2026.

## Что в ките

- `micro-os-5/src/` — ядро 5.8.8 целиком (структура репозитория).
- `micro-os-5/projects/smart_lock/` — профиль 0.5.15 целиком (вкл. data/).
- `бинарники/` — firmware.bin + littlefs.bin + version.json (с полем
  `profile_version`).

## Отвязка шкалы профиля от ядра (5.5.15 → 0.5.15)

Старая нумерация замка (5.5.x) — наследие времён, когда версия профиля
совпадала с версией ядра. С 5.8.8 ядро и профиль — две независимые шкалы.
Решение владельца 08.09.2026: «оставить 5.15, а в начале добавить 0 —
будем видеть, что это профиль, но прошедший определённый путь в своём
развитии». Ведущий 0 = версия ПРОФИЛЯ, хвост 5.15 — сохранённая история.

ВАЖНО для сверки OTA: 0.5.15 МЛАДШЕ 5.5.15 по semver. Поскольку на флоте
замок с 5.5.15 (ядро 5.8.7), переход на 5.8.8+0.5.15 срабатывает по ветке
«ядро новее» — обновление предложит по ядру, профиль придёт в комплекте.
Внутри 5.8.8 сравнение профилей дальше пойдёт по новой шкале (0.5.16,
0.6.0…) без изъянов. Одноразовый переход.

## Ядро 5.8.8 — что изменилось (общее для флота)

Двухполевая версия OTA: сверка «ядро новее ИЛИ (ядро равно И профиль
новее)», даунгрейд по любому полю не предлагается. В .bin две метки:
`MICROOS|5.8.8|END` и `MICROOS|5.8.8|0.5.15|END` (проверено grep'ом).
Полный список изменений ядра — в паспорте кита мастера.

## Профиль smart_lock 0.5.15

- `MICROOS_PROFILE_VER 0.5.15` в шапке SmartLockApp.h — единственный
  источник версии профиля; getVersion() отдаёт тот же макрос строкой.
- init(): `setProfileVersion(getVersion())` + boot-лог `bin tag: …`.
- Панель: карточка OTA показывает «ядро · профиль», различает
  «Доступно обновление ядра» / «…профиля».

## Приёмка

Обновление с мастера (тройка из `бинарники/` этого кита), конфиг из
бэкапа. Панель: «Текущая прошивка 5.8.8 · профиль 0.5.15». Boot-лог:
`bin tag: MICROOS|5.8.8|0.5.15|END`.

   # ПАСПОРТ КИТА — МикроОС 5.9.1 / smart_lock 0.5.16 «Сторож сети»

Дата сборки: 10.09.2026
Основание: Issue ветки weather_gate «два дефекта автономности (CC1101 +
сетевой стек)», 10.09.2026; решения владельца: net.dead_reboot=false
по умолчанию (осторожный путь), окно 10 минут, свёртка однотипных логов,
расширение аудита.

## Что в ките

- `micro-os-5/src/` — ядро 5.9.1 целиком (структура репозитория).
- `micro-os-5/projects/home_master/` — профиль 0.8.0 целиком (вкл. data/).
- `бинарники/` — firmware.bin + littlefs.bin + version.json.

## Ядро 5.9.1 — автономность и наблюдаемость

- **Сторож мёртвой сети.** Если линк и IP живы, но N минут нет ни одного
  успешного ping шлюза и нет MQTT-сессии — сеть признаётся мёртвой:
  Error в лог, публикация ошибки `NET_DEAD`, событие `NET_EVENT_DEAD`
  (зеркалится в MQTT), запись в аудит. Ребут — ТОЛЬКО если включить
  новое поле `net.dead_reboot` (по умолчанию ВЫКЛ — осторожный путь).
- **Новые поля конфига (группа «Сеть», в КОНЕЦ схемы):**
  - `net.dead_reboot` (BOOL, по умолчанию false) — программная
    перезагрузка при мёртвой сети;
  - `net.dead_min` (UINT, 3–120, по умолчанию 10) — минут молчания
    сети до вердикта «мертва».
- **Backoff на сбой создания ping-сессии.** Раньше при исчерпании
  сокетов lwIP попытка повторялась каждые ~500 мс бесконечно — спам
  `esp_ping_new_session(267): create socket failed: -1` часами (логи
  инцидента на шлюзе). Теперь при сбое создания сессии дедлайн
  переносится, плюс диагностический счётчик `_pingCreateFailStreak`
  (1-й и каждый 20-й сбой — строка со свободной кучей).
- **Свёртка однотипных логов.** Подряд идущие идентичные строки
  (уровень+тег+тело) схлопываются в одну с суффиксом «(×N)» — журнал
  перестаёт заспамливаться криками, история читаема.
- **Аудит: +поле `hp`** — свободная куча в КБ на момент события; новый
  тип события `NET_DEAD`.
- **CC1101 (для шлюза):** принудительный аппаратный сброс по SPI
  (ручной SRES: ожидание CHIP_RDYn на MISO, строб 1 МГц, readback
  PARTNUM/VERSION с FAIL-логом) — восстановление после тёплой
  перезагрузки без передёргивания питания; сторож MarcState раз в 60 с
  (выход из RX → полная переустановка приёма, счётчик rfStateFixes).

## Профиль smart_lock 0.5.16

Без изменений относительно 0.5.16 кита 5.9.0 — пересобран на ядре 5.9.1.
Метка в бинарнике: `MICROOS|5.9.1|0.5.16|END` (+ короткая `MICROOS|5.9.1|END`).

## Приёмка

1. Мастер уже прошит первым вручную (кит 5.9.1 / 0.8.0).
2. Замок — OTA с мастера этим китом (fw+FS парой).
3. Шлюз — отдельное уведомление ветке: ядро 5.9.1 отвечает на оба
   пункта их Issue, профиль трогать не нужно.
4. Проверка на стенде: выдернуть патч-корд из коммутатора на 10+ мин
   (или отключить upstream) → в журнале диагностика ping-create-fail
   со свёрткой, по истечении окна — `NET_DEAD` в логе/аудите/MQTT,
   устройство НЕ ребутается (дефолт). Вернуть сеть — RECOVERED штатно.

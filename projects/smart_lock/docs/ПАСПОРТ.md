# ПАСПОРТ КИТА — МикроОС 5.8.8 / smart_lock 0.5.15 «Двухполевая версия OTA»

Дата сборки: 08.09.2026
Основание: одобрено владельцем 08.09.2026.

## Что в ките

- `micro-os-5/src/` — ядро 5.8.8 целиком (структура репозитория).
- `micro-os-5/projects/smart_lock/` — профиль 0.5.15 целиком (вкл. data/).
- `бинарники/` — firmware.bin + littlefs.bin + version.json (с полем
  `profile_version`).

## Отвязка шкалы профиля от ядра (5.5.15 → 0.5.15)

Старая нумерация замка (5.5.x) — наследие времён, когда версия профиля
совпадала с версией ядра. С 5.8.8 ядро и профиль — две независимые шкалы.
Решение владельца 08.09.2026: «оставить 5.15, а в начале добавить 0 —
будем видеть, что это профиль, но прошедший определённый путь в своём
развитии». Ведущий 0 = версия ПРОФИЛЯ, хвост 5.15 — сохранённая история.

ВАЖНО для сверки OTA: 0.5.15 МЛАДШЕ 5.5.15 по semver. Поскольку на флоте
замок с 5.5.15 (ядро 5.8.7), переход на 5.8.8+0.5.15 срабатывает по ветке
«ядро новее» — обновление предложит по ядру, профиль придёт в комплекте.
Внутри 5.8.8 сравнение профилей дальше пойдёт по новой шкале (0.5.16,
0.6.0…) без изъянов. Одноразовый переход.

## Ядро 5.8.8 — что изменилось (общее для флота)

Двухполевая версия OTA: сверка «ядро новее ИЛИ (ядро равно И профиль
новее)», даунгрейд по любому полю не предлагается. В .bin две метки:
`MICROOS|5.8.8|END` и `MICROOS|5.8.8|0.5.15|END` (проверено grep'ом).
Полный список изменений ядра — в паспорте кита мастера.

## Профиль smart_lock 0.5.15

- `MICROOS_PROFILE_VER 0.5.15` в шапке SmartLockApp.h — единственный
  источник версии профиля; getVersion() отдаёт тот же макрос строкой.
- init(): `setProfileVersion(getVersion())` + boot-лог `bin tag: …`.
- Панель: карточка OTA показывает «ядро · профиль», различает
  «Доступно обновление ядра» / «…профиля».

## Приёмка

Обновление с мастера (тройка из `бинарники/` этого кита), конфиг из
бэкапа. Панель: «Текущая прошивка 5.8.8 · профиль 0.5.15». Boot-лог:
`bin tag: MICROOS|5.8.8|0.5.15|END`.

   # ПАСПОРТ КИТА — МикроОС 5.9.1 / smart_lock 0.5.16 «Сторож сети»

Дата сборки: 10.09.2026
Основание: Issue ветки weather_gate «два дефекта автономности (CC1101 +
сетевой стек)», 10.09.2026; решения владельца: net.dead_reboot=false
по умолчанию (осторожный путь), окно 10 минут, свёртка однотипных логов,
расширение аудита.

## Что в ките

- `micro-os-5/src/` — ядро 5.9.1 целиком (структура репозитория).
- `micro-os-5/projects/home_master/` — профиль 0.8.0 целиком (вкл. data/).
- `бинарники/` — firmware.bin + littlefs.bin + version.json.

## Ядро 5.9.1 — автономность и наблюдаемость

- **Сторож мёртвой сети.** Если линк и IP живы, но N минут нет ни одного
  успешного ping шлюза и нет MQTT-сессии — сеть признаётся мёртвой:
  Error в лог, публикация ошибки `NET_DEAD`, событие `NET_EVENT_DEAD`
  (зеркалится в MQTT), запись в аудит. Ребут — ТОЛЬКО если включить
  новое поле `net.dead_reboot` (по умолчанию ВЫКЛ — осторожный путь).
- **Новые поля конфига (группа «Сеть», в КОНЕЦ схемы):**
  - `net.dead_reboot` (BOOL, по умолчанию false) — программная
    перезагрузка при мёртвой сети;
  - `net.dead_min` (UINT, 3–120, по умолчанию 10) — минут молчания
    сети до вердикта «мертва».
- **Backoff на сбой создания ping-сессии.** Раньше при исчерпании
  сокетов lwIP попытка повторялась каждые ~500 мс бесконечно — спам
  `esp_ping_new_session(267): create socket failed: -1` часами (логи
  инцидента на шлюзе). Теперь при сбое создания сессии дедлайн
  переносится, плюс диагностический счётчик `_pingCreateFailStreak`
  (1-й и каждый 20-й сбой — строка со свободной кучей).
- **Свёртка однотипных логов.** Подряд идущие идентичные строки
  (уровень+тег+тело) схлопываются в одну с суффиксом «(×N)» — журнал
  перестаёт заспамливаться криками, история читаема.
- **Аудит: +поле `hp`** — свободная куча в КБ на момент события; новый
  тип события `NET_DEAD`.
- **CC1101 (для шлюза):** принудительный аппаратный сброс по SPI
  (ручной SRES: ожидание CHIP_RDYn на MISO, строб 1 МГц, readback
  PARTNUM/VERSION с FAIL-логом) — восстановление после тёплой
  перезагрузки без передёргивания питания; сторож MarcState раз в 60 с
  (выход из RX → полная переустановка приёма, счётчик rfStateFixes).

## Профиль smart_lock 0.5.16

Без изменений относительно 0.5.16 кита 5.9.0 — пересобран на ядре 5.9.1.
Метка в бинарнике: `MICROOS|5.9.1|0.5.16|END` (+ короткая `MICROOS|5.9.1|END`).

## Приёмка

1. Мастер уже прошит первым вручную (кит 5.9.1 / 0.8.0).
2. Замок — OTA с мастера этим китом (fw+FS парой).
3. Шлюз — отдельное уведомление ветке: ядро 5.9.1 отвечает на оба
   пункта их Issue, профиль трогать не нужно.
4. Проверка на стенде: выдернуть патч-корд из коммутатора на 10+ мин
   (или отключить upstream) → в журнале диагностика ping-create-fail
   со свёрткой, по истечении окна — `NET_DEAD` в логе/аудите/MQTT,
   устройство НЕ ребутается (дефолт). Вернуть сеть — RECOVERED штатно.

   # ПАСПОРТ КИТА — МикроОС 5.9.6 / smart_lock 0.5.18 «Wiegand: таймаут кадра»

**Дата сборки:** 21.10.2026
**Основание:** полевой лог 21.10 (новое железо замка, считыватель ST-PR012EHM-BK
за изолятором B1212S-2WR3 + AdUM1200): при подносе карты монитор показывал пары
`wiegand noise, bits=N` с интервалом ~50 мс, и **каждая пара в сумме давала
ровно 26** (13+13, 1+25, 17+9, 11+15, 14+12, 18+8, 22+4, 2+24). Диагноз:
считыватель шлёт полный кадр W26, все биты доезжают (развязка исправна), но
пауза посреди кадра превышает таймаут кадра драйвера (25 мс — стандарт
монолита v2.5.0). Драйвер честно режет кадр на два фрагмента, оба уходят
в шум. Переключатель W26/W34 на считывателе картины не менял — и не мог:
декодер определяет формат по длине кадра автоматически.

Ядро 5.9.6 **БЕЗ ИЗМЕНЕНИЙ** — только профиль замка. Перешивается ТОЛЬКО
замок (.51), мастер и шлюз не трогаем.

## Что изменено (профиль 0.5.18)

1. **SmartLockConfig.cpp** — новое поле В КОНЦЕ схемы, группа «Считыватель»:
   - `lock.wg_frame_ms` (UINT, 25–1000, **по умолчанию 100 мс**) — таймаут
     кадра Wiegand. 100 мс перекрывает межфрагментную паузу (~50 мс) и не
     сливает два подноса подряд (между карточками всегда секунды).

2. **WiegandDriver.h** (каталог профильной периферии, НЕ ядро) — публичный
   сеттер `setFrameTimeoutMs(uint32_t)`: смена таймаута на лету, без
   переустановки железа (таймаут — просто сравниваемая величина в ISR/poll).

3. **SmartLockApp.cpp** — применение значения в `init()` (НЕ в
   registerDrivers: значения схемы поднимает ConfigService::init, который
   бежит после регистрации драйверов — урок 5.8.4-pre5). В бут-логе строка
   `wiegand frame timeout: 100 ms` — контроль применения.

4. **SmartLockApp.cpp/.h** — лог шума с суммой бит за окно 500 мс:
   `wiegand noise, bits=13 (окно 500 мс: 26)` — фрагменты одного кадра
   видны сразу, не нужно складывать в уме.

## Состав

- `micro-os-5/` — исходники (ядро 5.9.6 + профиль smart_lock 0.5.18),
  структура репозитория.
- `бинарники/firmware.bin` — 1 116 512 Б, метки `5.9.6` (×3) и `0.5.18` (×2)
  grep-проверены.
- `бинарники/littlefs.bin` — 1 441 792 Б, шьётся парой с прошивкой.
- `бинарники/version.json` — двухполевой манифест OTA.

## Прошивка (WT32-ETH01, как всегда парой)

- firmware.bin → 0x10000
- littlefs.bin → 0x290000

## Контроль после прошивки

1. Бут-лог: `wiegand frame timeout: 100 ms` и статус `5.9.6·0.5.18`.
2. Поднести карту: вместо пары noise — событие карты, ключ появляется
   в веб-интерфейсе (вкладка чтения карты), можно привязывать.
3. Если вдруг всё ещё noise — смотреть «окно 500 мс»: сумма 26/34 при
   таймауте 100 мс будет означать, что пауза ещё длиннее; тогда
   `lock.wg_frame_ms` поднимается прямо из веба, без пересборки
   (применение — после перезагрузки).

## Откат

Кит 5.9.6·0.5.17 «лимит полей» остаётся в выдаче. Поле `lock.wg_frame_ms`
новое — после отката просто игнорируется старой схемой.





# ПАСПОРТ КИТА — МикроОС 5.9.6 / smart_lock 0.5.19 «веб-проходы + снимок базы»

**Дата сборки:** 22.10.2026
**Основание:** два решения владельца от 22.10.2026:
1. Персонифицированные веб-открытия должны идти в счётчик проходов жильца
   (наблюдение: вход по карте счётчик двигает, вход через веб-панель — нет).
2. На мастере — журнал событий доступа + снимок базы пользователей замка
   (утверждённый объём: «журнал + снимок базы»).

Ядро 5.9.6 **БЕЗ ИЗМЕНЕНИЙ** — только профиль замка. Платформа сборки
esp32:esp32 **3.3.12** (эталон с 21.10). Перешивается ТОЛЬКО замок (.51).

## Что изменено (профиль 0.5.19)

1. **Счётчик проходов веб-открытий** (SmartLockApp.cpp, CardStore.h/.cpp).
   Диагноз наблюдения: вердиктный путь карты (`grantAccess`) статистику
   вёл, а `remoteOpen()` (веб/MQTT) — нет, это была унаследованная
   семантика монолита «проходы = только по ключу». Теперь: при
   веб-открытии с именем жильца (сессия по ПИНу или серверный фолбэк)
   выполняется `findByName → recordUse` — счётчик и `lastUse` двигаются.
   Не считаются, осознанно:
   - «Админ (веб)» — такого имени в базе нет, findByName вернёт nullptr;
   - MQTT-открытия — канал автоматики, не человека;
   - анонимный веб при выключенном `lock.user_pin_enabled` — некому
     приписывать.

2. **Эндпоинт `GET /api/dev/lock/users/export`** (SmartLockUi.cpp) —
   потоковая отдача `users.json` через `streamFileDownload` (файл не
   грузится в RAM). **Только админ-токен**: в файле веб-ПИНы жильцов.
   Это половина контура «снимок базы на мастере»: вторая половина —
   опрос этого эндпоинта мастером (BackupService, в плане 0.9.5).
   Контур журнала событий доступа уже живой: ядро зеркалирует
   ACCESS_GRANTED/DENIED в `microos/<id>/events/*`, а JournalService
   мастера слушает `microos/+/events/#` — события доступа замка пишутся
   в журнал парка сегодняшним ПО.

## Состав

- `micro-os-5/` — исходники (ядро 5.9.6 + профиль smart_lock 0.5.19).
- `бинарники/firmware.bin` — 1 120 480 Б, метки `5.9.6` (×3) и `0.5.19` (×2)
  grep-проверены.
- `бинарники/littlefs.bin` — 1 441 792 Б (веб-морда не менялась; md5
  отличается от 0.5.18 — у mklittlefs недетерминированные метаданные,
  содержимое файлов идентично).
- `бинарники/version.json` — двухполевой манифест OTA.

## Прошивка (WT32-ETH01, парой)

- firmware.bin → 0x10000
- littlefs.bin → 0x290000

## Контроль после прошивки

1. Статус: `5.9.6 · 0.5.19`.
2. Войти жильцом в веб-панель (ПИН), открыть замок — «Проходов» у этого
   пользователя увеличивается на 1. Открытие кнопкой «Открыть» от админа
   счётчики не двигает.
3. `curl -H "X-Auth-Token: <админ>" http://10.146.75.51/api/dev/lock/users/export`
   — отдаётся users.json; без токена — 401 admin_required.

## Откат

Кит 5.9.6·0.5.18 остаётся в выдаче. Совместимость полная (схема конфига
не менялась, users.json не менялся).

# МикроОС 5.0 — доведение до «максимальных кондиций»
## Предложения по построению и оптимизации (за рамками базовой архитектуры)

Базовая идеология утверждена: единая платформа WT32-ETH01 + DS3231 + MAX803S → неизменное
ядро; периферия → профили. Ниже — 15 предложений системного уровня, сгруппированных
по пяти направлениям. Приоритеты: **P0** — делать в первую очередь (дешёвые,
закрывают реальные риски), **P1** — вторая волна, **P2** — стратегические.

---

## A. Живучесть устройства «в поле»

### A1. Защита от bootloop + A/B OTA — **P0**
Монолит v2.5.0 имеет Safe Mode по кнопке, но нет защиты от циклической
перезагрузки после неудачной прошивки.
- **Bootloop-счётчик** в RTC RAM: kernel инкрементирует на старте, сбрасывает
  после 60 секунд стабильной работы. 3 подряд → автоматический Safe Mode
  (сеть по DHCP, минимум модулей) — без участия человека с кнопкой.
- **A/B разделы OTA** (штатная возможность ESP32): новая прошивка грузится в
  неактивный раздел, первый старт помечается `pending`; если до отметки
  «работаю» дело не дошло — загрузчик сам откатывается на предыдущий раздел.
  Это бесплатно в ESP-IDF, нужно только задействовать.
- **Маркер совместимости FW/FS**: прошивка и образ LittleFS несут `min_fs_version`
  / `min_fw_version` — UpdateService отказывает в несовместимой паре до записи.

### A2. Реестр ресурсов (ResourceManager) — **P0**
Сегодня ничто не мешает двум профилям занять один GPIO или I2C-адрес.
- Ядро ведёт таблицу занятых ресурсов: GPIO, UART, I2C-адреса, NVS-namespace,
  диапазоны событий. BaseProfile регистрирует свои (PHY 16, I2C 32/33, 0x68).
- `describeHardware()` профиля **валидируется при старте**: конфликт пина →
  модуль не стартует, в лог — явная ошибка «GPIO15 занят: lock.relay vs …».
- Бонус: автоматически генерируемый документ «карта занятых пинов» по всем
  профилям — из того же реестра.

### A3. Деградация по уровням (Degraded Mode) — **P1**
Формализовать то, что в smart_lock сделано стихийно (джампер GPIO35):
- Три уровня: FULL (сеть+MQTT) → LOCAL_NET (только веб/API) → AUTONOMOUS
  (только драйверы и бизнес-логика). Каждый модуль объявляет в `describe()`,
  на каком минимальном уровне он работает.
- Падение сети переводит систему на уровень ниже **событиями**, без ребута;
  восстановление — наоборот. Джампер принудительно фиксирует AUTONOMOUS.

## B. Наблюдаемость и диагностика

### B1. Системные метрики как телеметрия — **P0**
HealthMonitor уже собирает heap/температуру — превратить в данные:
- TelemetryService регистрирует системные каналы: `sys.free_heap`,
  `sys.min_heap`, `sys.cpu_temp`, `sys.event_queue_depth`, `sys.tick_overruns`,
  `sys.event_dropped`.
- В HA — автоматические графики здоровья каждого контроллера. Утечка памяти
  или шторм событий видны **до** аварии, а не по ребуту.

### B2. Бюджеты времени исполнения — **P1**
- Kernel замеряет длительность `tick()` и `onEvent()` каждого модуля;
  превышение бюджета (например, 50 мс) → warning в лог с именем модуля.
- Медленный модуль перестаёт быть «невидимой» причиной WDT-ребутов.

### B3. Аудит-лог административных действий — **P1**
- Отдельный защищённый журнал: кто (роль), что (смена конфига, OTA, удаление
  ключа, сброс ПАЗ), когда. Не очищается кнопкой «Очистить журнал».
- Для СКУД это требование, а не опция.

## C. Безопасность

### C1. Provisioning вместо дефолтного пароля — **P0**
В монолите зашит дефолтный хэш админа — это backdoor на всех устройствах.
- Первый старт (или сброс): устройство требует задать пароль через веб до
  начала работы; до provisioning доступна только страница установки.
- Пароль существует только как хэш + соль; хэш никогда не покидает устройство
  (уже так — сохранить принцип).

### C2. Подпись прошивок и шифрование секретов — **P2**
- **Secure Boot v2 + Flash Encryption** (ESP32): прошивка не подписанная
  ключом вендора не стартует; NVS с PIN-хэшами и MQTT-паролем не читается
  при физическом доступе к flash.
- Тяжёлая мера, внедрять на этапе серийного производства.

### C3. Rate-limiting и защита эндпоинтов — **P1**
- В монолите есть CSRF и сессии; добавить: счётчик неудачных попыток
  авторизации с экспоненциальной паузой (уже есть в UserManager 5.0-концепте),
  лимит запросов/с на IP, блокировка `/api/auth` после N провалов.
- Rate-limit на `postEvent` — защита шины от шторма из сети.

## D. Качество производства (DevEx / QA)

### D1. Conformance-тест профиля — **P0**
Профиль — публичный контракт; нужен автоматический экзамен:
- Скрипт проверяет новый профиль: все обязательные провайдеры зарегистрированы,
  диапазон событий не пересекается с реестром, нет прямых вызовов железа
  в обход драйверов (grep-запреты: `digitalWrite`, `Wire.` в `profiles/*` вне
  манифеста), каждый `addRoute` имеет роль, каждый виджет — существующий
  эндпоинт.
- Запускается в CI: профиль, не прошедший conformance, не собирается.

### D2. Host-тесты бизнес-логики — **P1**
- Бизнес-логика профилей (машина доступа, расписания) не зависит от Arduino —
  выносится в чистый C++ и гоняется под PlatformIO `native` на ПК:
  подаём событие `CARD_READ` → проверяем вердикт.
- Драйверы заменяются mock-реализациями по тем же интерфейсам.

### D3. Автогенерация документации из кода — **P1**
- `/api/docs` уже агрегирует `addRoute(..., .desc=...)` — довести до
  OpenAPI-файла при сборке.
- Из `ConfigField[]` — таблица настроек профиля в Markdown.
- Из реестра событий — карта событий. Документация не устаревает никогда,
  потому что генерируется из единственного источника истины.

### D4. Бюджеты ресурсов в CI — **P2**
- При сборке: контроль flash/RAM по бюджету (например, ядро ≤ 60% flash,
  профиль ≤ 15%); превышение — сборка падает. «Расползание» прошивки
  останавливается на коммите, а не в поле.

## E. Экосистема (несколько контроллеров)

### E1. Идентичность устройства — **P0**
- Device ID = `profileId + efuse MAC` (как clientId в монолите) — публикуется
  в MQTT discovery, в ответ `/api/system`, метка на корпус.
- Это основа fleet-операций: обновить «все smart_lock до 5.1», найти
  устройство в сети (mDNS `_microos._tcp`).

### E2. Межустройственные события — **P2**
- Стандартный «мост» событий через MQTT: событие шины с флагом `GLOBAL`
  публикуется в `ecosystem/<event>`; контроллеры-подписчики получают его как
  локальное. Пример: smart_lock `DOOR_ALARM` → smart_light мигает в коридоре.
- Ядро маршрутизирует, профили не знают друг о друге.

### E3. Экспорт/импорт конфигурации устройства — **P1**
- Один файл: системные + профильные поля + список драйверов (без секретов —
  отдельный защищённый раздел). Сценарии: клонирование контроллера,
  замена сгоревшего устройства за 5 минут, бэкап перед OTA.

## Релиз 5.2.0 (ёмкость базы 250 ключей)

Реализован сценарий «200–250 из анализа 5.1.2» — для малого офиса, по
запросу пользователя. Но НЕ тем путём, что планировался: первый вариант
(heap-кэш 25 КБ + heap-буфер сериализации 55 КБ = 80 КБ) НЕ ПОДНЯЛСЯ бы —
живых свободных ~69 КБ (48 рабочих + 21 освобождённый из BSS), аллокация
буфера упала бы в fallback на 32 записи. Поймано пересчётом бюджета ДО
прошивки. Правильное решение — убрать мегабуфер из уравнения совсем:

| Изменение | Суть |
|---|---|
| **Потоковая запись** | carddb::serializeOne (выделена из serialize — источник формата один); save() пишет .tmp по записи (стековый кусок 320 Б) + commitTemp (openTemp/commitTemp — новый стриминг-API StorageService, атомарность rename прежняя) |
| **Потоковое чтение** | loadFromFile: скобочный сканер вырезает объекты по одному (640 Б стек) + carddb::parseOne (выделен parseObject — общий с parse, источник разбора один); sanitizeName режет '{'/'}' — иначе скобки в имени разрушили бы сканер |
| **RAM-бюджет** | Постоянного буфера сериализации НЕТ совсем; постоянный расход — только кэш 25 КБ heap (fallback-карман 32 записи). BSS 117→88 КБ; свободный heap в рантайме ~52 КБ (было 48) — стало ЛУЧШЕ, чем до роста ёмкости |
| **NVS-зеркало** | Потолок 16 КБ: крупная база (>~75 «тяжёлых» записей) — политика ПРОПУСКА с Info-логом (не воем Error); буфер зеркала — временный alloc/free на редкую операцию. Кнопка «Сохранить бэкап в NVS» в этом режиме пишет users.json.bak и панель честно докладывает режим |
| **uint8_t** | count/idx/capacity держат 250 (потолок типа 255) — без перепроектирования |

Уроки: (а) пересчёт бюджета RAM до прошивки дешевле боевого fallback'а;
(б) «буфер на всю коллекцию» — антипаттерн масштабирования: стриминг по
записи снимает потолок без жертв; (в) факторизация serializeOne/parseObject
— единый источник формата, старые тесты круговой serialize/parse сторожат
эквивалентность бесплатно.

Host-тесты: 998 PASS, 0 FAIL (+17: serializeOne≡serialize, parseOne,
скобки в sanitizeName). Прошивка 5.2.0: 77% flash, 26% RAM (BSS).

**Боевая приёмка подтверждена владельцем** (04.08.2026, скриншоты 116–117):
заголовок «База пользователей (7/250)», текущая прошивка 5.2.0, OTA fw+fs

## Релиз 5.5.7 — самодиагностика: собственный SNTP-клиент и честная машина состояний NTP (2026-08-10)

### Мотивация
Локализация дефекта NTP на мастере завершилась вердиктом: **запросы SNTP даже не покидают устройство** (Torch на MikroTik — пусто, при том что замок с той же сети синхронизируется за 755 мс). Стандартный lwIP-SNTP на связке ESP32-S3 + W5500 (MACRAW over SPI, core 3.3.11) молча не отправляет пакеты — и, что хуже, **не сообщает об этом ни слова**. Пороговая детекция «время ≥ 2025-01-01» маскировала проблему: лог писал «NTP synced» без единого ответа сервера. Диагностика, которая врёт оператору, — хуже её отсутствия.

### Что сделано
1. **SntpCore.h (новый, чистая логика, host-тестируемый)** — сборка запроса (48 байт, 0x1B) и строгий разбор ответа: длина ≥ 48, mode==4 (server), stratum ≥ 1 (0 = kiss-o'-death), timestamp ≥ эпохи NTP, unix ≥ 2025-01-01. Любое отклонение — отброс, без «почти похоже».
2. **TimeService: собственный SNTP-клиент на WiFiUDP** вместо configTime/lwIP sntp:
   - асинхронный DNS через `dns_gethostbyname` (колбэк-трамплин выставляет только volatile-флаги из tcpip_thread);
   - числовой IP — быстрый путь без резолва;
   - постоянный UDP-сокет-член, пересоздание перед каждым запросом;
   - каждый шаг логируется: «NTP: запрос -> X:123 (desc), попытка #N».
3. **Честная машина состояний NtpState**: IDLE → RESOLVING → REQUESTED → SYNCED | WAIT_RETRY:
   - таймаут ответа 5 с → «NTP: X молчит 5 с (попытка #N) — переарм через 60 с»;
   - таймаут DNS 5 с → «НЕ РЕЗОЛВИТСЯ»;
   - отказ отправки → «ОТПРАВКА НЕ УДАЛАСЬ — UDP-стек отказал» (сигнал, что мёртв и raw UDP на W5500);
   - SYNCED: RTT в лог, setSystemTime → RTC, суточный ресинк (86 400 с);
   - IP_CHANGED: сброс счётчиков и немедленный новый запрос.
4. **Пороговая детекция УДАЛЕНА полностью** — synced выставляется только по реальному валидному ответу сервера. Время из RTC после ребута — «время есть, источник RTC», но не «NTP synced».
5. **Панель мастера**: бейдж источника времени теперь показывает состояние машины и счётчик попыток вживую («нет · wait_retry · попыток 5» / «NTP · RTT 3 мс»); hm/info отдаёт ntp_state/ntp_attempts/ntp_rtt_ms.
6. **Host-тесты: 1009/1009 PASS** (+11 тестов SntpCore: корректный запрос, валидный ответ, 9 классов отбраковки).
7. Mock-приёмка панели: оба состояния бейджа подтверждены в chromium.

### Размеры
- smart_lock: 1 093 504 B (83%), full_4mb 4 128 768 B.
- home_master: 1 082 288 B (82%), littlefs 3 538 944 B (round-trip MD5 MATCH), full_16mb 16 711 680 B.

### Бенч-протокол 5.5.7 (решающий тест)
Прошить оба устройства, открыть монитор порта мастера. Ожидаемая цепочка:
1. «NTP: запрос -> 10.146.75.1:123 (10.146.75.1), попытка #1» — запрос ушёл из TimeService.
2a. **«NTP synced: 10.146.75.1, RTT X мс — время и RTC обновлены»** — победа: виноват был lwIP sntp, собственный клиент работает на W5500.
2b. **«NTP: 10.146.75.1 молчит 5 с (попытка #1) — переарм через 60 с»** — пакет ушёл, ответа нет: смотреть Torch, виден ли запрос на проводе.
2в. **«ОТПРАВКА НЕ УДАЛАСЬ — UDP-стек отказал»** — мёртв и raw UDP на W5500: эскалация на уровень стека/ядра (кандидаты: обновление core, разбор W5500 MACRAW UDP-path).
3. Панель мастера: бейдж обновляется каждые 5 с, счётчик попыток — прямой индикатор циклов переарма.

## Релиз 5.5.8 — аварийный фикс: lwIP только в tcpip_thread (2026-08-11)

### Инцидент 5.5.7 (полевой бенч, log1(12))
Оба устройства после прошивки 5.5.7 ушли в бутлуп: `assert failed: udp_new_ip_type (lwip udp.c:1278): Required to lock TCPIP core functionality!` сразу после получения IP — **включая Safe Mode** (recovery-веб недоступен, счётчик бутлупа дошёл до 12). Класс дефекта — самый тяжёлый: устройство не восстанавливается само, нужна перепрошивка по UART. Принято, разобрано, исправлено.

### Расследование (addr2line по бэктрейсу)
Цепочка падения: `TimeService::onEvent` (TimeService.cpp:105) → `requestNtp` (:129) → `dns_gethostbyname` → `dns_alloc_random_port` → `udp_new_ip_type` → assert. Три взаимоусиливающиеся ошибки проектирования 5.5.7:
1. **Сетевой ввод-вывод из контекста событийной задачи**: onEvent(NET_EVENT_IP_CHANGED) исполняется в задаче ETH-event (шина диспетчерит синхронно в контексте издателя), а оттуда — прямые вызовы lwIP.
2. **Сырой lwIP из чужих потоков без лока**: в IDF 5.x (core 3.3.x) включён LWIP_TCPIP_CORE_LOCKING; вызовы `dns_gethostbyname`/`udp_*` вне tcpip_thread без LOCK_TCPIP_CORE — assert. Проверкой исходников ядра подтверждено: `NetworkUdp.cpp` (он же WiFiUDP) в core 3.3.11 **не берёт лок вообще** — то есть WiFiUDP::begin/parsePacket из loopTask тоже были бы бомбами (recv-путь оперирует pbuf).
3. Почему configTime (5.0–5.5.6) никогда не падал: lwIP sntp весь свой UDP исполняет внутри tcpip_thread через tcpip_callback. Это и есть каноническая архитектура.

### Фикс 5.5.8 — архитектурный, не заплатка
- **ВЕСЬ lwIP — только внутри tcpip_thread**: задание (сервер из конфига) постится через `tcpip_callback` (без блокировки loopTask); создание pcb, DNS, отправка, приём — в колбэках tcpip_thread; наружу — только volatile-фазы (NtpPhase: DISPATCHING/RESOLVING/SENT/RX_READY/DNS_FAIL/SEND_FAIL). WiFiUDP удалён из TimeService полностью.
- **onEvent и HTTP-API — только флаги**: IP_CHANGED и forceNtpSync ставят `_ntpPending`; исполняет tick в контексте loopTask. Новое железное правило ядра: *ни один обработчик событий и ни один HTTP-хендлер не трогает сетевой стек напрямую*.
- Новое состояние автомата **DISPATCHING** (задание в очереди tcpip_thread) с таймаутом 5 с — теперь видна даже смерть tcpip_thread: «tcpip_thread не исполнил задание за 5 с — стек мёртв?».
- Один udp_pcb на всю жизнь устройства (как у sntp), приём armed навсегда.
- RTT теперь из меток tcpip_thread (sentAtMs/rxAtMs), точнее прежнего.
- Host-тесты 1009/1009; sl 1 089 282 B (83%), hm 1 078 188 B (82%); littlefs мастера пересобран и сверен по распакованному содержимому (разница образов — только mtime в gzip-заголовках).

### Уроки (железные правила)
1. **Никакого lwIP/UDP/TCP-API вне tcpip_thread без лока.** Сетевые операции из модулей — через tcpip_callback или очередь заданий, исполняемую владельцем стека.
2. **onEvent — только флаги.** Обработчик события не знает, в чьей задаче его вызвали; любая тяжёлая работа — в tick.
3. HTTP-хендлеры — тот же закон: forceNtpSync больше не исполняет сеть в задаче веб-сервера.
4. assert в lwIP — это отказ архитектуры, а не «редкий глюк»: ловить на бенче первым же прогоном обоих устройств до рассылки.
5. addr2line по .elf — обязательный первый шаг при любом бэктрейсе (здесь дал точную строку за минуту).
6. Safe Mode должен быть проверен на предмет «а не падает ли новый код и в нём» — 5.5.7 уронил и его (NTP стартует и в Safe Mode по IP_CHANGED).

### Бенч-протокол 5.5.8
Перепрошивка только по UART (устройства в бутлупе, OTA/recovery недоступны). После прошивки в мониторе порта:
1. «NTP: запрос -> X:123 (desc), попытка #1» — транспорт жив;
2. «NTP synced: …, RTT N мс» / «молчит 5 с» / «ОТПРАВКА НЕ УДАЛАСЬ» — как в 5.5.7, плюс новые: «DNS … НЕ РЕЗОЛВИТСЯ», «tcpip_thread не исполнил задание»;
3. Главный критерий 5.5.8: **отсутствие assert udp.c:1278** на обоих устройствах и в Safe Mode.

## Релиз 5.5.9 — фикс автомата NTP по результатам бенча 5.5.8 (2026-08-11)

### Полевой бенч 5.5.8 (замок, Log(9))
**Главный критерий выполнен: assert udp.c:1278 исчез полностью** — устройство работает часами, MQTT/HTTP живы, crash-loop прекращён. tcpip_thread-архитектура подтверждена полем. Самодиагностика сработала как задумано: новое состояние DISPATCHING тут же поймало следующий дефект — «tcpip_thread не исполнил задание за 5 с» по кругу каждые ~66 с.

### Дефект и разбор
Ветки DISPATCHING/RESOLVING в tick() обрабатывали PH_SENT/DNS_FAIL/SEND_FAIL, но НЕ PH_RESOLVING: при hostname-сервере (pool.ntp.org по умолчанию) DNS уходит в ERR_INPROGRESS, фаза становится PH_RESOLVING, а автомат так и остаётся в DISPATCHING до таймаута — вечный цикл, запрос никогда не доходил до лога «запрос ->». Доказано по логу: числовой путь (10.146.75.1) логировал бы отправку, hostname — застревал молча; наблюдалось второе.
Попутно закрыт второй латентный случай: PH_RX_READY прямо из DISPATCHING (по LAN ответ приходит за ~1 мс — раньше ближайшего тика loopTask; в 5.5.8 такой ответ игнорировался до таймаута).

### Фикс 5.5.9
- DISPATCHING + PH_RESOLVING → переход в RESOLVING (лог «резолв %s (async DNS)...»), далее штатно.
- PH_RX_READY принимается из DISPATCHING/RESOLVING как «запрос ушёл И ответ уже здесь» — попытка засчитывается, разбор ответа веткой REQUESTED; RTT по меткам tcpip_thread, задержка тика на точность не влияет.
- Host-тесты 1009/1009; sl 1 089 370 B (83%), hm 1 078 188 B (82%); merges сверены по app-секции.

### Инцидент OTA 5.5.7→5.5.8 (log1(13))
OTA из бутлупящейся 5.5.7 «завершился», но устройство продолжило грузить 5.5.7 с 0x150000. Гипотезы: (а) финализация (esp_ota_end/set_boot_partition) оборвана очередным assert'ом — окно жизни 5.5.7 после IP всего ~1 с; (б) в OTA загружен full-образ (для UART) вместо app-бинаря. Полное стирание + UART-прошивка 5.5.8 решила. Правило: **OTA — только smart_lock.ino.bin (app); full_4mb/full_16mb — только для UART**. Кандидат в 5.6.x: UpdateService отвергает образ больше OTA-партиции и валидирует заголовок приложения до записи; OTA из бутлупящейся прошивки считать негарантированным.

## Релиз 5.5.10 — DNS-терпеливость под холодный upstream (2026-08-11)

### Полевой бенч 5.5.9 — ПОБЕДА: синкаются ОБА устройства

- Замок: 192.36.143.130 (synced RTT 69 мс, попытка #1), pool.ntp.org (1 таймаут → synced RTT 66 мс на 75-й секунде).
- «Замок не синкается по имени» — ложная тревога: вторая проверка была прервана ребутом до завершения 60-секундного переарма; по логу замок по hostname синкается так же, как мастер.

### Разбор: почему hostname идёт «со второго захода»
Наш DNS-таймаут наблюдения 5 с срабатывал РАНЬШЕ, чем lwIP завершает собственную лестницу ретраев (несколько серверов × растущие таймауты, суммарно ~5–15+ с) против холодного upstream за MikroTik. Запрос lwIP при этом НЕ умирал — он дорезолвивался в фоне, попадал в кэш, и следующий 60-с переарм отправлял NTP уже по кэшу (ERR_OK). Потому synced всегда случался на 72–156-й секундах, а не на 5–10-й.

### Фикс 5.5.10
NTP_DNS_TIMEOUT_MS 5000 → 15000: ждём lwIP до конца его лестницы. Теперь первый же цикл: «резолв …» → (до 15 с терпения) → «DNS X -> Y» → «запрос ->» → «synced». Host-тесты 1009/1009; sl 1 089 520 B (83%), hm 1 078 432 B (82%); merges сверены по app-секции.

## Релиз 5.5.13 «БД и мастер-ключ» (12.08.2026): ПРИНЯТ НА МОКЕ, доставлен

Решение владельца (по итогам инцидента 12.08): «если зеркало пусто и БД пуста,
то при добавлении через вэб форму первая карта... выскакивало-бы предупреждение,
что это должен быть мастер-ключ. Тогда мы и этот канал возможных
нестыковок/ошибок закроем». Реализовано сильнее: не предупреждение, а гвард.

**1. Гвард первой карты (замок, веб-канал).**
Физический путь (поднесение к считывателю на пустой БД) всегда назначал
первую карту мастером; веб-форма оставалась единственным каналом создать
первую карту «просто картой» — именно этим путём оператор и создал мастера
с типом «Постоянный». Теперь apiKeysAdd при count()==0 принудительно
назначает тип MASTER (как физический путь) и возвращает first_master:1.
Панель на пустой БД блокирует выбор типа (disabled, значение «Мастер-ключ»),
показывает жёлтую плашку «👑 База пуста: первая карта всегда становится
Мастер-ключом — как при поднесении к считывателю», а после добавления —
тост «Первая карта пустой базы — назначена МАСТЕР-ключом».

**2. Автозапечатывание зеркала БД (замок).**
NVS-зеркало (db_backup/db_raw, монолит-формат) больше не устаревает тихо:
nvsBackupNow() вызывается после КАЖДОЙ успешной мутации БД (add / remove /
update / setBlocked / clear) и в суточном тике. В recordUse (каждый проход)
НЕ запечатываем — слишком часто, ресурс флеша.

**3. Возраст зеркала (замок).**
Мета запечатывания пишется ОТДЕЛЬНЫМ NVS-ключом db_meta (`{"u":unix,
"fw":"x.y.z"}`) — формат db_raw не тронут, монолит-совместимость свята.
/api/status отдаёт mirror_u + mirror_fw; перед «Восстановить из NVS»
подтверждение показывает «зеркало от DD.MM.YYYY, HH:MM:SS, fw X.Y.Z»
(старое зеркало без меты — честное «возраст НЕИЗВЕСТЕН»). Восстановление
по-прежнему «осознанно, понимая что делаешь» — но теперь не вслепую.

Версии: ядро 5.5.12 → 5.5.13, SmartLockApp 5.5.6 → 5.5.13,

### РЕЛИЗ 5.8.0 — «Живая телеметрия ПАЗ, антифлуд, скачивание журнала» (15.08.2026)

Закрывает ночную эпопею 14→15.08 (защёлкнутый HEAP_CRITICAL, 1488 строк
шума в журнале, 11 ложных cpu_temp STUCK/час) и утверждённые ранее
дизайны (аккордеон 13.08, «Скачать журнал» 14.08).

**Состав:**
1. **HealthMonitor — новая семантика heap (ядро, оба профиля).** Было:
   проверка каждые 30 с смотрела на since-boot watermark
   (`esp_get_minimum_free_heap_size`), который не восстанавливается —
   после одного транзиентного нырка CRITICAL защёлкивался НАВСЕГДА
   (ночь 14→15.08: «крит: 211» за 12,5 ч при полностью живом heap).
   Стало: конечный автомат по ТЕКУЩЕМУ free с гистерезисом возврата
   (HM_HEAP_HYST_BYTES=4096): события только на переходах
   Ok↔Warn↔Crit, RECOVERED при выходе. Watermark — одноразовый факт
   на новый минимум с шагом HM_HEAP_MIN_STEP_BYTES=1024 (против
   микрокасаний 5536→5380→5340 — одно дно, а не серия). Счётчики
   «пред/крит» — теперь счёт АКТИВНЫХ состояний, а не исторических
   всплесков (бэклог «семантика крит:N» закрыт самой схемой).
2. **cpu_temp: дежурный переведён со значения на ПУЛЬС чтений.** В
   тепловом равновесии квантованное 0,1 °C значение стоит часами —
   11 ложных STUCK/час. Драйвер инкрементит readSeq на каждом
   успешном чтении (EspTempDriver::getReadSeq → TelemetrySnapshot.
   cpuSeq), сторож следит за пульсом: значение может стоять — пульс
   обязан идти.
3. **Бут-грейс температурных переходов (ESP_TEMP_BOOT_GRACE_MS=15000).**
   Гонка: первый poll драйвера мог отработать с compile-time
   дефолтами 60/75/90 до применения конфига из NVS (ложный
   TEMP_CRITICAL на старте). Переходы в окне грейса запоминаются
   молча и публикуются фактом после окна. Паника (105 °C) сознательно
   БЕЗ грейса — последний рубеж безопасности не задерживаем.
4. **TWDT косметика:** status-first — `esp_task_wdt_status(NULL)`;
   если ядро Arduino уже подписало loopTask, только реконфигурация,
   без ложного INVALID_STATE в логе.
5. **Антифлуд журнала (JournalService).** Серия одинаковых
   «топик+тело» подряд склеивается: первое событие пишется сразу,
   повторы считаются, при смене события выходит сводка «<тело> ×N»
   (N — повторы сверх первой строки; время сводки = время последнего
   повтора). Кап серии JRN_REPEAT_CAP=20 — длинный флуд режется на
   куски. Сводка материализуется также перед client_left, stop() и
   финальным flush по SHUTDOWN. Потерь нет: количество в N, штампы
   первого/последнего — в строках. Ночной шум 1488 строк стал бы
   ~76 строками (факт + 74 сводки ×20 + хвост).
6. **HTTP-гард (ядро).** (а) Веб-сервер поднимается через
   HTTP_WEB_DELAY_MS=10000 после появления сети, а не мгновенно:
   бут-шторм (NTP/MQTT/брокер/SD) больше не делит heap с lwIP-сокетами
   браузеров (урок 14.08: три браузера на загрузке уронили heap замка
   до 5 КБ; вкладки переподключаются сами через пару секунд). Safe
   Mode ждёт те же 10 с — цена приемлемая, ядро важнее консоли.
   (б) sendJson шлёт явный `Connection: close` (ядро 3.3.11 и само его
   шлёт — дубль на случай ядер с keep-alive).
7. **«Скачать журнал» (решение владельца 14.08).** HttpService ::
   streamFileDownload(fs::File&, имя): Content-Disposition attachment
   + streamFile кусками — сегмент целиком в heap НЕ поднимается.
   Контракт handleApiDev: statusCode==0 = провайдер уже отстримил сам,
   ядро JSON поверх не шлёт. HomeMasterUi: GET /api/dev/hm/journal/dl?n=
   <сегмент> (admin-токен, 401/404/503 честно; имя валидирует
   JournalService::segmentPath — траверсал исключён). Панель мастера:
   кнопка «⬇ Скачать» в тулбаре журнала — сегмент приходит честным
   файлом с SD, без копипаста с экрана.
8. **Аккордеон «Служебные» (дизайн утверждён 13.08).** Ядро:

   токенов, пробелы по краям не значат); toJson помечает поля

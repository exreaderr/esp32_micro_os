# Запрос к ядерной ветке: два дефекта автономности (CC1101 + сетевой стек)

Дата: 10.09.2026
От: ветка weather_gate (профиль 0.7.1, ядро 5.9.0)
Тип: запрос на доработку ЯДРА (2 пункта, оба — автономность флота)
Основание: два инцидента на железе 09–10.09.2026, задокументированы
по двум независимым источникам (монитор порта + журнал событий мастера).

## Пункт 1. CC1101 не восстанавливается после тёплого ребута

**Факт (09.09, ~23:21):** после штатной смены поля CFG_CRITICAL
(wx.rf_agcctrl1) контроллер перезагрузился программно (sw_restart —
видно в событиях мастера). После загрузки эфир молчал полностью:
0 пакетов, 0 дублей, RSSI 0, WARN RADIO_NO_PACKETS (ПАЗ отработала
корректно — зафиксировала тишину).

**Ключевое наблюдение:** кнопка сброса (ещё один тёплый ребут) НЕ помогла.
Приём восстановился только после полного снятия питания.

**Причина (архитектурная):** у CC1101 нет проводного RESET. Тёплый ребут
ESP перезапускает прошивку, но радиочип сохраняет своё состояние; если
он к моменту ребута был в невалидном состоянии (зависший MarcState,
рассинхрон SPI), текущая инициализация драйвера его не выводит.

**Предложение:** в драйвере CC1101 (ядро):
1. При init — безусловная последовательность сброса: SRES-строба
   (в т.ч. с ручным формированием CS/SI по таймингам для выхода из
   любого состояния), ожидание готовности кристалла, затем полная
   перезапись регистров и readback-верификация (chip version / PARTNUM).
   Если readback не сошёлся — ошибка init в лог, а не молчаливый «ok».
2. В рантайме — сторож по MarcState/тишине: если при валидной частоте
   и живом GDO0-прерывании N минут нет пакетов И MarcState не в RX —
   одна переинициализация чипа без ребута контроллера (с записью
   в журнал ПАЗ).

**Почему это ядро:** драйвер CC1101 — ядерный (MicroOS/src/drivers),
профиль его не трогает и SPI напрямую не владеет.

## Пункт 2. Заклинивание сетевого стека после кратного провала связи

**Факт (ночь 09→10.09):** шлюз, аптайм от 23:34. В 02:22 кратная
деградация LOCAL_NET → через 2 минуты RECOVERED FULL (события мастера).
Далее сетевой стек заклинен: с ~08:40 и до снятия питания в 10:56
(окно лога порта) — непрерывно, каждые 500 мс:

```
E (...) ping_sock: esp_ping_new_session(267): create socket failed: -1
[...] [W] [NetworkService] ping session create failed
```

Open-Meteo (HTTPS-клиент профиля) в том же окне: fetch failed ×4.
При этом система ЖИВА: тики идут, TWDT молчит, RTC hourly sync пишется,
панель отвечала — «упала» только сеть. Контроль: forecastTask профиля
проверен, http.end() вызывается безусловно — утечки сокетов в нашем
коде нет; остальные участники сети (ping-контроль шлюза, WebServer,
MqttTransport, NTP) — ядерные.

**Диагноз:** lwIP не может выделить сокет (esp_ping_new_session = -1) —
исчерпание сокетов/pbuf или битое состояние netif после ночного провала
связи. Самовосстановления нет вообще: только power cycle.

**Предложение:**
1. Диагностика: при провале esp_ping_new_session логировать счётчики
   lwIP (свободные/занятые сокеты, pbuf, heap) — иначе причина утечки
   невидима.
2. Аудит жизненного цикла сокетов: WebServer (keep-alive, висячие
   клиенты), MqttTransport (переподключения), NTP — кто оставляет
   сокеты при обрывах.
3. Крайняя мера автономности (флот-функция): сторож «сеть мертва
   N минут при живом линке» → программная перезагрузка с записью
   причины в журнал ПАЗ. Устройство без сети и без самовосстановления
   автономным не является.

## Приоритет

Оба пункта — про автономность: устройства флота стоят без присмотра,
«съездить передёрнуть питание» — не эксплуатационная модель.
Пункт 2 считаем более приоритетным (затрагивает ВСЕ профили и ядро,
воспроизводится на «голом» сетевом контуре без нашей периферии).
Пункт 1 специфичен для профилей с CC1101.

**Приложения:** выдержки лога порта и журнала событий мастера с
временными метками — в ветке weather_gate (дорожная карта, запись
от 10.09.2026).

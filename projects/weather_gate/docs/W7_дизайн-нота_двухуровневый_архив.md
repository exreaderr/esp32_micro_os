# W7 — Дизайн-нота: двухуровневый архив погодных данных (шлюз ↔ мастер)

Профили: weather_gate 0.9.0 → 0.9.1 (клиент восстановления),
home_master (архивариус — новый модуль профиля, НЕ ядро).
Ядро 5.9.5 — неизменно (ЗАКОН ФЛОТА). Дата: 20.09.2026.
Статус: на утверждение владельцем. Код — после утверждения.

---

## 1. Постановка (решения владельца 20.09)

- Шлюз хранит «короткие» данные у себя; длинный архив — на мастере (SD 32 ГБ, примонтирована, `sensor.home_master_sd_sostoianie = mounted`).
- При обновлении шлюза (пара bin+littlefs стирает /datalog) шлюз **запрашивает свои же данные за последние 7 дней у мастера** и восстанавливает яруса — графики не пустеют.
- **Мастер пишет архив, подписываясь на MQTT** (weather-топики шлюза уже retained — архивариусу хватит подписки, шлюз в части записи не меняется).
- **Восстановление — MQTT запрос-ответ** (выбор владельца; HTTP-вариант отклонён).

## 2. Фактура (что уже есть)

- Шлюз: 5 dlog-каналов (wx_ot, wx_oh, wx_p, wx_w, wx_r). Яруса: часовой 744 записи = 31 сутки (≈12 КБ/канал), суточный 366 = год. Ребут яруса не теряет (LittleFS); теряет только перепрошивка ФС.
- Формат записи яруса: `DlogAggr` 16 Б (ts, mn, mx, avg...). 7 дней = 168 часовых записей/канал; 5 каналов ≈ **13,4 КБ бинаря** на восстановление.
- MqttTransport: `subscribeExternal(topic, handler)` — ядерный примитив подписки для профилей (мастер использует как есть). `publishRaw` — публикация в полный топик. Бюджет: MQTT_BODY_LEN=256 для publish-API с буфером; publishRaw онлайн — без капа (0.9.0 weekly 477 Б проходит), офлайн outbox дропнет (приемлемо: восстановление при живом MQTT).
- Мастер уже умеет: подписки (профиль home_master имеет карту зависимостей), SD запись (mounted), восстановление конфигов по сети (реализовано и работает — образец UX).

## 3. Архитектура

### 3.1. Архивариус на мастере (профиль home_master, новый модуль HmArchiveModule)

- Подписка: `microos/<gw_id>/weather` (retained → мгновенный старт) — из weather-JSON пишем точки температуры/влажности/давления/ветра/дождя в свой архив-лог на SD.
- Хранение: append-only файлы на SD: `/littlefs`-подобно, но на SD: `/sd/archive/wg/<канал>.log` — бинарные записи 16 Б (тот же DlogAggr-layout: ts+mn+mx+avg), ротация по году. 5 каналов × 17 568 записей/год × 16 Б ≈ **1,4 МБ/год** — 32 ГБ это века.
- Точность: weather-JSON идёт раз ~48 с; архив пишет **часовые ведра** (та же логика Bucket — переиспользуем DataLogCore? Нет: ядро менять нельзя, но DataLogCore.h — чистая логика в ядре, инклюд и использование профилем допустимы, как делает weather_gate; либо своя минимальная копия bucket-логики в профиле мастера. Решим при реализации — предпочтительно переиспользование без правок).
- Идемпотентность: запись с ts ≤ последнего записанного — пропуск (retained-повторы при реконнектах не дублируются).

### 3.2. Восстановление (шлюз 0.9.1 + мастер), MQTT запрос-ответ

Топики (префикс master из конфига мастера; id — deviceId шлюза):
```
microos/master/archive/req   ← шлюз: {"id":"<gw_id>","days":7,"part":0}
microos/master/archive/resp/<gw_id> ← мастер: куски (см. ниже)
```

Протокол нарезки (13,4 КБ не влезают в одно сообщение):
- Ответ — серия кадров, каждый ≤ 200 Б payload: заголовок кадра ASCII
  `AR1|<ch>|<idx>|<of>|<ts0>|` + бинарный хвост? **Нет** — MQTT у нас текстовый
  (payload NUL-терминирован). Поэтому кадр — hex/base64? Base64 раздувает
  13,4 КБ → 18 КБ, ~95 кадров по 200 Б. Терпимо (раз в прошивку), но шумно.
- **Альтернатива проще:** передаём не бинарь, а текстовый JSON построчно:
  один кадр = один канал-день: `{"ch":"wx_ot","day":0,"r":[[ts,mn,mx,avg],...24]}`
  ≈ 24 записи × ~25 Б ≈ 600 Б на кадр — publishRaw онлайн тянет (weekly 477 Б
  уже ходит). Всего 5 каналов × 7 дней = **35 кадров по ~600 Б**. Шлюз парсит
  strstr'ом с якорями (урок №25) — JSON-парсер уже обкатан. Выбираю этот
  вариант: текст дороже бинаря, но не нужен base64-декодер и отладка глазами
  в MQTT Explorer тривиальна (проверено: владелец им пользуется).
- Шлюз принимает кадры по подписке `archive/resp/<id>`, складывает в RAM-образ
  яруса (5 × 168 × 16 Б = 13,4 КБ кучи, временно), по кадру `end` (счётчик
  сходится) — атомарно переписывает `/datalog/H_*.bin` и применяет.
- Таймаут: не собралось за 60 с — молчаливая деградация, остаёмся с пустым
  dlog (как сейчас), повтор при следующем старте.

Триггер запроса: при старте, если dlog часового яруса пуст/короче суток И
MQTT подключён И мастер ответил на `req` положительно. Запрос один раз за
загрузку, не чаще.

### 3.3. Что НЕ делаем

- Ядро не трогаем: всё — профильный код (мастер + шлюз).
- Суточный ярус шлюза не восстанавливаем (неделя часового достаточна;
  суточный сам накопится).
- Конфликт «у шлюза есть свежие часы, у мастера старьё»: мердж по ts,
  свежая локальная запись побеждает (правило: локальное новее архива —
  оставить локальное).

## 4. Ворота качества (стандартные + новое)

- Host-тесты: сериализация/парсинг кадров, мердж по ts, границы (0 кадров,
  битый кадр, дубликаты). Норма 43958 PASS/0 FAIL — только растёт.
- Прогон 4 профилей, readback меток, ФС round-trip 3/3.
- Полевой тест: перепрошивка шлюза → графики 7 дней на месте без ожидания.

| Сторона | Файлы | Оценка |

Риски: объём RAM-образа 13,4 КБ при восстановлении — держим однократно,

## 6. Ревизия 2 (20.09.2026): решения ядерной ветки — приняты все

Ответ ветки (docs/Ответ_ветке_weather_gate_W7.md). Уточнения контракта,
включённые в проект:

1. **Архивариус — профиль home_master.** В ядро — по факту второго
   потребителя (правило обобщения ветки). Ядро под W7 не меняется.
2. **Технические условия ядра для архивариуса:**
   - запись часового ведра одним flush'ем, сеанс open→append→close
     короткий (без вечно открытого дескриптора) — урок питания 15.09;
   - tick мастера не держать дольше десятков мс, без сканов каталога
     на каждый append;
   - пространство имён на SD: `/archive/<host>/<канал>.w7a` — сразу
     с именем устройства, второй источник вписывается без миграции.
3. **Транспорт: MQTT запрос-ответ — подтверждён.** У ядра bulk-трансфера
   нет и не планируется. Уточнение протокола от ветки: каждый кадр несёт
   `seq`/`total` и CRC кадра; сборщик шлюза при несовпадении CRC
   переспрашивает **кадр** (`archive/req` с номером), не весь пакет;
   таймаут 60 с и молчаливая деградация — одобрены. Прецедент publishRaw
   477 Б онлайн — канон для кадров.
4. **Формат: DlogAggr 16 Б — канон флота.** Плюс требование ветки:
   заголовок файла архива = магия + версия формата + имя канала
   (самоописывающий файл «с SD-карты руками через год»).
5. **Keepalive TCP:** копилка, не код, Issue не нужен — закрыто.

### Контракт топиков (сверка с веткой до кода)

```
# запрос (шлюз -> мастер), retained=false
microos/master/archive/req
  {"id":"<gw_id>","days":7}                  — полный набор
  {"id":"<gw_id>","seq":<n>}                 — переспрос кадра (CRC не сошёлся)

# ответ (мастер -> шлюз), retained=false
microos/master/archive/resp/<gw_id>
  {"seq":<n>,"total":<N>,"ch":"<chan>","day":<d>,"crc":<u32>,
   "r":[[ts,mn,mx,avg],...до 24 записей]}
  последний кадр: seq == total-1
```

Кадр ≤ ~700 Б (24 записи × ~28 Б + обвязка). CRC — CRC32 поля `r`
(полином ядерный, если есть в DataLogCore/CRC-утилитах — переиспользуем;
иначе стандартный CRC-32/MPEG-2, фиксируем в коде обеих сторон).
Триггер запроса на шлюзе: старт + пустой/короткий (<24 ч) часовой ярус +
MQTT подключён. Один запрос за загрузку.

*На утверждение. После «добро» — реализация поэтапно: сначала архивариус
мастера (накопление), затем восстановление шлюза.*

## 7. Ревизия 3 (20.09.2026): контракт УТВЕРЖДЁН, пять штифтиков ветки

Письмо ветки: docs/Ответ_ветке_weather_gate_W7_контракт.md. Вердикт —
утверждено. Разделение сторон: архивариус (home_master) делает ядерная
ветка сама; наша сторона — восстановление в weather_gate 0.9.1.
Стороны идут параллельно, контракт зафиксирован.

Штифтики (зафиксированы в коде обеих сторон):

1. **Семантика `day`:** 0 — самый старый день набора, days−1 — сегодня;
   записи внутри `r` — по возрастанию ts.
2. **CRC32 — zlib-вариант:** полином 0xEDB88320, init 0xFFFFFFFF,
   xorout 0xFFFFFFFF, вход — сырые байты сериализованной строки поля `r`
   как есть (проверяемо снаружи через Python zlib.crc32).
3. **Темп выдачи мастером:** не залпом — очередь кадров, один кадр за
   тик (100–200 мс). Условие ядра к архивариусу (их сторона).
4. **Пустой архив:** немедленный `{"seq":0,"total":0}` — шлюз
   деградирует мгновенно, не дожидаясь таймаута.
5. **Антидребезг:** мастер игнорирует повторный полный req от того же
   id в течение 120 с (их сторона); у шлюза — один запрос за загрузку.

Подтверждено без правок: топики retained=false; текстовые кадры;
≤700 Б онлайн-only; идемпотентность по ts; мердж «локальное новее
побеждает»; суточный ярус не восстанавливаем; RAM-образ 13,4 КБ на boot
(контроль — max block в net health); переиспользование DataLogCore.h
мастером без правок ядра — допустимо.

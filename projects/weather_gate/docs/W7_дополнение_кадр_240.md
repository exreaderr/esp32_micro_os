# W7 — Дополнение к контракту: кадр ≤ 240 байт (входящий кап MQTT)

**Дата:** 20.09.2026. **На:** контракт, утверждённый письмом «W7: контракт
утверждён (с пятью штифтиками)». **Тип:** одно уточнение, обнаруженное при
кодосторении; без него протокол не заведётся.

## Факт

Прецедент «weekly 477 Б проходит» — это ИСХОДЯЩИЙ путь (publishRaw,
esp_mqtt_client_publish len=0, онлайн без капа). Кадры `archive/resp`
идут ВХОДЯЩИМ путём (subscribeExternal), а он капает payload:

- MqttTransport: `ExtSub.payload[MQTT_BODY_LEN]`, копирование через
  `bbuf[MQTT_BODY_LEN]`; MQTT_BODY_LEN = 256 (постмортем 5.0.x —
  uint8_t оборачивался в 0, с тех пор фиксирован 256).

Итого: кадр ~700 Б будет молча усечён до 255 байт, CRC не сойдётся
никогда, сборщик уйдёт в вечный переспрос.

## Предлагаемая правка контракта (одна цифра)

**Кадр ≤ 240 байт payload** (запас под 256 с учётом обвязки). Состав:
до **6 записей** на кадр (`[ts,mn,mx,avg]` ≈ 25–30 Б/запись + обвязка
~60 Б). Набор 7 дней × 5 каналов = 840 часовых записей → **~140 кадров**
по ~200 Б ≈ 28 КБ трафика раз в прошивку.

Почему это нормально: решение владельца («притекут по частям, медленно —
не страшно, важно что вернутся») прямо покрывает рост числа кадров;
темпованная выдача (штифтик 3) уже утверждена, 140 кадров × 150 мс ≈
21 с выдачи — сопоставимо с заявленным.

## Что НЕ меняется

Топики, seq/total, CRC32 zlib над строкой поля `r` как есть, day=0 —
самый старый, total=0 для пустого архива, антидребезг 120 с, таймаут
сборки 60 с, мердж «локальное новее побеждает», суточный ярус не
трогаем. Формат записи DlogAggr 16 Б, заголовок файла архива
магия+версия+канал — всё по утверждённому.

## Просьба

Подтвердить «кадр ≤ 240 Б, до 6 записей» — архивариус на стороне ветки
режет по 6 записей вместо 24. Со стороны шлюза код собирается
размер-агностично (парсеру всё равно, 6 или 24 записи в кадре), правка
контракта на нашу сторону кодом не бьёт.

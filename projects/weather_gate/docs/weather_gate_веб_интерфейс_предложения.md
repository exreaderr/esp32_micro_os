## 1. Что было в монолите и что из этого забрать

| Функция монолита | Оценка архитектора | Решение |
|---|---|---|
| Карточки Mushroom: мин/макс + шкала-полоса | Мин/макс в монолите — сессионные (RAM, обнулялись ребутом). У нас есть DataLog с настоящими суточными min/max — сделаем **лучше** | ✅ Блок A |
| Роза ветров (компас, 16 румбов, плавная стрелка) | Чистый CSS/JS, ~40 строк, данных не добавляет | ✅ Блок A |
| Прогноз Замбретти + тенденция давления | Уже утверждён ядром как W5 слой 1 | ✅ Блок A (тренд), W5 (прогноз) |
| Карточка «Система»: uptime, MQTT, радио OK, батарея станции, ID датчика | Умная диагностика одной строкой; всё уже есть в weatherJson и ядерных статусах | ✅ Блок A |
| Шкалы-полосы (temp −30..+50, давление 970–1050 и т.д.) | CSS only, нулевая цена | ✅ Блок A |
| Сканер АЧХ 914.80–915.20 МГц, click-to-tune | Нужно расширение драйвера (2 метода). В монолите был публичным — **уходим в админку** (решение владельца) | ✅ Блок B |
| Кнопки подстройки частоты ±0.01/0.02/0.05 | Тот же driver delta, что и сканер | ✅ Блок B |
| Настройки через веб (hostname, MQTT, высота…) | **Не нужно** — ядерная админка /admin уже редактирует весь конфиг с валидацией | ❌ дубль ядра |
| Своя аутентификация (sha256 PIN, роли) | **Не нужно** — ядерный токен + requireAdmin | ❌ дубль ядра |
| Синхронизация времени с браузера | Уже в ядерной админке (/api/time/*) | ❌ дубль ядра |

## 2. Блок A — публичная страница «до кондиций» (без смены драйверов)

**Принцип:** публичная часть самодостаточна — весь набор данных из одного
публичного `/api/dev/weather`. Для этого контракт weatherJson **расширяется
аддитивно** (старые поля не меняются, WeatherMirror мастера не ломается):

```
+ "tmin24":.., "tmax24":..      — из DataLog wx_ot (aggr 24ч)
+ "pmin24":.., "pmax24":..      — из wx_p
+ "wmax24":..                   — макс ветра из wx_w
+ "trend": -1|0|+1              — баротренд 3ч из wx_p (простая версия,
                                  в W5 заменится классификатором слоя 1)
```

Вёрстка новой публичной страницы:

- **Герой-карточка** (как сейчас): большая температура, состояние,
  ощущается-как.
- **Сетка метрик** в стиле монолита, но в нашей тёплой палитре и с данными
  из БД: температура (мин/макс 24ч + шкала), влажность (шкала), давление
  (мин/макс 24ч + шкала, мм рт.ст.), дождь (мм/ч + шкала), ветер (макс 24ч
  + шкала), **роза ветров** — компас со стрелкой и 16 румбами.
- **Карточка прогноза**: пока — тенденция давления (↑ растёт / → стабильно /
  ↓ падает) с честной подписью «прогноз появится в W5»; в W5 сюда встаёт
  Замбретти без переделки вёрстки.
- **Строка состояния**: батарея уличного блока, возраст пакета, RSSI,
  ID станции, температура в котельной (BME280) — мелкой строкой.

Объём: правка wx.html + additive-поля в WeatherGateApp::weatherJson
(считаются из своего же DataLog, нового хранилища нет). Host-сьют
пополнится тестами вычисления тренда. Ворота стандартные.

## 3. Блок B — сканер АЧХ в админской части (после приёмки мерджа)

**Почему отдельно и позже:** сканеру нужны два публичных метода драйвера —
`setFreqMHz(float)` (ретюн на лету) и `readRssiNow()` (мгновенный RSSI,
не пакетный). Драйверы прямо сейчас мержатся ядерной веткой в
`MicroOS/src/drivers/` — вносить в них правки до возврата пакета на
приёмку = разойтись версиями. Правильная последовательность: приёмка
мерджа → дельта драйвера через Issue #1 (методы общие, RX-only,
доктрину не нарушают) → сканер.

**Архитектура сканера в новой системе:**

- **ScanCore.h** (host-тестируемая чистая логика): план свипа (21 точка,
  шаг 0.02 МГц вокруг wx.rf_freq_mhz), накопление матрицы RSSI,
  рекомендация центра (максимум с проверкой ширины горба), валидация
  кликнутой частоты. Тесты — в общий сьют, норма только растёт.
- **App-конечный автомат**: по команде админа входит в режим сканирования
  (~23 мин, dwell ~65 с на точку — ловим реальный пакет станции),
  по выходу возвращает частоту. **Важно:** на время сканирования сторож
  wg.radio приостанавливается (иначе RADIO_SILENCE через 15 мин сканирования
  — ложная тревога); событие «scan started/finished» — в журнал.
- **API**: `POST /api/dev/scan/start`, `GET /api/dev/scan` (точки, шаг,
  активность, живой RSSI), `POST /api/dev/radio/freq?f=` — все три
  строго за isAdminToken. Частота персистится через
  `ConfigService::set("wx.rf_freq_mhz", …)` — переживает ребут, попадает
  в NVS-бэкап.
- **UI**: карточка «Радиоканал» в админской секции wx.html: canvas-график
  АЧХ (линия сигнала, пунктир шума, маркер текущей частоты, живой RSSI),
  click-to-tune с confirm, кнопки ±0.01/0.02/0.05, счётчики
  пакеты/дубли/потери фронтов, кнопка «Найти лучшую частоту» с прогрессом.
  RX-only доктрина соблюдена: сканер только слушает.

## 4. Что сознательно НЕ переносим

- Настройки и смену пароля через профильную страницу (есть в ядре).
- Свою систему ролей (есть ядерная).
- Графики 24ч отдельными карточками под каждую метрику — у нас уже общий
  блок «История» с чипами каналов и диапазонами 6ч…год, он функционально
  богаче монолитного (там только 24ч и только 2 канала). Оставляем наш.

## 5. План-график

1. **Блок A (W3.2)** — можно начинать сразу, железо не нужно до финальной
   проверки; не пересекается ни с мерджем, ни со стендом.
2. Приёмка merged-пакета (когда придёт от владельца).
3. **Блок B (W3.3)** — сканер, после приёмки, дельта драйвера через Issue #1.
4. **W5** — Замбретти в готовую карточку прогноза + слой 2 + soak 72 ч.

*Правило стоит: одна правка — один прогон ворот; норма host-сьюта не
падает; ядро не трогаем, расширения — через Issue #1.*

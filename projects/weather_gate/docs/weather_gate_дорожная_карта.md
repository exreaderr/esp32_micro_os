# weather_gate — дорожная карта проекта

## История вопроса (происхождение названия)

Владелец, имея хорошую погодную станцию с уличным блоком и домашним монитором,
захотел подключить её к компьютеру — собирать, накапливать и анализировать
данные с уличного блока. Штатное ПО оказалось только под Windows и притом
«кривое»; забрать данные с домашнего монитора по USB не удалось. Тогда
возникла идея изготовить устройство, которое **само получает сырые данные
с уличного блока параллельно родному монитору**, обрабатывает их и отдаёт
дальше потребителям в удобоваримом виде. А что это, как не **шлюз**, через
который данные текут тому, кто их запрашивает — отсюда и имя: weather_gate.

Из этой предыстории выросли ключевые доктрины профиля: радио строго
receive-only (ничего не передаём в эфир, родной монитор не страдает),
открытые интерфейсы вместо проприетарного ПО (HTTP API, MQTT retained,
графики в браузере), накопление истории своими силами (DataLog).

## Опции (отложено решением владельца)

### 💤 Датчики среды технического помещения (котельной)
**Решение владельца (W3):** шлюз стоит в котельной — температура там всегда
повышена, влажность понижена; комнатные SHT31/VEML7700 смысла не имеют.
Зафиксировано как опция на будущее, в активный план не входит.
- **Триггер возврата:** появление задачи контроля микроклимата самой
  котельной (перегрев помещения, протечки → тогда кандидаты: SHT31 0x44
  на системной I2C 32/33, датчик протечки на свободный GPIO 5/12).
- **Стоимость входа:** драйвер по образцу Bme280Driver + поля конфига в
  конец схемы + host-тесты; ядро не затрагивается.

## Стратегическое будущее: аналитический узел на ESP32-P4

- **Планы владельца (23.08.2026):** мастер переезжает с ESP32-S3-ETH
  (SD 32 ГБ) на **ESP32-P4-WIFI6-POE-ETH** + апгрейд флеша до 32 МБ.
- P4: двухъядерный RISC-V 400 МГц, векторные AI-инструкции; радио
  на модуле через companion-чип. С SD и зеркалом wx_* мастер становится
  **озером данных** глубиной сезоны/год.
- Архитектурная роль: шлюз остаётся сенсорным краем (слои 1–2),
  мастер на P4 — аналитическим узлом слоя 3: хранение глубокого архива,
  обучение/подбор модели, раздача уточнённого прогноза обратно.
  МикроОС-философия сохраняется: при отказе аналитики край остаётся
  на слое 1 и не тупеет ни на грамм.
- Это мысли на будущее — в активный план не входит, триггер: приход
  железа P4 + накопленный архив.

## Эррата платы WT32-ETH01: IO5/IO35

- **Прозвонка владельцем (20.08.2026, несколько плат):** пэд,
  подписанный шелкографией «IO35», — это фактический **GPIO35**
  (input-only, без подтяжек) — как и принято в пин-плане (CC1101 MISO).
- **Источник разночтения (расследование владельца):** опечатка в ранних
  официальных схемах Wireless-Tag (контакт назвали IO5, не имея
  отношения к GPIO5), разошедшаяся по неофициальным распиновкам.
  С версии платы v1.2 шелкография исправлена на IO35.
- **Свойства GPIO35:** строго вход (input-only), внутренних подтяжек
  в кристалле нет. Для CC1101 MISO — идеальное совпадение роли:
  линию активно драйвит трансивер, подтяжка не нужна.
- **Настоящий GPIO5** выведен на пэд **CFG** — учитывать, если он
  понадобится (опция датчиков котельной упоминает GPIO 5/12 для
  протечки: подтяжка у GPIO5 есть, валиден).
- **Изменений в коде и пин-плане НЕ требуется.** При сборке ориентир —
  фактическая прозвонка, а не надпись на плате или старые схемы.

### W3.2-diag5 — затык пойман: висячий pathTail в ядре (2026-08-26)

**Пара «трасса × serial» дала ответ.** Трасса diag4 (модалка входа, без логина):
`GET /api/dev/dlog?ch=0&range=6h → 404` за 33 мс с телом `unknown_dev_api` —
при живом токене (`/api/telemetry`, `dlog/channels`, `ota/info`, `config/backup`
в ту же секунду — 200). Тело `unknown_dev_api` ядро шлёт ТОЛЬКО когда профильный
`handleApi` вернул `false`. А в serial за все буты — полная тишина по `dlog`:
ни `admin=ok`, ни `admin=NO` (для `dlog/channels` строки есть). Обе ветки
нашего кода логируются — молчание значит: в `handleApi` пришёл `pathTail`,
который НЕ начинается с "dlog".

**Корень — в ядре, HttpService::handleApiDev:**
```cpp
const char* tail = _server.uri().c_str() + strlen("/api/dev/");  // String-временник!
bool handled = _ui->handleApi(tail, ...);                        // tail уже висячий
```
`WebServer::uri()` возвращает `String` по значению; временник умирает на `;`,
`tail` указывает в освобождённую кучу. Срабатывание — лотерея heap:
`/api/dev/dlog` (14 Б, ходовая 16-байтная корзина) затирается стабильно,
`/api/dev/lock/dlog` на замке (другая корзина) выживает — поэтому «на замке
графики замечательно отображаются», а у нас 404. Это же объясняет молчание
serial: содержимое буфера затёрто ДО strcmp.

**Правка профиля (diag5, один файл — WeatherGateApp.cpp):** безусловный лог
входа `api hit: tail='...' len=N tok=есть/НЕТ` первой строкой handleApi
(печатает tail дословно, %.40s) + лог `api miss` на финальном return false.
После прошивки serial покажет мусорный tail дословно — финальное
подтверждение для тикета ядру.

**Fix-заявка в Issue #1 (ядро):**
```cpp
String _uri = _server.uri();                       // держим живым
const char* tail = _uri.c_str() + strlen("/api/dev/");
bool handled = _ui->handleApi(tail, ...);
```
Проверить тот же паттерн в handleWebFile/handleNotFound.

**Попутно исправлено (diag4, подтверждено владельцем):** вход в админку больше
не «моргает» — мягкая перепроверка сессии (isRealAuthFail) работает, вход
проходит, ПАЗ/Система зелёные. «Сессия истекла» при успешном логине ушла.

**Ворота:** host-тесты профиля 43751 PASS/0 FAIL; ядро 43351/0; сборка
4/4 (weather_gate 1078474 Б). Пакет: weather_gate_W3.2_diag5.zip.

снять wx.diag (галочка) или решить об оставлении. Backlog ядра дополнен:

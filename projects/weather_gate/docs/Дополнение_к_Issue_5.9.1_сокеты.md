# Дополнение к запросу: пул сокетов lwIP (ядро 5.9.1, прогон 10–11.09)

Дата: 11.09.2026
От: ветка weather_gate
К Issue: «Запрос к ядерной ветке: два дефекта автономности» от 10.09.2026.
Статус: пункт 1 (CC1101) — ЗАКРЫТ (см. ниже). Пункт 2 — уточнение по свежему
эпизоду: диагностика 5.9.1 сработала отлично и дала опровержение гипотезы
«куча». Нужен следующий шаг.

## Что закрыто (пункт 1, CC1101)

- Стенд: 3 тёплых ребута кнопкой подряд — после каждого CC1101 init ok,
  приём восстанавливается без снятия питания, FAIL-строк readback нет.
- Бой: 1 срабатывание сторожа MarcState (0x08 != RX, ~4,5 ч аптайма) —
  приёмник переустановлен сам, приём не прерывался. Ровно то, что просили.

## Новый эпизод (11.09, ~13 ч аптайма): веб мёртв, система жива

Лог порта:

```
[43833648] [I] [HealthMonitor] HEAP new min: 17128 bytes
[47000308] [W] [NetworkService] ping session create failed x1
           (heap 81768, min 63036) — пул сокетов lwIP?
E (47030804) ping_sock: esp_ping_new_session(267): create socket failed: -1
E (47061304) ping_sock: esp_ping_new_session(267): create socket failed: -1
```

Внешний симптом: веб-страничка шлюза перестала отвечать, монитор порта жив,
тики идут, TWDT молчит.

**Ключевой вывод из диагностики 5.9.1:** куча в порядке (81 КБ свободно) —
исчерпан ПУЛ СОКЕТОВ lwIP, не RAM. Backoff работает (30 с вместо 500 мс).

**Пробел в стороже NET_DEAD — ПОДТВЕРЖДЁН измерением (11.09, вечер),
сняты обе стороны одновременно:
- MQTT ЖИВ: встроенный брокер мастера принимает телеметрию шлюза, в HA
  сенсоры свежие (аптайм 47422 с ≈ моменту эпизода; «Свободная память»
  81768 B — байт-в-байт совпадает с heap из строки ping-fail в логе
  порта, т.е. публикация шла уже ПОСЛЕ смерти HTTP).
- HTTP МЁРТВ: браузер получает ERR_CONNECTION_RESET на любой путь
  (/api/info_card, /admin) — соединение сбрасывается на уровне стека,
  listen-сокет HttpService фактически не обслуживает.
- NET_DEAD при этом молчит: критерий «нет ping И нет MQTT» состояние
  «HTTP мёртв, MQTT жив» не ловит. Это зафиксированный боевой сценарий,
  не теория.
Просим расширить:
- критерий по HTTP: сервер не принимает/не обслуживает соединения N минут;
- либо прямой критерий: создание сокета невозможно M раз подряд при живом
  линке — это уже само по себе «сеть мертва», независимо от MQTT.

**Диагностика пула:** при провале esp_ping_new_session просим логировать
счётчики сокетов lwIP (занято/свободно, по типам PCB: TCP/UDP/RAW) — иначе
утечку видно только по следствию. В ESP-IDF это доступно через
lwIP stats (MEMP_TCP_PCB и др.) или подсчёт в sockets API.

**Контекст нагрузки (честно):** профиль 0.6.1+ открыл публичные графики
и инфо-карточку — входящего HTTP стало больше (опросы панели каждые
15–30 с на вкладку + HA + мастер). Если WebServer не добирает закрытия
при грубом обрыве клиента — утечка накопится за часы. Просим аудит
HttpService на предмет keep-alive/timеout/закрытия.

**План с нашей стороны:** после сбора статуса MQTT — тёплый ребут,
прогон продолжаем; при повторе пришлем свежий лог.

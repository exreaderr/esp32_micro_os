# Дополнение 2 к запросу: сторож сработал, улика сужает диагноз до RAW PCB (ядро 5.9.2, прогон 12–13.09)

Дата: 13.09.2026
От: ветка weather_gate
К Issue: «Запрос к ядерной ветке: два дефекта автономности» от 10.09.2026
(дополнение 1 — «пул сокетов lwIP» от 11.09.2026).

## Сторож 5.9.2 — РАБОТАЕТ (первое боевое срабатывание)

Аптайм ~14,1 ч, эпизод развился и закрыт без участия человека:

```
E (50605335) ping_sock: esp_ping_new_session(267): create socket failed: -1
[50605339] [W] ping session create failed x1 (heap 69860, min 66148)
[50605350] [I] lwip pool stats (ping-create-fail): недоступны (ядро без LWIP_STATS)
... (backoff 30 с, всего 10 провалов за ~5 мин) ...
[50879839] [E] NETWORK DEAD: socket pool starved — link+IP живы,
           молчание 10 мин, ping create fails x10, heap 79664, http idle 331 с
[50879862] [C] NET_DEAD: программная перезагрузка (net.dead_reboot=1)
→ rst:0xc (SW_CPU_RESET), чистый boot, система восстановлена
```

Критерий «socket pool starved» поймал ровно эпизод 11.09-го типа, за ~5 минут
вместо часов тихого висения. Вердикт различим, причина в логе, ребут штатный.
За это спасибо — автономность закрыта.

## Ключевая улика: TCP жив, мёртв только RAW (ping)

Через 5 секунд после ПЕРВОГО провала создания ping-сессии профильный
HTTP-клиент успешно выполнил исходящий запрос:

```
E (50605335) ping_sock: create socket failed: -1
[50610213] [I] [WeatherGateApp] open-meteo: weather_code=0   ← TCP-сокет создан и отработал
```

То есть на момент клинча: link+IP живы, исходящий TCP создаётся, MQTT
(по прошлым эпизодам) жив — а не создаётся именно RAW-сокет ping.
Гипотеза сужается: исчерпывается не общий пул сокетов/PCB, а пул
RAW PCB (MEMP_RAW_PCB).

Второй системный факт — окно повторяется: аптайм эпизодов 13,0 ч (11.09,
утро), 13,2 ч (11.09, вечер), 14,1 ч (13.09). Постоянное окно до клинча =
медленная утечка с постоянной скоростью (~1 RAW PCB в ~час при лимите
порядка 8–16). Случайные стечения обстоятельств так не выглядят.

Честные оговорки:
- `http idle 331 с` в этом эпизоде НЕ доказывает смерть входящего HTTP —
  панель могли просто не открывать (входящих запросов не было).
- Срез PCB не получен: ядро Arduino собрано без LWIP_STATS, строка
  «недоступны» отработала честно.

## Просьбы к ядерной ветке

1. **Аудит парности esp_ping_new_session / esp_ping_delete_session** во всех
   путях NetworkService: backoff-цикл, reconnect, смена IP/линка, переходы
   FULL/DEGRADED. Подозрение: при некотором переходе старая ping-сессия
   (RAW PCB) не удаляется перед созданием новой — утечка 1 шт за событие.
   Периодичность «~час» совпадает с периодом какого-то часового события
   (hourly time sync? ротация?).
2. **Счётчик активных ping-сессий** в ядре (new++ / delete--), вывод в
   диагностику x1/x20 и в вердикт NET_DEAD — заменит LWIP_STATS без
   пересборки Arduino-ядра и сразу покажет рост утечки.
3. Если по п.1 пути чисты — тогда просим рецепт сборки с LWIP_STATS
   (или сказать, чем замерить RAW PCB из sketch), ловим владельца PCB
   на следующем окне.

С нашей стороны: прогон продолжаем, монитор порта пишет непрерывно,
при повторе пришлём лог. Профильные HTTP-клиенты аудированы ранее — чисты
(end() на всех путях); RAW-сокетов профиль не создаёт.
